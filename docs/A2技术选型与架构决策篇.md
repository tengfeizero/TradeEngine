## 一、选型的思维框架：先定义约束，再谈技术

大多数选型争论的根源，是双方在讨论**不同的约束条件**。技术人员争论「WordPress 和 Next.js 谁更好」没有意义——正确的问题是：**在给定约束下，哪个方案的失败概率更低？**

### 1.1 选型前必须确认的五个约束

在写任何一行代码之前，向客户（或给自己）确认这五件事：

| 约束 | 关键问题 | 为什么影响选型 |
|---|---|---|
| **① 谁维护** | 上线后谁改内容、谁处理故障？客户自己、你的团队、还是未来未知的开发者？ | 客户自己维护 → 生态成熟的方案赢；你有长期合同 → 自由度大的方案赢 |
| **② 业务复杂度** | 产品多少个 SKU？几个市场？要不要对接 ERP/CRM？ | 单市场 50 SKU 和 8 市场 5000 SKU 是完全不同的工程 |
| **③ 时间窗** | 客户有没有明确的 deadline（展会前必须上线之类）？ | 4 周内上线，WordPress；6 个月以上，Headless 可谈 |
| **④ 预算结构** | 一次性建站预算多少？有没有年度维护预算？ | 没有维护预算的项目，不要选需要持续投入的方案 |
| **⑤ 流量预期与增长路径** | 主要靠品牌搜索还是 SEO？预期月 PV 量级？ | 日均 PV < 5000，任何方案性能都够；要支撑 10 万+，架构完全不同 |

> **经验法则**：五个约束里有三个指向「简单」，就不要用复杂方案。外贸站 80% 的项目，正确答案是 WordPress——不是因为它是最好的技术，而是因为它是最不容易让项目失败的技术。

### 1.2 一个反直觉但重要的判断

**技术选型的最优解，往往不是技术最优的方案，而是「最平庸的、出问题概率最低的」方案。**

原因：外贸站是客户的营收基础设施。它宕机一天、询盘丢失一周、被黑一次，损失都远超你的开发费。所以选型时的第一排序不是「酷」，是「稳」。

## 二、WordPress vs Headless：量化决策矩阵

### 2.1 决策矩阵

评分 1–5，5 为最优。这是模板，你可以按项目调整权重。

| 维度 | 权重 | WordPress<br>+ 经典主题 | Headless<br>（Next.js + Headless CMS） | 说明 |
|---|---|---|---|---|
| 上线速度 | 15% | **5** | 2 | WP：成熟主题 + 插件，2–4 周可交付；Headless：前后端都要开发 |
| 3 年 TCO（总拥有成本） | 15% | **4** | 2 | 见 2.2 的成本拆解 |
| SEO 开箱能力 | 15% | **5** | 3 | WP：Yoast/Rank Math 覆盖 90% 需求；Headless：每个细节都要手写 |
| 多语言成熟度 | 10% | **4** | 3 | WPML/Polylang 开箱即用；Headless 需自建 i18n 工作流 |
| 性能上限 | 10% | 3 | **5** | SSG/ISR 可以把 LCP 压到 1s 级；WP 优化好一般在 1.8–2.5s |
| 定制自由度 | 10% | 3 | **5** | WP 受主题/插件约束；Headless 完全自由 |
| 维护门槛（客户侧） | 15% | **4** | 2 | WP：客户自己就能更新；Headless：改内容要经过 CMS + 前端发布流程 |
| 开发者交接难度 | 10% | **5** | 2 | 会 WP 的人满地都是；会 Next.js + Strapi + 外贸业务的人很少 |

**加权总分：WordPress 4.35 vs Headless 2.95**（权重可调，但差距通常不会逆转）。

### 2.2 三年 TCO 拆解

以一个标准项目（单市场起步、5 万–8 万预算、500 SKU 以内）为例：

| 成本项 | WordPress | Headless（Next.js + Strapi） |
|---|---|---|
| 初次开发 | 3–8 万 | 12–25 万 |
| 年度主机 | 1,500–6,000 元 | 3,000–12,000 元（Vercel/服务器 + CMS 服务器） |
| 年度商业插件/服务 | 1,500–4,000 元（WPML、WP Rocket、ACF Pro 等） | 0–6,000 元（多为开源，但 CI/CD、监控、备份要自建） |
| 年度维护工时 | 20–40 小时（更新、备份、小迭代） | 60–120 小时（依赖升级、安全补丁、前后端联动） |
| **三年合计** | **约 8–20 万** | **约 25–60 万** |

> Headless 的 TCO 高，核心原因不是开发贵，而是**维护面变成了两个系统**（CMS + 前端），每次依赖升级都是一次全链路回归测试。

### 2.3 各自的真实短板（不是官方话术）

**WordPress 的真实短板：**

- 数据库 + PHP 的性能天花板真实存在。SKU 过千、筛选维度复杂时，WP 查询会变慢，需要上对象缓存甚至 Elasticsearch
- 插件质量参差。装 15 个插件 = 15 个潜在冲突点和攻击面，需要严格的插件准入纪律
- Gutenberg 编辑体验对复杂产品页并不友好，很多团队最终还是靠 ACF + 自定义区块

**Headless 的真实短板：**

- 生态里没有「外贸站全家桶」。WPML 那种一键多语言、Yoast 那种 SEO 面板，在 Headless 里都是要自己写的代码
- 编辑预览体验割裂。运营改完内容想看效果，要理解「草稿 → 预览环境 → ISR 重新生成」的链路
- **交接成本极高**。这是外包场景的致命项：两年后客户想换开发者，能接手 Next.js + Strapi + 自定义 i18n 的人，报价是 WP 开发者的 2–3 倍

### 2.4 关于「WordPress Headless 模式」——通常不推荐

有一种流行做法：WordPress 只当后台（用 WPGraphQL 出数据），前端用 Next.js 渲染。听起来两全其美，**实际上是两头不占**：

- 失去了 WP 的服务端渲染生态（SEO 插件、缓存插件、多语言插件的渲染侧全部失效或要重新适配）
- 背上了 Headless 的全部维护成本（两套系统、两次部署、预览链路）
- 性能上限确实高了，但 WP + 好的缓存方案（页面缓存 + Redis + Cloudflare）已经能到 2s 以内，多数项目用不到这个上限

**例外情况**：客户明确需要「内容团队用 WP 后台 + 前端有 App/小程序等多端消费同一内容源」，Headless 化才有真实价值。纯网站项目不要这么做。

### 2.5 什么时候必须选 Headless

满足以下**任意两条**，再考虑 Headless：

1. 目标市场 ≥ 5 个，每个市场独立价格体系、库存、认证要求
2. SKU ≥ 5,000，或需要复杂多维度筛选/比价
3. 已有 ERP/PIM 系统作为产品数据源，网站只是消费端
4. 需要同时服务 Web + App + 小程序 + 第三方市场places 的统一内容/API 层
5. 团队有专职前端，且客户签了**年度维护合同**（否则上线即失养）

> 触发条件成立后，后端具体选哪一个 → 见 **附录 C：开源 Headless CMS 选型参考**。

### 2.6 SaaS（Shopify 等）在矩阵里的位置

补齐三个选项的完整视角：

| 场景 | 建议 |
|---|---|
| 客户只想要「能收询盘的站」，预算 < 1.5 万，2 周内上线 | SaaS 模板站，别硬做定制 |
| 客户要做小额在线批发（B2B 电商，少量多批） | **Shopify + B2B 功能**反而合适（原生支付、库存、批发价体系） |
| 纯询盘型 B2B 品牌/工厂站 | WordPress |

> 一个容易踩的认知坑：Shopify 的 SEO 天花板问题被网上过度渲染了。真实情况是——Shopify 的产品页 SEO 够用，弱的是 URL 结构灵活度和博客能力。**对询盘型站点，真正的差距在「结构性 SEO（Schema 自由度、内链策略）」，这块 WP 确实强不少。**

## 三、多语言架构：四种方案与 hreflang 实战

多语言是外贸站区别于普通企业站的第一技术分水岭，也是最容易做出「伪多语言」的地方。

### 3.1 先分清两件事：翻译工作流 vs URL 架构

很多讨论把这两者混在一起。正确的分层：

```text
┌─ 第一层：内容翻译工作流（谁来翻、怎么维护同步）
│    机器翻译 / 人工翻译 / 混合（机翻 + 母语审校）
│
└─ 第二层：URL 架构（多语言内容怎么组织、怎么告诉 Google）
     子目录 /es/ 、子域名 es.example.com 、独立域名 example.es 、参数 ?lang=es（禁用）
```

**第二层决定 SEO 成败，第一层决定用户信任。** 两层独立决策。

### 3.2 四种 URL 架构方案对比

| 方案 | 示例 | SEO 权重 | 成本 | 适用 |
|---|---|---|---|---|
| **① 子目录** | `example.com/es/` | ✅ 所有语言共享主域权重，**累积最快** | 低 | **默认选择**，90% 项目用这个 |
| **② 子域名** | `es.example.com` | ⚠️ Google 官方说一视同仁，实际权重传递弱于子目录 | 中 | 各语言要独立部署/独立 CDN 节点时 |
| **③ 独立国家域名** | `example.es`、`example.de` | ✅ 本地信任度最高（ccTLD 本身是信任信号） | 高（多套主机/证书/备案逻辑） | 重仓单一市场、需要本地支付/本地合规时 |
| **④ URL 参数** | `example.com?lang=es` | ❌ Google 明确不建议，参数常被合并或忽略 | 最低 | **不要用**，仅限内部测试 |

> **决策口诀**：起步用子目录；某个市场月询盘稳定超过总量的 30% 时，为它单独上 ccTLD 独立站（此时内容、价格、认证通常也该本地化了，正好配套）。

### 3.3 hreflang 实战

hreflang 告诉 Google「这个页面有哪些语言版本，分别给谁看」。做错的后果：Google 给德国用户展示英文页（或反之），多语言投入全部打水折。

**标准写法**（每个语言版本的 `<head>` 里都要包含**全量**的互指声明，包括指向自己的那条）：

```html
<!-- 英文页 https://example.com/en/agricultural-drone/ 的 head 中 -->
<link rel="alternate" hreflang="en"      href="https://example.com/en/agricultural-drone/" />
<link rel="alternate" hreflang="es"      href="https://example.com/es/dron-agricola/" />
<link rel="alternate" hreflang="de"      href="https://example.com/de/landwirtschaftsdrohne/" />
<link rel="alternate" hreflang="x-default" href="https://example.com/en/agricultural-drone/" />
```

**语言代码规范**：

- 纯语言：`en`、`es`、`de`、`zh`
- 语言 + 地区：`en-US`、`en-GB`、`pt-BR`、`es-MX`（当同一语言在不同市场有不同页面/价格时必须区分）
- **`x-default`**：指定「语言不匹配时的兜底页」，通常指向英文版或语言选择器页。**必填**，缺了它 Google 对未覆盖地区的处理不可控

**五个最高频的错误（评审他人代码时按此打勾）**：

| # | 错误 | 后果 |
|---|---|---|
| 1 | **缺少返回链接**（A 页声明了 B，B 页没声明 A） | Google 直接忽略整组 hreflang——**最常见，占错误的 70%** |
| 2 | `x-default` 缺失或指向错误 | 未覆盖地区的流量归零或错配 |
| 3 | hreflang 与 canonical 冲突（canonical 指向英文页，等于告诉 Google「这个西语页是重复内容」） | 西语页不被收录 |
| 4 | 用了不存在的语言代码（如 `zh-CN` 写成 `cn`，或 `uk` 当乌克兰用——`uk` 是乌克兰语，英国是 `en-GB`） | 声明无效 |
| 5 | 某些语言版本 404 或 301 走了，hreflang 还留着 | 整组信号被污染 |

**WordPress 实现**：WPML 和 Polylang Pro 都会自动输出 hreflang（含返回链接）。验证方式：上线后跑一遍 [Google 的 hreflang 检查](https://www.google.com/webmasters/tools/international)（Search Console → 国际定位报告），看有无错误项。

**Headless/自建实现**：必须写自动化测试——爬全站页面，校验「每个 hreflang URL 可访问（200）、双向互指、含 x-default」。这条规则放进 CI，人工检查一定会漏。

### 3.4 翻译工作流：三种模式的取舍

| 模式 | 成本 | 质量感知 | 适用 |
|---|---|---|---|
| 纯机器翻译（DeepL / GPT 批量） | 极低 | ⚠️ 技术文档尚可，营销文案痕迹重 | 内部验证阶段、长尾博客先机翻占位 |
| 机翻 + 母语审校 | 中 | ✅ 性价比最高 | **推荐的标准工作流**：关键页面（首页/详情页/询盘页）必须母语审校，博客可以先机翻 |
| 全人工翻译 | 高 | ✅ 最佳 | 详情页与品牌页；或客户有本地团队 |

**工程要点**：无论哪种模式，**翻译内容必须结构化存储**（WPML 的翻译队列 / Headless 的 i18n JSON 文件），绝不能用「复制一个页面手动改文字」的方式——三个月后语言版本必然不同步，hreflang 全部指向过期内容。

**审校质量红线**：产品参数、认证名称、单位换算（英寸/毫米、磅/公斤）必须逐一人工核对，机翻在这些地方最容易出现「专业级事故」（比如把 mm 翻成 inches）。

## 四、产品数据模型设计

产品数据模型是外贸站的心脏。模型设计错了，后面每个功能（筛选、多语言、多市场、询盘）都在还债。

### 4.1 B2B 产品数据的特点

先认清它和 B2C 电商数据模型的差异：

| 差异点 | B2C（Shopify 类） | B2B 外贸站 |
|---|---|---|
| 核心转化动作 | 加入购物车 | **发询盘** |
| 价格 | 明确标价 | 区间价 / 阶梯价 / FOB 报价，常需隐藏 |
| 关键字段 | 图片、价格、库存 | **MOQ、Lead time、包装装柜量、认证** |
| 变体逻辑 | 尺码颜色 | 型号系列、功率档位、定制选项（与报价强关联） |
| 内容深度 | 卖点文案 | **技术参数表、认证证书、应用案例、合规文档** |
| 受众 | 消费者 | 采购经理 + 工程师（后者看参数，前者看场景） |

### 4.2 字段清单（可直接作为开发依据）

```text
【基础标识】
- model_code        型号（唯一，URL slug 来源）
- series            所属系列（分类的上一级）
- category          产品分类（多选）
- status            生命周期：在产 / EOL / 预售

【规格参数】（建议分组，前端渲染为可折叠表格）
- params_core       核心参数（5–8 项，列表页展示）
- params_full       全量参数（详情页，分组：性能/物理/电气/环境）
- materials         材质
- dimensions        尺寸重量（单机/单箱分开）
- packing           包装：每箱数量、箱规（长宽高）、毛净重、CBM
- loading_qty       装柜量：20GP / 40HQ / 40HQ 堆叠层数   ← B2B 特有，买家必问

【商务信息】
- moq               最小起订量
- lead_time         交期（常规/旺季分开）
- price_tiers       阶梯价区间（可只存区间不存实价）
- payment_terms     支持的付款方式
- oem_odm           定制能力：OEM 起订量 / ODM 起订量 / 打样周期

【认证关联】（独立内容类型，多对多）
- certificates → [ { type: CE, region: EU, number: xxx, valid_until: 2028-01, pdf: url }, ... ]

【市场可用性】
- markets           可售市场（多选：EU / US / MENA / SEA ...）
- market_notes      每个市场的特殊说明（电压制式、认证差异）

【媒体与文档】
- gallery           图集（含场景图、细节图、对比图）
- video             视频（工厂实拍 > 精剪宣传）
- datasheet         规格书 PDF（可下载，记录下载事件）
- manual            说明书 / 安装指南

【内容】
- short_desc        一句话卖点（列表页/OG 用）
- long_desc         详情长文（分块结构化，不要一坨富文本）
- faq               产品级 FAQ（输出 FAQPage Schema）
- applications      应用场景关联

【SEO】
- focus_keyword     目标关键词
- seo_title / meta_description
- schema_overrides  结构化数据覆盖项
```

### 4.3 WordPress 实现：CPT + ACF（推荐）vs WooCommerce Catalog 模式

**方案 A：自定义文章类型（CPT）+ ACF 字段组 —— 纯询盘站首选**

```php
// register_post_type 示意（实际放插件或主题的 mu-plugin 中）
register_post_type('product', [
  'labels'   => ['name' => 'Products', 'singular_name' => 'Product'],
  'public'   => true,
  'has_archive' => true,
  'rewrite'  => ['slug' => 'products'],
  'supports' => ['title', 'editor', 'thumbnail', 'excerpt', 'revisions'],
  'menu_icon' => 'dashicons-cart',
]);

register_taxonomy('product_category', 'product', [
  'hierarchical' => true,
  'show_in_rest' => true,   // 供块编辑器 / Headless 消费
  'rewrite'      => ['slug' => 'product-category'],
]);
```

- 用 ACF 为 `product` 注册上面的字段组（`params_full` 用 Repeater + Group 做成分组参数表）
- 认证做成独立 CPT `certificate`，用 ACF 关系字段双向关联
- 关掉评论、关掉不需要的东西；**不要为了一个询盘表单安装 WooCommerce**

✅ 优点：数据干净、查询快、字段完全按业务设计、前端渲染自由
⚠️ 缺点：筛选/排序要自己做（ACF 不能直接高效过滤 repeater，核心筛选字段要用**独立字段**而非 repeater 内字段，或落库到 post_meta 并加索引）

**方案 B：WooCommerce Catalog 模式 —— 未来可能转在线交易时选**

- 关闭购物车（或用插件切换成「仅询盘」），保留 WooCommerce 的产品架构、分类、属性系统
- 属性（`pa_*`）天然支持筛选归档，参数筛选直接用属性实现
- 规格参数用「属性 + 自定义字段」混合：**可筛选的用属性，纯展示的用 ACF**

✅ 优点：筛选生态现成（FacetWP 等）、未来开在线批发只需打开购物车
⚠️ 缺点：WooCommerce 的表结构重、模板层级深、为「不卖货」承担了电商复杂度

**选择规则**：

```text
未来 24 个月内有在线交易计划？ → 方案 B（WooCommerce Catalog）
纯询盘、展示为主？           → 方案 A（CPT + ACF），更轻更快
```

### 4.4 Headless 实现：Schema 示意

```jsonc
// 产品文档结构示意（Strapi / Sanity / Payload 通用思路）
{
  "model_code": "AN-X9P",
  "slug": { "en": "an-x9-pro", "es": "an-x9-pro", "de": "an-x9-pro" },
  "series": "x9-pro",
  "params_core": { "flight_time_min": 55, "range_km": 15, "weight_g": 895 },
  "params_groups": [
    { "group": "performance", "items": [ { "label": "Max Speed", "value": "82 km/h" } ] }
  ],
  "commerce": {
    "moq": 10,
    "lead_time_days": { "standard": 25, "peak": 35 },
    "price_tiers": [ { "qty": "10-49", "note": "contact" } ],
    "loading": { "20gp": 240, "40hq": 560 }
  },
  "certificates": ["cert_ce_2026", "cert_fcc_2026"],   // 关联 ID
  "markets": ["EU", "US", "MENA"],
  "localizations": { "en": "...", "es": "...", "de": "..." }  // 与多语言层联动
}
```

Headless 方案的优势在多端复用与复杂筛选；代价是 4.2 清单里的每一个字段都要自己做后台录入体验（Schema + 组件），工期按 1.5–2 倍估。

### 4.5 一条重要的数据纪律

> **参数字段必须是结构化数据，不要塞进富文本。**

「电池容量：5000mAh」如果写在一段描述文字里，它就永远无法参与筛选、对比、Schema 输出、多语言同步和移动端表格化展示。**每个参数 = 一个字段 = 一条数据**，这是外贸站数据模型的底线。

## 五、多市场的价格与认证条件化展示

### 5.1 需求本质

同一个产品，在不同市场要展示不同的东西：

| 维度 | 欧盟 | 美国 | 中东 |
|---|---|---|---|
| 强调认证 | CE、RoHS、REACH | FCC、UL、FDA（如适用） | SASO、G-Mark |
| 电压/插头 | 220V / 欧标 | 110V / 美标 | 220V / 英标 |
| 价格基准 | EXW 青岛 + 欧线运费参考 | FOB 上海 | CFR Jebel Ali |
| 案例与联系 | 欧洲案例、欧洲代表 | 美国案例 | 本地代理 |

### 5.2 判定「用户属于哪个市场」的四种方式

| 方式 | 实现 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **按语言** | 语言版本即市场版本（`/es/` 默认展示欧盟内容） | 零额外成本，无隐私问题 | 语言 ≠ 市场（墨西哥和西班牙内容不同） | **起步默认** |
| **手动切换器** | 页头「Market: EU ▾」，选择存 cookie/localStorage | 精确、可控、合规无忧 | 依赖用户主动操作 | **必备**，与语言选择器并列 |
| **Geo-IP 自动建议** | 按 IP 推测市场，**弹提示条问用户**「切换到 US 版？」 | 转化提升明显 | 不问直接跳转体验差；IP 库要维护 | 做成「建议」而非「强制」 |
| **独立国家站** | `example.de` 完全独立 | 体验与 SEO 最优 | 成本最高 | 重仓市场才用 |

**Cloudflare 技术细节**（免费能力，很多人不知道）：套了 Cloudflare 的站，边缘会注入 `CF-IPCountry` 请求头，服务端可直接读取做 Geo 判定，**不需要买任何 MaxMind 之类的 IP 库**。配合 Workers/Pages 可以在边缘层完成市场路由。

> **红线**：绝不做「静默跳转」。德国用户打开 `.com` 被无声重定向到 `/de/`，会破坏 hreflang 逻辑、破坏用户预期，还可能被 Google 判定 cloaking。**只建议，不强制。**

### 5.3 认证条件化展示的实现

数据层已经就绪（4.2 的 `certificates` 关联 + `markets` 字段），渲染层按市场过滤即可：

```text
渲染规则：当前市场 ∈ certificate.region → 展示该证书（编号 + PDF 下载）
        当前市场 ∉ certificate.region → 不展示（避免混淆）
```

**合规注意**：证书是市场准入的**法律事实**。产品没有美国 FCC 认证，美国版页面就绝不能出现 FCC 图标——哪怕「看着更好看」。这是外贸站的法律红线，作为开发者有责任在代码层面让「认证展示」只能来自证书库的关联数据，**禁止手动硬编码认证图标进模板**。

### 5.4 价格展示策略

B2B 价格展示是一个**商务决策 + 线索过滤**问题，三种策略：

| 策略 | 做法 | 效果 | 适用 |
|---|---|---|---|
| **完全隐藏** | 「Request Quote」按钮 | 询盘量大但质量参差，比价型线索多 | 定制型产品、价格敏感不想公开 |
| **阶梯区间价** | 100–499 台：$210–190；500+：Contact us | 买家可自估成本，**留下的是真实采购意向** | 标准品、批发为主 |
| **FOB 单价参考** | 标注「FOB Shanghai, USD 195 @ 500pcs」 | 专业度信号极强，直接过滤外行 | 工业品、成熟品类 |

**我的建议**：标准品用「阶梯区间价 + 注明贸易条款与港口」。区间价既过滤了零售询盘，又给了采购经理算到岸成本的抓手——他在内部汇报时需要这个数字。

**技术实现要点**：阶梯价数据必须结构化存储（4.2 的 `price_tiers`），按市场关联不同币种与条款；展示层加 Schema.org `AggregateOffer`（如公开），并把「Request Quote」按钮事件接入 GA4（`generate_lead` 带产品参数）。

## 六、性能预算的制定方法

性能预算（Performance Budget）= 在写第一行代码之前，就书面约定「每个页面类型的资源与指标上限」。它是把「性能优化」从上线后的补救，变成开发中的**约束条件**。

### 6.1 为什么外贸站必须有性能预算

- 海外买家设备/网络分布广：大量移动端 + 中端 Android + 4G，**不能按你的 MacBook + 光纤来开发**
- 每慢 1 秒，转化率下降约 7%（行业共识数据量级）；询盘页多 1 秒 = 直接烧客户的广告费
- 性能衰减是渐进的：上线的第 3 个月，市场部往首页塞了 8MB 的轮播视频——**没有预算约束，没有人会说不**

### 6.2 按页面类型制定预算（可直接套用的模板）

| 页面类型 | LCP | 总 JS（压缩后） | 图片（首屏） | 总传输 | 备注 |
|---|---|---|---|---|---|
| 首页 | ≤ 2.0s | ≤ 150KB | ≤ 400KB | ≤ 1.2MB | Hero 图 AVIF + preload，禁自动播放大视频 |
| 产品列表页 | ≤ 2.2s | ≤ 150KB | 首屏 ≤ 300KB | ≤ 1.0MB | 懒加载 + 占位尺寸防 CLS；筛选走前端缓存 |
| 产品详情页 | ≤ 2.2s | ≤ 170KB | 首屏 ≤ 350KB | ≤ 1.2MB | 参数表格延迟渲染；schema 必出 Product |
| 博客文章页 | ≤ 2.0s | ≤ 120KB | 按需 | ≤ 0.8MB | 最轻的页面，SEO 主力 |
| **询盘页** | ≤ 1.8s | ≤ 120KB | 极少 | ≤ 0.7MB | **全站最轻**——这是收钱的页面 |

配套全局约束：

```text
□ 第三方脚本总量 ≤ 80KB（GA + reCAPTCHA + 客服插件是三大吞金兽）
□ 自托管字体 ≤ 2 个家族、≤ 5 个字重，子集化（拉丁字符集）
□ 所有图片 AVIF 优先 / WebP 兜底，详情图带 srcset
□ TTFB ≤ 600ms（页面缓存 + Cloudflare）
□ INP ≤ 200ms：询盘表单页禁阻塞脚本
```

### 6.4 超预算时的取舍原则

总会有产品经理/市场部要求加东西。给一个可辩护的优先级：


| 需求 | 裁决 |

| 「接入某在线客服气泡」 | ⚠️ 有条件放行：延迟到首次交互后加载（`requestIdleCallback`），并计入第三方脚本预算 |
| 「详情页加 3D 展示」 | ✅ 单独评估：做成按需加载的独立路由/弹层，不进首屏预算，用独立预算项管理 |

## 七、架构决策记录（ADR）：让你的决策可辩护

### 7.1 为什么要写 ADR

ADR（Architecture Decision Record）= 用一页纸记录「当时为什么这么选」。三个用处：

1. **客户沟通**：报价单里附上 ADR，客户看到的不是「我会写代码」，而是「我在替他管控风险」——这是溢价依据
2. **半年后的自己**：需求变更时（「当初为什么用子目录不做多站点？」），翻 ADR 而不是考古聊天记录
3. **作品集素材**：一篇好的 ADR 比十个截图更能证明工程判断力

### 7.2 ADR 模板 + 完整示例

```markdown
# ADR-003：多语言采用子目录架构而非多站点

- 状态：已接受
- 日期：2026-10-21
- 决策人：（你）＋ 客户方市场负责人

## 背景
客户计划首发英语 + 西语市场，12 个月内可能增加德语、阿语；
SEO 是主要获客渠道之一；客户团队无专职开发，维护靠外包年度合同。

## 备选方案
A. 子目录（example.com/es/）—— WPML 单站实现
B. 多站点（WordPress Multisite，每语言一个站点）
C. 独立 ccTLD（example.es）

## 决策
选择 A（子目录）。

## 理由
1. 权重共享：所有语言累积同一主域权重，SEO 起步期收益最大
2. 维护成本：单站单后台，产品/认证数据一处更新全语言同步；
   Multisite 意味着每语言重复维护一遍数据
3. 成本：无额外主机与域名开销，符合客户 8 万预算结构
4. 演进路径：西语市场月询盘占比 > 30% 时，再升级为独立 ccTLD（届时内容本地化也已具备）

## 取舍（我们接受了什么代价）
- ccTLD 级别的本地信任信号放弃（当前阶段非主要矛盾）
- 未来迁移到独立站时需要一次 301 映射工程（已预估 2 人日）

## 验证方式
Search Console 国际定位报告：上线 4 周后 hreflang 错误数为 0，
西语页面对西语查询的展示占比 > 60%。
```

**模板要点**：`取舍` 和 `验证方式` 两节最见功力——说明你清楚选择的代价，并且定义了「什么信号出现说明决策错了」。敢写这两节的人，在客户眼里和只写「采用最佳实践」的人是两个物种。

## 附录 C：开源 Headless CMS 选型参考

> **本附录的前提**：第二章已经论证了「80% 的询盘型外贸站应该用 WordPress」。本附录**不重复讨论该不该用 Headless**，只回答下一个问题——**当项目确实触发了 2.5 节的硬条件、必须上 Headless 时，后端该选哪一个。**

### C.1 先厘清一件事：Headless CMS 不解决外贸站的核心问题

这是选型前最容易产生的误解。所有 Headless CMS 提供的只是**「内容存储 + 数据 API + 管理后台」**，而外贸站真正费工时的部分，它们一个都不管：

| 外贸站的真实需求 | Headless CMS 是否提供 |
|---|---|
| 产品参数结构化建模（4.2 节 40+ 字段） | ⚠️ 只提供字段建模能力，模型要自己设计 |
| 多语言内容版本管理 + 翻译工作流 | ⚠️ 多数需付费插件或自建（Strapi i18n 免费但工作流弱） |
| hreflang 输出与互链校验 | ❌ 自建 |
| Schema.org Product / Organization 结构化数据 | ❌ 自建 |
| 产品多维度筛选比价 | ❌ 自建（或另接搜索服务） |
| 证书文件管理与按市场条件展示 | ❌ 自建 |
| 询盘表单 + 反垃圾 + 通知链路 | ❌ 自建（或接第三方） |
| SEO 面板（标题/描述/OG/站点地图） | ❌ 自建 |

**换句话说**：选 Headless CMS 只是选了一个「数据层」，上面第 2–8 行的工作量全部转移到你身上。这是第二章结论的技术依据——不是 Headless 不好，而是**外贸站的成本大头不在数据层**。

### C.2 第一梯队：三个主流选项

| | **Strapi** | **Payload** | **Directus** |
|---|---|---|---|
| 语言/栈 | Node.js（JS 为主，TS 支持持续改善） | **TypeScript 原生** | Node.js + 任意 SQL |
| 建模方式 | 可视化 Content-Type Builder | **代码定义**（TS 配置文件，可 review / diff / 版本化） | 数据库优先，包在已有 SQL 之上 |
| 许可证 | MIT 核心，**部分企业功能收费** | **MIT 全开放，无营收门槛** | ⚠️ **已改为源码可见，非 OSI 开源** |
| 部署形态 | 独立服务 | **可装进 Next.js `/app` 目录，单次部署** | 独立服务（Docker 最简） |
| 社区规模 | 最大（65k+ stars） | 增长最快（40k+ stars） | 中等（30k+ stars） |
| 性能 | 中等 | **最快**（同进程 Local API，无 HTTP 往返） | 中等 |
| 最适合 | 编辑团队主导、要 GUI 建模 | Next.js / TS 团队、要代码可控 | 已有 ERP/数据库、要做数据平台 |

> **三者真正的分水岭**（比 star 数重要得多）：**schema 归谁拥有、部署面有几个、许可证天花板在哪。** 这三个问题答完，答案通常就唯一了。

### C.3 两个 2026 年的关键变化（大量旧文章已过期）

**① Payload 于 2025 年 6 月被 Figma 收购**

| 维度 | 影响 |
|---|---|
| ✅ 好消息 | MIT 许可证不变、代码库继续开源、发布节奏照旧；客户名单含 Microsoft、ASICS、Blue Origin |
| ⚠️ 变化 | **Payload Cloud 停止接受新用户**，只能用自托管（Vercel / Docker / Cloudflare Workers） |
| ⚠️ 隐忧 | 路线图现在跟随 Figma 的「design-to-deployment」战略，不再是纯独立社区项目。**MIT 是兜底**——最坏情况你可以 fork |
| 📌 版本 | Payload 4.0 于 2026 年 4 月进 beta，后台按 Figma 设计系统重做 |

**② Directus 不再是标准开源许可证**

- 2026 年 4 月 v12 起改用 **MSCL（Monospace Sustainable Core License）**，属「源码可见」而非 OSI 认证开源
- 免费条件：年营收 **< 500 万美元** 且 员工 **< 50 人**；超过任一门槛需购买商业许可
- **对服务商的实际影响**：客户若是中大型企业，报方案前必须先核许可证，否则交付即违规

### C.4 其他候选清单

| 项目 | 定位 | 评价 |
|---|---|---|
| **Wagtail** | Django + BSD，内容型站点强 | ✅ **被严重低估**。`wagtail-localize` 做多语言、SEO 完全可控，内容量大的外贸站很合适；会 Python 的话性价比最高 |
| **Keystone 6** | TS + Prisma，代码优先 | ✅ 小众但干净，适合小型项目 |
| **TinaCMS / Decap CMS** | Git-based，内容存 repo，无数据库 | ✅ 静态站 + 小团队很舒服；内容量大后构建变慢 |
| **Ghost** | 开源，博客/邮件订阅为核心 | ⚠️ 只适合做博客，有 Content API 但不是通用 CMS |
| **WordPress + WPGraphQL** | 把 WP 变成 headless 后端 | ⚠️ 能用，但如 2.4 节所述——**两头不占** |
| **Sanity** | ❌ **不是开源** | Studio 开源，内容后端是 SaaS，按 API 调用计费 |
| **Medusa / Vendure** | Headless 电商（含购物车/订单） | ✅ 若要做 B2B 在线批发而非纯询盘，比 CMS 更对症 |

### C.5 决策表（按项目实际情况对号入座）

| 你的情况 | 选择 | 注意事项 |
|---|---|---|
| Next.js + TypeScript 团队，想一个 repo 一次部署 | **Payload** | 接受 Figma 路线风险；CI 里锁版本 |
| 编辑是非技术人员，要可视化建模、生态要大 | **Strapi** | SSO、细粒度权限、审计日志、审核流均为**付费企业版** |
| 客户已有 ERP/数据库，网站只是给它套 API 和后台 | **Directus** | **先确认客户规模与营收**，跨 MSCL 门槛要买许可 |
| 会 Python，内容量大、多语言要求高 | **Wagtail** | 中文资料少，但技术债最低 |
| 小站 + 博客，想零运维 | **TinaCMS / Decap** | 内容进 Git，纯静态输出 |
| 要做在线批发（下单/阶梯价/账期） | **Medusa / Vendure** | 这是电商引擎，不是 CMS，别混用 |

### C.6 自托管的真实持有成本（最容易被漏算）

「自托管 = 免费」是错觉。真实成本如下，报方案时应计入 TCO：

| 成本项 | 量级 | 说明 |
|---|---|---|
| 服务器 | $12–40 / 月 | Node 进程常驻内存 200–400MB 起，2C4G 是底线 |
| 数据库/备份 | $0–20 / 月 | 自建 Postgres 需另做备份与恢复演练 |
| 依赖升级 | **20–60 小时 / 年** | 安全补丁 + 大版本迁移 |
| 大版本回归测试 | **16–40 小时 / 次** | Strapi 大版本升级历来是持有成本最痛的一环 |
| 前端独立部署 | 1 套 CI/CD | 前端、后端两处故障面 |
| 交接成本 | 高 | 两年后接手者需同时懂 Headless CMS + 自建 i18n + 前端框架 |

> 按 100 元/小时的保守工时费率折算，**一个 3 年期 Headless 项目仅运维侧就比 WordPress 多出 1–3 万元**——这部分在第二章 2.2 节的 TCO 表里已经体现。

### C.7 两个不要踩的坑

1. **别拿 GitHub stars 当选型依据。** Strapi、Payload、Directus 都是第一梯队，star 数差异反映的是营销力度和上线时间，不是适配度。真正要看的是 C.2 末尾那三个问题。
2. **别把「用了 Headless CMS」当成技术先进性的证明。** 客户买的是询盘量和维护保障，不是架构时髦度。你作为开发者，能讲清楚「这个项目为什么**不需要** Headless」——这种判断力比会用它更值钱，也更容易拿到长期维护合同。

### C.8 一页版结论

```text
必须上 Headless（2.5 节触发条件成立）
 ├─ 要在线批发交易？ ────────── 是 → Medusa / Vendure
 └─ 否（内容型 + API）
      ├─ 团队 TS/Next.js，能接受自托管 ──→ Payload（首选）
      ├─ 编辑主导，要 GUI 与生态 ──────→ Strapi（核企业版功能）
      ├─ 已有数据库/ERP，做数据平台 ────→ Directus（先核 MSCL 许可）
      ├─ 会 Python，内容量大 ─────────→ Wagtail（性价比最高）
      └─ 极小站 + 博客，零运维 ────────→ TinaCMS / Decap

任何分支都必须额外确认：
  ① 多语言工作流由谁实现（CMS 自带 or 自建）
  ② hreflang / Schema / sitemap 的产出方式
  ③ 客户是否签年度维护合同（否则上线即失养）
```

> **核查提示**：Headless CMS 领域许可证与商业化状态变动频繁（本附录已记录 Directus 与 Payload 两次变更）。**报方案前务必到官方仓库核对 LICENSE 与 pricing 页当次状态**，不要引用二手文章。
