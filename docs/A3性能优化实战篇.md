# 外贸站开发系列 · A3 性能优化实战篇

> **系列定位**：A1 建立认知、A2 定下架构与预算，本篇是执行层——**预算落不了地时，具体该动哪一刀、能拿回多少毫秒、怎么证明不是幻觉**。
> **适合读者**：手上有一个 LCP 不达标的站（自己的、客户的、或样板站），需要在两周内把它做到能过 Core Web Vitals，并且要向非技术决策者解释的人。
> **读完之后你应该能**：拆开 LCP 的四段、判断瓶颈在哪一段、按收益排序动手、配好 WordPress 三层缓存、并把整个过程写成一份能放进作品集的对比报告。

> **口径声明（先读这一段）**
> 本篇案例是一个**可复现的样板站**：WordPress 6.8 + 典型外贸主题（首页带轮播 Hero）+ 8 个常见插件，部署在 2C4G 的普通 VPS 上。所有数字都是**同一台机器、同一个 Lighthouse 版本、同一套网络与 CPU 节流设置下跑三次取中位**得到的，测量脚本在附录 B，你可以拿自己的站复现同一组口径。
> 为什么强调这个：性能数字一旦脱离口径就毫无意义。**「我的站 1.2 秒」是一句无法验证的话；「Lighthouse 12 移动模拟 / Slow 4G / 4× CPU / 冷缓存 / 三次中位 = 1.2 秒」才是一句可验证的话。** 本文所有对比都遵守后者。
> 另：本仓库 B 系列交付引擎产出的站走的是另一条路（静态生成、零 JS 框架），第 3、7 节对它意义有限（构建期已解决 / 没有 PHP 层），第 4、5 节仍然是主战场——差异我在每节末尾标注了。

## 一、先统口径：4.2 秒有十种意思

客户说「我的站打开要 4 秒」，这句话里至少藏着四个互相矛盾的可能。优化之前先把口径钉死，否则你会在「改完怎么没变快」上浪费两周。

### 1.1 四个必须分开的数字

| 数字 | 是什么 | 谁在看 | 典型偏差 |
|---|---|---|---|
| **实验室 LCP**（Lighthouse / WebPageTest） | 固定设备 + 固定网络 + 冷缓存的单次结果 | 开发者、CI 门禁 | 比现场数据**好 20–40%**（真实网络有丢包、有并发、有老设备） |
| **现场 LCP p75**（CrUX / GA4 / Search Console） | 真实用户 75 分位的 28 天滚动值 | 客户、老板、Google 排名 | 慢于实验室，且**改完要等 28 天才动** |
| **单页 vs 全集** | 首页 4.2s，产品页可能 6.8s | 客户只会看首页 | 用首页分数代表全站是常见的美化 |
| **冷缓存 vs 热缓存** | 首次访问 vs 二次访问（CDN/浏览器命中） | 买家第一次来一定是冷缓存 | 热缓存能好看 3 倍，毫无参考价值 |

**本文所有数字都是第一种：Lighthouse 12 移动模拟、Slow 4G、4× CPU 节流、冷缓存、三次中位。** 这个口径最苛刻，也最能反映「买家在海外用中端安卓第一次打开你的站」。

### 1.2 固定测量协议（照抄即可）

```text
□ 工具与版本：Lighthouse 12.x（写进报告，版本变了数字不可比）
□ 形态：移动模拟（不是桌面，不是「我自己手机」）
□ 网络：Slow 4G（1.6Mbps 下行 / 750Kbps 上行 / 150ms RTT）
□ CPU：4× 节流（模拟中端安卓）
□ 缓存：每次清空（Lighthouse 默认；WebPageTest 要显式勾选）
□ 次数：3 次取中位（单次结果抖动可达 ±15%）
□ 页面：首页 + 列表页 + 详情页 + 询盘页，四类都测
□ 记录：分数、LCP、CLS、TBT、传输字节、请求数、LCP 元素选择器
```

命令行（Windows 的 `CHROME_PATH` 要用反斜杠绝对路径，这是实操坑）：

```bash
export CHROME_PATH="C:\Program Files\Google\Chrome\Application\chrome.exe"
for i in 1 2 3; do
  npx lighthouse@12 "https://staging.example.com/" \
    --only-categories=performance \
    --output=json --output-path="./lh-$i.json" \
    --chrome-flags="--headless" --quiet
done
```

### 1.3 一条纪律

> **不同口径的数字永远不许放在同一张表里比较。**
> 「昨天 Lighthouse 4.2s，今天 PageSpeed 线上 2.1s，所以我们优化了 2 秒」——这句话一旦说出口，你的专业度就归零了。PageSpeed Insights 顶部是**现场数据**，底部是**实验室数据**，两个数天然不同，不是「优化成果」。

## 二、案例与基线：4.2 秒到底花在哪

### 2.1 样板站构成

| 项 | 内容 | 备注 |
|---|---|---|
| CMS | WordPress 6.8 | 外贸站最常见的起点 |
| 主题 | 商业主题，首页含 3 图轮播 + 图标网格 | 主题自带 jQuery 与 3 个 CSS 文件 |
| 插件 | 表单、SEO、多语言、图片优化、缓存、客服、分析、安全 | 8 个，外贸站标配组合 |
| 服务器 | 2C4G VPS，Nginx + PHP-FPM 8.3 + MySQL 8 | 无机房级缓存，无 CDN |
| 内容 | 首页 1 轮播 + 6 产品 + 3 文章 | 数据量小，问题全在资源 |

### 2.2 基线数字

| 指标 | 基线 | 判读 |
|---|---|---|
| **Performance 分** | **38** | 红色 |
| LCP | **4.20s** | 目标 ≤2.0s（A2 6.2 首页预算） |
| FCP | 2.40s | 首屏第一像素都很晚 → 大概率渲染阻塞 |
| TBT | 480ms | JS 主线程严重堵塞 |
| CLS | 0.18 | 图片无尺寸 + 字体闪动 |
| TTFB | 620ms | 未缓存，PHP 每次全量执行 |
| 传输总量 | 4.82MB | 预算 1.2MB，超 4 倍 |
| 请求数 | 96 | 主题 + 6 插件 + 字体 + 图标库 |

### 2.3 LCP 四段拆解（全篇的纲）

LCP 不是一个数字，是**四段相加**。不拆开就动手，等于闭眼拧螺丝。

```text
LCP = TTFB + 资源加载延迟 + 资源加载时长 + 元素渲染延迟
      ↑        ↑              ↑              ↑
   服务器    HTML 解析完到   真正开始下载    下载完到画出来
   响应完    发现这张图     到下载完        （含 JS 执行、样式计算）
```

用附录 B 的脚本量到的基线：

| 段 | 数值 | 占比 | 含义 |
|---|---|---|---|
| TTFB | 620ms | 15% | 无页面缓存，PHP 全量渲染 |
| **资源加载延迟** | **1480ms** | **35%** | Hero 图由轮播 JS 在 DOM ready 后注入 → **浏览器发现它太晚** |
| **资源加载时长** | **1720ms** | **41%** | 1.92MB 的 JPEG，Slow 4G 上就是这个速度 |
| 元素渲染延迟 | 380ms | 9% | 渲染阻塞 CSS + 字体 |
| **合计** | **4200ms** | 100% | — |

**这张表是本篇最重要的一页。** 它直接告诉你：

- 只有 15% 是「服务器慢」。**买更贵的服务器最多拿回 0.6 秒，而且很贵。**
- 76% 集中在「发现晚 + 文件大」，这两件事**不需要花一分钱**。
- 渲染延迟里有一部分是「等 CSS 解析」，属于关键路径治理（这一段的收益上限不高，真正的大头在下面两段）。

> **方法论**：任何 LCP 优化的第一件事，永远是跑这个拆解，然后把 76% 的两段切成待办。不要先去看插件、不要先换主题、不要先买 CDN。

### 2.4 诊断结论（写成一句话，后面所有动作都服务它）

> **这个站的 Hero 图既「被发现得太晚」（JS 轮播注入），又「太重」（1.92MB JPEG），还把首屏渲染堵在 382KB 同步 CSS 和 612KB 同步 JS 后面。**

三件事，对应第 3、4、6 节。

## 三、第一刀：TTFB 与渲染阻塞

先做这一刀，不是因为它收益最大，而是因为它**便宜且无副作用**，且能立刻让 FCP 好看，给后面争取时间。

### 3.1 页面缓存：先把 PHP 从链路里拿掉

外贸站的首页、产品页、文章页对每个访客都是**同一份 HTML**，没有任何理由每次执行 PHP。开启页面缓存后：

| | 基线 | 页面缓存后 |
|---|---|---|
| TTFB | 620ms | **180ms** |
| 每秒可承载请求 | ~40 | ~600+ |

选择（按项目约束）：

| 方案 | 适用 | 注意 |
|---|---|---|
| 插件（WP Rocket / LiteSpeed Cache / FlyingPress） | 90% 的外贸站 | 先确认与主机栈匹配（LiteSpeed 主机用 LSCache 才有效果） |
| 主机级（RunCloud / GridPane / Cloudways Varnish） | 有运维能力 | 与插件容易打架，**只留一层** |
| 静态导出 | 内容变动少、追求极致 | 换 WordPress 的编辑体验 |

**必须排除缓存的页面**（下一节 7.2 会展开，这是外贸站最容易翻车的地方）：

```text
□ /inquiry/、/contact/ 等带 nonce 或 CSRF token 的表单页
□ WooCommerce 购物车 / 结账 / 我的账户
□ 已登录用户（wp-admin 与前台登录态）
□ 带预览参数、带 UTM 且会回显的落地页
```

### 3.2 渲染阻塞 CSS：382KB 里有 340KB 不需要首屏

基线加载 6 个 CSS 共 382KB，全部是同步 `<link>`。首屏只需要容器宽度 1280 以内、比折叠线以上用到的那部分。

做法（三种，按工程量排序）：

| 做法 | 说明 | 适用 |
|---|---|---|
| 插件提取关键 CSS | 自动生成 + 内联，其余异步 | 不想碰代码 |
| 手写关键 CSS | 首屏骨架 30–50KB 内联，其余 `media="print"` 交换 | 可控、可审计 |
| 只保留必要文件 | 停用不用的插件 CSS（图标库、滑块库） | 收益最大、最常被忽略 |

```html
<!-- 非关键 CSS 异步加载（必须带 noscript 兜底，否则 JS 关闭时全裸） -->
<link rel="stylesheet" href="/css/app.css" media="print" onload="this.media='all'">
<noscript><link rel="stylesheet" href="/css/app.css"></noscript>
```

案例结果：CSS 382KB → **首屏内联 38KB + 异步 208KB**，FCP 2.40s → 1.60s。

> **别把「移除未使用 CSS」当银弹**：外贸站主题大量使用动态类名（`elementor-*`、`wp-block-*`），暴力 purge 会在某个页面白屏。要么按模板白名单，要么只砍「整份文件不用」。

### 3.3 JS 收敛：480ms 的 TBT 来自哪里

基线 612KB JS：jQuery 87KB + 滑块 120KB + 表单校验 95KB + 客服 210KB + 其它。三件事按顺序做：

1. **给所有脚本加 `defer`**（除必须同步的极少例外）。WordPress 6.3+ 原生支持：

```php
add_filter('wp_script_attributes', function ($attrs) {
    if (isset($attrs['id']) && str_contains($attrs['id'], 'jquery-core')) {
        $attrs['defer'] = 'defer';
    }
    return $attrs;
});
```

2. **按页条件加载**（第 6.2 节给完整代码）——客服插件只在有询盘表单的页加载，能省 210KB。
3. **第三方延迟到交互后**：客服气泡、在线聊天、回访弹窗，全部 `requestIdleCallback` 或首次滚动/点击后再注入。

结果：TBT 480ms → 300ms，JS 612KB → 340KB。

### 3.4 阶段收益

| 指标 | 基线 | 第一刀后 | 归因 |
|---|---|---|---|
| TTFB | 620ms | 180ms | 页面缓存 |
| FCP | 2.40s | 1.60s | 关键 CSS |
| LCP | 4.20s | **3.70s** | render delay 380→300，TTFB −440 |
| TBT | 480ms | 300ms | defer + 条件加载 |

**LCP 只动了 0.5 秒**——这很正常，也很说明问题：真正的 76% 在图片，还没动。

> **本仓库引擎路线**：静态生成 + 零 JS 框架，这一刀在构建期就完成了（HTML 直出、CSS 单文件内联、无 jQuery），TTFB 由主机决定，不需要 WP 三层缓存。**这不是「引擎更强」，是「约束不同」**：静态站换掉了 CMS 的编辑体验。

## 四、图片管线：LCP 的主战场

基线里 76% 的 LCP 时间在这一节被解决。四个动作，按顺序：**算尺寸 → 换格式 → 写对 srcset → 修发现时机**。

### 4.1 先算清楚「这张图到底该多大」

外贸站最常见的错误：上传 4000×2667 的原片，主题缩到 1600 宽显示——**浏览器下载的是原片**。

| 场景 | CSS 宽度 | DPR | 需要的最宽图 |
|---|---|---|---|
| 移动（iPhone 14 / 390pt） | 390px | 2 | **780px** |
| 移动（中端安卓） | 360–412px | 1.5–3 | 540–1236px |
| 平板 | 768px | 2 | 1536px |
| 桌面 | 1280px 容器 | 1 | 1280px |
| 桌面 Retina | 1280px | 2 | 2560px（**不值得，用 1440 就够**） |

**外贸站的现实取舍**：买家 60–80% 来自移动端，DPR 2 为主。所以图档给 **480 / 768 / 1024 / 1440 / 1920** 五档就够，2400 以上只在桌面 Retina 有意义，收益小于成本——**别为了「清晰」把 LCP 卖掉**。

### 4.2 格式：同一张 Hero 的三种编码实测

源图 2400×1600，内容为真实产品照（非纯色）：

| 格式与规格 | 体积 | 相对 JPEG | 视觉 |
|---|---|---|---|
| JPEG q82 2400w | **1.92MB** | 1× | 基线 |
| JPEG q80 1440w | 620KB | −68% | 与基线肉眼无差 |
| WebP q75 1440w | 178KB | **−91%** | 无差 |
| **AVIF q55 1440w** | **96KB** | **−95%** | 无差 |
| **AVIF q55 768w** | **34KB** | **−98%** | 移动端无差 |
| AVIF q55 480w | 18KB | −99% | 小屏无差 |

**移动端实际会下载哪一档？** 390pt × DPR2 = 780 设备像素 → 命中 768w 档 → **34KB**。相比基线的 1.92MB，**56 倍**。

编码命令见附录 C。两条经验：

- `avifenc -q 55` 的视觉质量约等于 JPEG q80，**不要用 q80 编 AVIF**（体积会翻倍且看不出差别）
- AVIF 编码慢 10–20 倍，在构建期做，别在请求时做；解码在低端安卓上比 JPEG 慢 30–60ms，**但省下的 1.8MB 传输远大于这个代价**

兼容写法（覆盖到 ≈100%）：

```html
<picture>
  <source type="image/avif" srcset="/img/hero-480.avif 480w, /img/hero-768.avif 768w, /img/hero-1024.avif 1024w, /img/hero-1440.avif 1440w" sizes="(max-width: 900px) 100vw, 1280px">
  <source type="image/webp" srcset="/img/hero-480.webp 480w, /img/hero-768.webp 768w, /img/hero-1024.webp 1024w, /img/hero-1440.webp 1440w" sizes="(max-width: 900px) 100vw, 1280px">
  <img src="/img/hero-1024.jpg" srcset="/img/hero-480.jpg 480w, /img/hero-768.jpg 768w, /img/hero-1024.jpg 1024w, /img/hero-1440.jpg 1440w"
       sizes="(max-width: 900px) 100vw, 1280px" width="1440" height="960"
       alt="..." fetchpriority="high" decoding="async">
</picture>
```

### 4.3 srcset / sizes 的三个致命写法

| 错法 | 后果 | 正确 |
|---|---|---|
| 只给 `srcset` 不给 `sizes` | 浏览器默认按 `100vw` 算 → 移动端也挑大图 | 显式写 `sizes`，并保证与 CSS 断点一致 |
| `sizes="100vw"` 但容器只有 600px | 永远多下一档，白花钱 | `sizes="(max-width: 900px) 100vw, 600px"` |
| 缺 `width` / `height` | CLS 直接爆（图片撑开时重排） | 写死宽高比，或用 CSS `aspect-ratio` |

> **自查一行命令**：`document.querySelectorAll('img:not([width])').length` —— 首页返回值不是 0，CLS 就别指望 0.02。

### 4.4 preload 的优先级陷阱（本篇最容易踩的坑）

这一段是「优化做了一半反而更慢」的高发区。四个坑，全部在案例里真实出现过或差点出现：

#### 坑 1：把 LCP 图放在 JS 轮播里

基线的根因。轮播插件在 `DOMContentLoaded` 后注入 `<img>`，浏览器**在 1480ms 才第一次看到这张图**，前面 1.5 秒它只是在执行别的 JS。

两种修法：

- **正解**：首屏第一帧用静态 `<img>` 直出，轮播 JS 只负责「切换」，不负责「创建第一张」
- 次解：保留轮播，但用 `preload` 提前声明这张图（坑 2 就开始生效了）

#### 坑 2：preload 与 `<img>` 的 srcset 不一致 → 下载两次

```html
<!-- 错：preload 固定 1440 档，img 却在移动端挑 768 档 -->
<link rel="preload" as="image" href="/img/hero-1440.avif" type="image/avif">
<img srcset="/img/hero-480.avif 480w, /img/hero-768.avif 768w, ..." sizes="100vw">
```

现象：Network 面板里 `hero-1440.avif` 和 `hero-768.avif` **都下载了**，白花 96KB 带宽，还把 LCP 挤后 200–400ms。因为 preload 的 URL 与实际选择不匹配时，浏览器不会复用缓存条目。

```html
<!-- 对：用 imagesrcset / imagesizes，让 preload 走同一套选择算法 -->
<link rel="preload" as="image" type="image/avif"
      imagesrcset="/img/hero-480.avif 480w, /img/hero-768.avif 768w, /img/hero-1024.avif 1024w, /img/hero-1440.avif 1440w"
      imagesizes="(max-width: 900px) 100vw, 1280px"
      fetchpriority="high">
```

三个细节必须同时对：

| 细节 | 为什么 |
|---|---|
| `type` 与 `<source type>` 一致 | MIME 不匹配时 preload 被丢弃，等于没写 |
| `imagesrcset` 与 `img` 的 `srcset` 逐档一致 | 少一档就可能选不中，触发二次下载 |
| `fetchpriority="high"` 只给这一张 | 给两张以上等于没给，还会拉低真正的 LCP |

#### 坑 3：给非 LCP 图 preload

案例里第一版「优化」给首屏 3 张图都加了 preload，结果 **LCP 从 3.7s 变成 4.0s**——三张图抢同一个连接池，真正的 LCP 图排在后面。

> **规则：一页只 preload 一张图，就是 LCP 元素那一张。** 用附录 B 的脚本先确认它是谁（可能是标题文字而不是图）。

#### 坑 4：给首屏 LCP 图加 `loading="lazy"`

主题的「图片懒加载」功能会无差别加 `lazy`。首屏图一旦 `lazy`，浏览器会等布局完成才发起请求，**直接加 800–1500ms**。

```html
<!-- 首屏 LCP 图：绝不 lazy，反而要抢 -->
<img ... fetchpriority="high" decoding="async">
<!-- 折叠线以下：lazy 才成立 -->
<img ... loading="lazy" decoding="async">
```

**修完这一节，LCP 从 3.70s → 2.50s（资源加载时长 1720→560），再静态化 + preload 后 → 1.70s（资源加载延迟 1480→700）。**

### 4.5 WordPress 里的落点

| 要做的事 | 落点 | 注意 |
|---|---|---|
| 阻止主题把首屏图变 lazy | 主题 filter / 子主题模板 | 常见钩子 `wp_get_attachment_image_attributes`，或在模板里直接写 `<picture>` |
| 输出 srcset | WP 默认已生成（`add_image_size` 补档位） | 默认只生成 4 档，补 480/768/1024/1440 |
| preload LCP 图 | `wp_head` 里按模板条件输出 | **只在首页/指定页输出**，全站输出等于自伤 |
| 换 AVIF | 插件（Imagify / ShortPixel / 主题自带）或构建期预生成 | 插件在**请求时**转码会让 TTFB 抖动，优先构建期 |

```php
// 只在首页 preload Hero，且带 imagesrcset（与模板里的 picture 逐档一致）
add_action('wp_head', function () {
    if (!is_front_page()) return;
    $base = get_template_directory_uri() . '/img/hero';
    printf(
        '<link rel="preload" as="image" type="image/avif" fetchpriority="high" imagesizes="(max-width: 900px) 100vw, 1280px" imagesrcset="%s">',
        esc_attr(implode(', ', [
            "$base-480.avif 480w", "$base-768.avif 768w",
            "$base-1024.avif 1024w", "$base-1440.avif 1440w",
        ]))
    );
}, 1);
```

## 五、字体加载：别让它拖住第一屏

字体本身很少是 LCP 元素，但它做两件坏事：**阻塞文字渲染**（LCP 是文字时直接受害）和**引发布局位移**（CLS）。

### 5.1 三种策略的取舍

| 策略 | 首屏 | CLS 风险 | 适用 |
|---|---|---|---|
| 系统字体栈 | 最快（零请求） | 无 | 追求极致性能、品牌要求不高 |
| 自托管子集 woff2 + `swap` | 快（20–60KB） | 中（需回退匹配） | **外贸站默认答案** |
| Google Fonts 外链 | 慢 200–500ms（多一次 DNS+TLS，且常被墙/慢） | 中 | 不建议；国内访问尤其糟 |

### 5.2 `font-display` 的三个值，选错了就是 CLS

```css
@font-face {
  font-family: 'Inter';
  src: url('/fonts/inter-400-subset.woff2') format('woff2');
  font-weight: 400;
  font-display: swap;      /* 先画兜底字体，字体到了再换 —— CLS 来源 */
}
```

| 值 | 行为 | 结果 |
|---|---|---|
| `block` | 最多 3s 隐形（FOIT） | 文字延迟出现，LCP 直接受害 |
| `swap` | 立即用兜底字体，到达后切换 | 文字最快可见，但**有 CLS**（兜底字体宽度不同） |
| `optional` | 3s 内到就用，不到就本次不换 | CLS ≈ 0，但弱网用户看不到品牌字体 |

外贸站推荐 **`swap` + 回退字体匹配**（5.4），而不是退回 `optional`——品牌字体对 B 端信任感有实际作用。

### 5.3 preload 字体：只 preload 一个，且必须带 crossorigin

```html
<!-- 只 preload 首屏 H1/正文实际使用的那个字重 -->
<link rel="preload" href="/fonts/inter-600-subset.woff2" as="font" type="font/woff2" crossorigin>
```

两个坑：

- **漏 `crossorigin`**：字体请求是 CORS 模式，即使同源也会因为 preload 模式不匹配而**下载两次**（和 4.4 坑 2 同理）
- **preload 整个家族**：6 个 woff2 全 preload，等于把字体塞进关键路径的头部，FCP 反而变差

### 5.4 用回退字体匹配把 CLS 消掉

原理：给兜底字体做「度量校正」，让它在切换前后占位几乎一致。Chrome 支持 `size-adjust / ascent-override / descent-override / line-gap-override`：

```css
@font-face {
  font-family: 'InterFallback';
  src: local('Arial');
  size-adjust: 105.2%;        /* 这三个数用工具算，别手猜 */
  ascent-override: 90%;
  descent-override: 22.5%;
  line-gap-override: 0%;
}
:root { --font-body: 'Inter', 'InterFallback', Arial, sans-serif; }
```

这三个参数的计算工具（Next.js 的 `next/font` 自动生成同类值，WordPress 侧可用在线 fallback 生成器）——**案例里靠这一步把 CLS 从 0.18 压到 0.02**。

### 5.5 子集化：拉丁字符集只有 20KB

```bash
# 只保留拉丁 + 常用标点 + 数字符号（外贸站英文站的标准字符集）
pyftsubset Inter-Regular.woff2 \
  --unicodes="U+0000-00FF,U+0131,U+0152-0153,U+02BB-02BC,U+2000-206F,U+2074,U+20AC,U+2122" \
  --flavor=woff2 --layout-features="kern,liga" \
  --output-file=inter-400-subset.woff2
```

结果：**字体 6 个文件 340KB → 2 个文件 46KB**。

中文站提醒：中文字体不要整包自托管（3–8MB），要么用系统字体栈（`PingFang SC / Microsoft YaHei`），要么做「按常用 3500 字 + 分片」的方案——这是另一个话题，别在英文站上花时间。

### 5.6 阶段收益

| 指标 | 前 | 后 | 归因 |
|---|---|---|---|
| 字体请求 | 6 | 2 | 子集化 + 只留两档 |
| 字体传输 | 340KB | 46KB | 子集化 |
| CLS | 0.18 | **0.02** | 回退匹配 + 图片宽高 |
| LCP | 1.70s | 1.69s | 基本不变（本来就不是瓶颈） |

> **诚实结论**：字体优化的主要收益是 **CLS 和 FCP**，不是 LCP。别在汇报里把它写成 LCP 功臣。

## 六、CSS/JS 关键路径与第三方脚本

### 6.1 关键 CSS 的工程化边界

第 3.2 已经提过做法。补三条纪律：

```text
□ 关键 CSS 内联后，HTML 别超过 100KB（压缩后）；超了就是「把 CSS 搬进 HTML」而已
□ 内联部分必须与异步主样式「无冲突覆盖」——顺序错了会有首屏闪烁
□ 每次主题改版重跑一次提取器，别一次做完永远不管（这是最常见的回退源）
```

### 6.2 按页条件加载（外贸站性价比最高的 20 行代码）

```php
add_action('wp_enqueue_scripts', function () {
    // 客服、回访弹窗：只在有询盘表单的页面加载
    $form_pages = ['page-inquiry.php', 'page-contact.php'];
    if (!is_page_template($form_pages) && !is_singular('product')) {
        wp_dequeue_script('crisp-chat');
        wp_dequeue_style('crisp-chat');
    }
    // reCAPTCHA 只在表单页
    if (is_page_template($form_pages)) {
        wp_enqueue_script('recaptcha', 'https://www.google.com/recaptcha/api.js', [], null, ['strategy' => 'defer']);
    }
}, 100);
```

案例：首页 JS 612KB → **176KB**，第三方脚本从关键路径彻底移出 410KB。

### 6.3 第三方脚本加载时机矩阵

| 脚本 | 何时加载 | 方式 | 不这样做的代价 |
|---|---|---|---|
| GA4 / GTM | 交互后或 `idle` | `requestIdleCallback` 注入 | 45KB + 主线程 60ms |
| reCAPTCHA | 表单页 + 表单进入视口 | `IntersectionObserver` | 190KB（v3 更大） |
| 在线客服 | 首次滚动 30% 或 8s 后 | 延迟注入 | 210–320KB + 长任务 |
| 回访弹窗 | 离开意图 / 30s 后 | 延迟 | 干扰 INP |
| 社交嵌入（IG/YouTube） | 点击封面后替换 iframe | facade 模式 | 单个 iframe 可达 1MB+ |

```js
// 客服类脚本的统一延迟入口
const loadChat = () => {
  if (window.__chatLoaded) return;
  window.__chatLoaded = true;
  const s = document.createElement('script');
  s.src = '/js/chat-widget.js'; s.defer = true;
  document.body.appendChild(s);
};
addEventListener('scroll', () => {
  if (scrollY > document.body.scrollHeight * 0.3) loadChat();
}, { passive: true, once: true });
setTimeout(loadChat, 8000);
```

### 6.4 INP：比 LCP 更容易被忽视

LCP 是一次性的，INP 是**每一次交互**。外贸站的三个高频交互：语言切换、产品筛选、表单提交。

```text
□ 事件处理器自己别超过 50ms（超了拆成 rAF / setTimeout 分片）
□ scroll / touchstart 一律 passive
□ 表单校验别在每次 input 上跑正则全表——防抖 150ms
□ 提交按钮立即给「提交中」状态，别等 fetch 回来才变（用户感知的 INP 会好很多）
```

### 6.5 阶段收益

| 指标 | 前 | 后 |
|---|---|---|
| TBT | 300ms | **110ms** |
| JS 传输 | 340KB | 176KB |
| 第三方关键路径 | 410KB | 0 |

## 七、WordPress 缓存体系：三层各管什么

这一节是外贸站**最容易配错、也最容易在客户面前翻车**的地方。三层不是「越多越快」，是**各管一段链路，配错会互相抵消**。

### 7.1 三层职责表

| 层 | 缓存什么 | 命中后省掉什么 | 失效条件 | 常见误配 |
|---|---|---|---|---|
| **页面缓存**（WP Rocket / LSCache / Varnish） | 整页 HTML | PHP + MySQL 全部 | 发布内容、改菜单、改插件设置、清缓存 | 缓存了表单页 / 登录页 |
| **对象缓存**（Redis / Memcached） | 查询结果、transient、选项 | 重复 SQL | 数据变更时按 key 失效 | 以为它能救首屏（命中页面缓存时根本不执行 PHP） |
| **CDN**（Cloudflare 等） | 静态资源 + 可选 HTML | 跨地域 RTT、源站带宽 | purge / TTL / 规则 | HTML 缓存与页面缓存 purge 不同步 → 客户看到旧价 |

### 7.2 页面缓存 + 询盘表单：外贸站第一号真坑

**症状**：开了页面缓存后，询盘表单提交全部 403，或者客户收到「链接已过期」。

**原因**：WordPress 的 `wp_nonce` 有时效（默认 12–24h），且与用户会话绑定。页面被缓存后，**所有访客拿到的都是同一个（或过期的）nonce** → 校验必然失败。

三种解法，按推荐顺序：

| 解法 | 做法 | 代价 |
|---|---|---|
| **该页不进缓存**（推荐） | 模板里 `define('DONOTCACHEPAGE', true);` 或插件排除规则 | 少一个页面的缓存收益，**完全可接受** |
| nonce 生命周期 > 缓存 TTL | nonce 有效期设 48h，页面缓存 TTL 12h | 仍有窗口期，且降低重放保护 |
| 换成无状态 CSRF | HMAC 签名（含时间戳）+ 蜜罐字段 | 要改表单逻辑，但最稳，且可以放心缓存 |

```php
// 询盘页模板顶部：明确告诉缓存层「别碰这一页」
if (!defined('DONOTCACHEPAGE')) define('DONOTCACHEPAGE', true);
```

**验收标准（必须做）**：开缓存后，用**未登录的隐身窗口**提交一次，看是否 200 + 入库；再等 13 小时重复一次。两次都过才算配好。

### 7.3 对象缓存什么时候值得

| 判断项 | 阈值 | 说明 |
|---|---|---|
| 单请求 SQL 数 | > 60 条 | 用 Query Monitor 看 |
| 登录用户 / 后台操作多 | 是 | 页面缓存对登录态无效，对象缓存才起效 |
| 有 WooCommerce 或复杂筛选 | 是 | 购物车、库存查询走 DB |
| 纯展示站 + 页面缓存命中率 > 90% | **不必上** | 命中时 PHP 都不执行，Redis 纯摆设 |

> 案例里上了 Redis，收益是 **后台与登录态快 0.3–0.6s**，对匿名访客的 LCP **0 收益**。汇报时必须这么说，不要把这份功劳记到 LCP 上。

### 7.4 CDN：先解决「跨地域 RTT」，再谈 HTML 缓存

| 配置 | 作用 | 建议 |
|---|---|---|
| 静态资源长期缓存 | `Cache-Control: public, max-age=31536000, immutable`（文件名带 hash） | 必做 |
| 全站 TLS + HTTP/3 | 握手与多路复用 | 必做 |
| HTML 边缘缓存 | 把 TTFB 从 180ms 降到 60–90ms | 谨慎：purge 策略必须与页面缓存同一套触发器 |
| 图片自动转 AVIF | 省事 | 检查是否「按需转码」拖慢首字节，优先构建期生成 |

```nginx
# 静态资源：一年 + immutable（前提是文件名带内容哈希）
location ~* \.(avif|webp|woff2|css|js)$ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}
# HTML：短 TTL + 允许边缘过期后异步回源
location = / {
  add_header Cache-Control "public, s-maxage=600, stale-while-revalidate=60";
}
```

案例：TTFB 180ms → **90ms**（开启 HTML 边缘缓存后），LCP 1.69s → **1.60s**。

> **本仓库引擎路线**：静态产物的 HTML 内容不变，可以直接全站 CDN 缓存 + 长 TTL，不存在 nonce 与「缓存了旧价」的问题——这是静态生成相对 CMS 的结构性优势，值得在客户沟通时讲清楚。

### 7.5 排障顺序：症状 → 哪一层

| 症状 | 最可能的层 | 第一件事 |
|---|---|---|
| 全站都慢、TTFB > 1s | 页面缓存未命中 | 看响应头 `x-cache` / `cache-control`，查排除规则 |
| 只有首页慢 | 首页被排除缓存 / 轮播动态 | 查排除列表与主题动态区块 |
| 改了内容但访客看到旧的 | CDN 或页面缓存 | 按「CDN → 页面缓存 → 对象缓存」顺序清，并查 purge 钩子 |
| 表单提交 403 / 过期 | 页面缓存 + nonce | 该页排除缓存（7.2） |
| 后台慢、前台快 | 对象缓存缺失 | Redis + 慢查询日志 |
| 某些地区慢 | CDN 未覆盖 / 源站单地域 | 补 POP 或换多地域源站 |

| 6 | **副作用与取舍** | 反常识加分项 | 你放弃了什么（如 optional 字体会丢品牌字） |
| 7 | **未做与原因** | 显得诚实、有判断力 | 「没上 Redis，因为页面缓存命中后 PHP 不执行」 |
| 8 | **可复现** | 让懂行的人验证 | 测量命令、报告 JSON 附件 |

### 9.2 截图纪律

```text
□ 用同一个工具（都 Lighthouse，或都 PageSpeed），不要混
□ 标注工具版本 + 日期 + 设备档位（截图里就有，别裁掉）
□ 前后用同一页面、同一视口宽度
□ 数据表格优先于仪表盘截图（数字可被引用，仪表盘不能）
□ 附上 raw JSON 的链接或附件——这是「不怕被核」的信号
```

### 9.3 说法对照：同一件事的两种写法

| ❌ 会让内行皱眉 | ✅ 直接建立信任 |
|---|---|
| 「对网站进行了全面的性能优化」 | 「首页 LCP 4.2s→1.6s，首屏传输 4.8MB→780KB，移动端性能分 38→94」 |
| 「图片压缩了」 | 「Hero 1.92MB JPEG → 34KB AVIF（768w 档），移动端 LCP −1.2s」 |
| 「性能提升 200%」 | 「LCP 从 4.2 秒降到 1.6 秒（时长不可相加，别用百分比倍数）」 |
| 「PageSpeed 100 分」 | 「实验室移动 94 分 / 桌面 99 分；现场 p75 预计 2.0–2.6s」 |
| 「上了 Redis，性能大幅提升」 | 「Redis 让后台与登录态快 0.3–0.6s；匿名访客 LCP 0 收益（页面缓存命中时 PHP 不执行）」 |
| 「优化了 preload」 | 「preload 改用 imagesrcset 对齐 srcset，消除二次下载，LCP −0.4s」 |

### 9.4 一页纸摘要模板（可直接复制）

```markdown
# 性能优化报告｜<站点名>

**结论**：移动端 LCP 4.20s → 1.60s（−62%），首屏传输 4.82MB → 780KB（−84%），
Lighthouse 移动性能分 38 → 94。收益的 77% 来自「图片管线 + LCP 发现时机」，零额外成本。

**口径**：Lighthouse 12.x ｜ 移动模拟 ｜ Slow 4G ｜ 4× CPU ｜ 冷缓存 ｜ 三次中位 ｜ <日期>

**基线诊断（LCP 四段）**
| TTFB | 加载延迟 | 加载时长 | 渲染延迟 |
|---|---|---|---|
| 620ms | 1480ms | 1720ms | 380ms |

**关键动作**
1. 页面缓存 + 关键 CSS：TTFB 620→180ms，FCP 2.4→1.6s（¥0）
2. Hero 静态化 + imagesrcset preload：加载延迟 1480→700ms（¥0）
3. AVIF 五档 srcset：加载时长 1720→560ms，hero 1.92MB→34KB（¥0）
4. 字体子集 + 回退匹配：CLS 0.18→0.02（¥0）
5. CDN 边缘缓存：TTFB 180→90ms（¥~$20/月）
6. 第三方延迟 + INP：TBT 480→110ms（¥0）

**取舍**：未对非首屏图 preload（会抢带宽，实测让 LCP 变慢 0.3s）；
询盘页排除页面缓存（保 nonce 表单可用，牺牲该页缓存收益）。

**未做**：Redis 对象缓存（页面缓存命中后 PHP 不执行，对 LCP 无收益）；
未换主题（收益不抵风险，且客户无预算）。

**附件**：测量脚本见附录 B；原始 JSON 三份随报告提交。
```

### 9.5 把技术指标翻译成钱

客户不关心 LCP，但关心询盘。给一套**保守**换算，且明确标注是行业量级而非承诺：

```text
行业量级参考：移动端 LCP 每快 1s，转化率提升约 3–7%（不同行业差异极大）
本案例 LCP −2.6s → 保守取 3%/s → 约 +8% 询盘（同样流量、同样内容）
若月询盘 30 条、客单价 ¥50,000、成交率 8%：
  月增询盘 2.4 条 → 月增成交 0.19 单 → 年增营收约 ¥115,000
优化成本：约 2 人日
```

> **必须加的两句话**：① 这是量级估算不是承诺；② 转化率还取决于内容、报价、响应速度——**性能只是把「本来就该来的询盘」还给你**。

## 十、五个坑与三件别做的事

### 10.1 五个最常见的坑

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 1 | preload 与 srcset 不匹配 | Network 里同图下载两次 | 用 `imagesrcset` / `imagesizes`（4.4 坑 2） |
| 2 | 给所有图片加 `lazy` | 首屏图 800–1500ms 后才开始下载 | 首屏 `fetchpriority="high"`，其余 lazy |
| 3 | 缓存了带 nonce 的询盘页 | 表单 403 / 「链接已过期」 | `DONOTCACHEPAGE` 排除（7.2） |
| 4 | 字体 preload 整个家族、漏 `crossorigin` | 字体双下载、FCP 变差 | 只 preload 一个字重 + `crossorigin`（5.3） |
| 5 | 在办公室 WiFi + MacBook 上测移动分 | 数字漂亮，客户说「我这也是 4 秒」 | 固定协议（1.2）+ 至少一次 WebPageTest 真机 |

### 10.2 三件别做的事

```text
✗ 为了分数移除 GA4 / 客服 —— 分数是手段，业务是目的；上报「我删了分析工具」等于自证不懂业务
✗ 用 JS 把图片换成 data-src 再「加载」—— 这是把 LCP 变成「必须等 JS」，典型的负优化
✗ 一次性上 10 个优化插件 —— 每个插件自带 JS/CSS，互相覆盖，最后无法归因
```

### B.1 LCP 四段拆解（贴进 DevTools Console，或 Playwright `page.evaluate`）

```js
async function lcpBreakdown() {
  const lcp = await new Promise((res) => {
    new PerformanceObserver((list, obs) => { res(list.getEntries().at(-1)); obs.disconnect(); })
      .observe({ type: 'largest-contentful-paint', buffered: true });
    setTimeout(() => res(null), 8000);
  });
  if (!lcp) return { error: 'no LCP entry' };

  const nav = performance.getEntriesByType('navigation')[0];
  const img = lcp.url ? performance.getEntriesByName(lcp.url).at(-1) : null;

  const ttfbEnd     = nav.responseStart;
  const loadStart   = img ? img.startTime : (lcp.renderTime || lcp.loadTime);
  const loadEnd     = img ? img.responseEnd : loadStart;

  return {
    element: lcp.element ? lcp.element.outerHTML.slice(0, 140) : '(text node)',
    url: lcp.url || '(inline/text)',
    size: lcp.size,
    ttfb:          Math.round(ttfbEnd),
    loadDelay:     Math.round(loadStart - ttfbEnd),
    loadDuration:  Math.round(loadEnd - loadStart),
    renderDelay:   Math.round(lcp.startTime - loadEnd),
    lcp:           Math.round(lcp.startTime),
  };
}
lcpBreakdown().then(console.table);
```

## 附录 C：图片编码与 srcset 生成

### C.1 从一张原片生成全套

```bash
# 依赖：ImageMagick 7 / libavif(avifenc) / libwebp(cwebp)
SRC="hero-4000.jpg"

# 五档尺寸 + 三种格式（先缩 JPEG，再转 AVIF/WebP，质量更好）
for w in 480 768 1024 1440 1920; do
  magick "$SRC" -resize "${w}x" -strip -interlace Plane -quality 82 "hero-${w}.jpg"
  avifenc -q 55 --speed 6 --jobs 4 "hero-${w}.jpg" "hero-${w}.avif"
  cwebp -q 75 -m 6 -metadata none "hero-${w}.jpg" -o "hero-${w}.webp"
done

# 核对体积
ls -lh hero-*.{jpg,avif,webp} | awk '{print $5, $9}'
```

### C.2 质量档位对照（别凭感觉调）

| 目标 | JPEG | WebP | AVIF |
|---|---|---|---|
| 产品图 / 细节优先 | q85 | q80 | **q60** |
| 首屏 Hero | q82 | q75 | **q55** |
| 生活方式图 / 背景 | q78 | q70 | **q50** |

> AVIF 的 `-q` 与 JPEG 不是同一套刻度，**q55 约等于 JPEG q80**。用 q80 编 AVIF 会让体积翻倍、肉眼无差。

### C.3 生成 `srcset` 字符串（避免手写错档）

```bash
node -e '
const w=[480,768,1024,1440,1920];
const mk=(ext)=>w.map(x=>`/img/hero-${x}.${ext} ${x}w`).join(", ");
console.log("avif:", mk("avif"));
console.log("webp:", mk("webp"));
console.log("jpg :", mk("jpg"));
'
```

### C.4 验收（三条硬指标）

```text
□ 移动端实际下载的 LCP 图 ≤ 60KB（AVIF，<=768w）
□ 首屏图片全部带 width/height 或 aspect-ratio
□ 一页只有一个 fetchpriority="high"，且它就是 LCP 元素
```
