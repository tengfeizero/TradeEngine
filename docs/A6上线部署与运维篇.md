### 1.2 部署形态：静态站 + 一个写入口

引擎的产物天然分成两半，部署架构必须围绕这个事实设计：

```
买家浏览器
    │  HTTPS（TLS 在这里终止）
    ▼
CDN 边缘节点（缓存、压缩、限速、WAF）
    │  回源（HTTP 或全链路 HTTPS）
    ▼
反向代理（Nginx / Caddy：gzip/brotli、HSTS 头、/ → /en/ 301）
    │
    ▼
engine serve（单进程）
 ├─ 静态产物  .build/public/**        ← 只读，随时可整体替换
 ├─ /api/inquiry                       ← 唯一的写入口
 ├─ /healthz                           ← 监控探针专用，回显版本号
 └─ inquiries.db（SQLite）+ 通知队列   ← 有状态，必须落持久盘
```

三条硬约束，每一条都直接决定架构：

1. **单实例**。限流计数器、反重复指纹都锁在进程内存里（B3 9.5：限流锁只在进程内），挂两台 = 限流形同虚设。**伸缩的出路是把静态请求在 CDN 层消化掉，而不是给 API 加实例。**
2. **写入口只有 `/api/inquiry` 一个**。静态部分无状态、可随时整体替换；有状态的只有 `inquiries.db` 一个文件。这决定了备份与回滚策略可以极简（§6）。
3. **`engine admin` 只绑回环地址**（main.go 安全模型注释：admin 端点能读写站点内任意 YAML，因此**只允许绑定 loopback**）。远程改内容走 SSH 隧道，B1 R3 的「后台不对外暴露」是引擎级保证，不是运维自觉。

### 1.3 引擎已做与没做：一张对账表

部署前先知道哪些活引擎干完了、哪些必须你在反代层补。以下是 0.13.4 实测（附录 C）+ 源码取证：

| 事项 | 引擎现状 | 证据 |
| --- | --- | --- |
| HTML 缓存头 | ✅ `Cache-Control: no-cache`（协商缓存，内容更新立刻生效） | 实测 `/en/` |
| 哈希媒体缓存头 | ✅ `public, max-age=31536000, immutable` | 实测 `/media/brand-card.29b27b80.jpg` |
| 其余资源缓存头 | ✅ `public, max-age=3600`（无哈希兜底，不敢更长——源码注释原话） | 实测 `/assets/inquiry.js`、`/llms.txt` |
| 安全头 | ✅ `X-Content-Type-Options: nosniff` + `Referrer-Policy: strict-origin-when-cross-origin` 全路由 | 实测所有响应 |
| CORS | ✅ 白名单制、不收 `*`，`Vary: Origin` 防跨站缓存串包 | server.go:119–137 |
| 探活端点 | ✅ `/healthz` 回 `{"ok":true,"version":"0.13.4"}`，`no-store` | 实测 |
| 后台暴露面 | ✅ `engine admin` 只绑回环 | main.go:817 |
| 优雅关闭 | ✅ Ctrl+C 后给在途请求 10 秒收尾 | server.go:102 |
| **传输压缩** | ❌ **不压缩**。74,991 B 的 HTML 裸传，无 `Content-Encoding` | 实测 + §4.4 |
| **404 缓存头** | ❌ 404 响应无 `Cache-Control`，个别 CDN 会缓存负响应 | 实测 `/no-such-page` |
| **根路径** | ❌ `/` 返回 404，无跳转默认语言（A5 已记录的缺口，生产必须反代补 301） | 实测 `/` |
| **HSTS / TLS** | ➖ 不归引擎管——引擎按纯 HTTP 设计，TLS 终止在反代。但 HSTS 头必须有人发 | §3.2 |
| **真实客户端 IP** | ⚠️ `--trust-proxy` 默认 `false`（防 XFF 伪造绕限流）。放在 Cloudflare/Nginx 后**必须显式开启**，否则全站共享一个限流额度 | main.go:426、salt.go:54 |

**「➖」不是缺口，是分层**：引擎按「反代之后的一个普通进程」设计，TLS、压缩、跳转这些边缘职责本来就该在边缘做。但**没人做就是全没做**——§8 的九项就是给「没人做」兜底的。

## 二、域名与 DNS：注册商和解析器是两回事

### 2.1 一张完整的 DNS 记录账

外贸站的 DNS 不只是「域名指到服务器」一条记录。以下是一张**交付时一次配齐**的账，每一行都能用 `dig` 验证：

| 记录 | 值 | 干什么 | 谁在用 |
| --- | --- | --- | --- |
| `@ A` / `@ AAAA` | 服务器或 CDN IP | 裸域解析 | 所有人 |
| `www CNAME` | 指向主域（或 CDN CNAME） | www 子域 | 所有人 |
| `@ MX` | 邮件服务商指定值 | **收询盘邮件**（或转发到销售邮箱） | A4 通知链路 |
| `@ TXT`（SPF） | `v=spf1 include:<ESP> ~all` | 声明谁有权替你发信 | R4 |
| `<selector>._domainkey TXT` | 邮件服务商给的公钥 | DKIM 签名验签 | R4 |
| `_dmarc TXT` | `v=DMARC1; p=none; rua=mailto:dmarc@…` 起步 | 拒收伪造邮件 + 收滥用报告 | R4 |
| `@ CAA` | `0 issue "letsencrypt.org"`（按实际 CA 填） | 限定只有这家 CA 能给你签证书 | §3 |
| `_acme-challenge CNAME` | 按 DNS-01 验证要求 | 证书自动续期（DNS challenge 时） | §3.1 |

三条纪律：

1. **R4 的三条 TXT 和 MX 是同一个邮件域的一体四面**，A4 的「四周节奏」从写下这些记录那天开始计时。常见事故：SPF/DKIM 配在测试域上，生产域没抄——§8 第 4 项。
2. **CAA 一行记录，防的是「CA 误签」这类低概率但不可拒绝的事故**。填了你实际使用的 CA，别的 CA 想签签不了。
3. **每条记录写完立刻 `dig` 验证**，别攒到上线日。`dig +short TXT _dmarc.example.com` 十秒钟的事。

### 2.2 注册商四条铁律

域名是整个资产体系里**唯一被抢注了就几乎救不回来**的东西（证书丢了能重签，DNS 错了能改回，域名被别人注册了就只能换品牌或仲裁）。四条铁律：

| # | 铁律 | 反面案例 |
| --- | --- | --- |
| 1 | **域名自己注册在自己（或客户）名下**，绝不放在建站服务商账户里 | 服务商跑路或闹翻，站和域名一起被扣 |
| 2 | **开注册商转移锁 + WHOIS 隐私**，但保留邮箱可达 | WHOIS 隐私挡的是垃圾邮件，不是到期通知——到期通知发到注册邮箱，邮箱丢了就收不到 |
| 3 | **一次注册多年 + 自动续费 + 提前告警**：注册商 90/30/7 天的提醒邮件之外，把它写进 §7 的监控日历 | 域名过期 → 全站解析消失 → 抢注者按小时计价卖给你 |
| 4 | **注册邮箱用独立于站点服务器的基础设施** | 站点服务器挂了连到期邮件都收不到 |

第 4 条值得展开：它和 §7.3 的告警原则是同一条——**告警通道不能依赖被监控对象本身**。

### 2.3 TTL：不是「48 小时生效」，是「新旧叠加」

DNS 迁移最流行的迷信是「改了解析要等 48 小时」。真相：**每条记录按各自的 TTL 过期，期间新旧值按缓存剩余时间叠加**。所以 TTL 是你自己控制的风险阀门：

| 阶段 | TTL | 理由 |
| --- | --- | --- |
| 域名刚注册、站点未上线 | 86400（1 天）无所谓 | 没流量，错配无所谓 |
| **计划内迁移前 24–48 小时** | **降到 300（5 分钟）** | 先降 TTL 再改记录，这是顺序，不能反 |
| 迁移当天 | 300 | 出问题 5 分钟回滚 |
| 稳定运行 1–2 周后 | 回到 3600（1 小时） | 降低解析器查询压力，也降低 DNS 故障的暴露面 |
| **永远不要** | 86400 + 频繁迁移 | 等于把每个错误放大成一天 |

**「48 小时」的正确用法**：它是你给迁移留的观察窗，不是生效延迟。把迁移安排在**买家流量最低的时段**（对欧美买家，北京时间的凌晨），观察窗 48 小时，出问题按 §2.3 回滚。

### 2.4 www 与裸域：301 统一，一天都不能拖

`https://example.com` 和 `https://www.example.com` 同时可访问、互不做跳转，等于把整站的权重和收录劈成两半——这是 A5 §5 重复内容陷阱的域名版。规则：

1. **选一个做主域**（惯例如 `www`，或品牌裸域），另一个 **301** 过去；
2. 引擎输出的所有绝对地址（canonical、hreflang、og:image、sitemap）都由 `settings.baseURL` 单点生成——**baseURL 必须填主域**，跳转由反代做；
3. 验证：`curl -sI https://副域/en/ | grep -i location` 必须返回 301 且 `Location` 指向主域。

引擎侧没有任何「选主域」的开关，也没有跳转逻辑——**这个 301 是反代的活，写进 §8 第 7 项的检查单**。

## 三、证书与 HSTS：绿锁是底线，不是加分项

### 3.1 选型判定：自动续期 > 一切

不用纠结免费还是付费、DV 还是 EV。判定只有一条：

> **能自动续期的优先于一切不能自动续期的。**

理由：证书过期是「站点挂掉」成因里最蠢也最常见的一种——不是攻击、不是故障，是**没有人记得去点续期**。EV 证书那点浏览器绿条加成，外贸买家根本不看；而一次过期停机在 B1 里直接挂 Veto 级别的影响（买家 10 秒关站，询盘通道 V9 连带不可达）。

| 方案 | 续期方式 | 判定 |
| --- | --- | --- |
| Let's Encrypt（90 天） | acme 客户端 + 定时器，或 DNS-01 challenge | ✅ 默认选 |
| CDN 厂商托管证书（如 Cloudflare 边缘证书） | 厂商自动 | ✅ 可选，前提是源站到 CDN 一段也加密 |
| 商业 DV/OV（1 年） | 人工下单 + 人工安装 | ⚠️ 必须配到期监控（§7.2 L3）且提前 30 天续 |
| 自签 | — | ❌ 永不 |

**90 天不是缺点是优点**：续期周期短 = 自动化演练频繁 = 真出问题时你早就发现过。

### 3.2 HSTS：一条阶梯，两个不可逆的坑

HSTS（RFC 6797）让浏览器**记住**「这个站以后只许 HTTPS 访问」，从此用户手输 `http://` 或点了 http 链接都被浏览器本地强制升级。它是防降级攻击的正解，但两个坑都不可逆：

**坑一：`includeSubDomains` 会连坐子域。** 加了它，`mail.example.com`、`dev.example.com` 全都必须 HTTPS，否则那些子域在支持 HSTS 的浏览器里直接打不开。**确认所有子域都 TLS 化之前不要加。**

**坑二：`preload` 名单进得去出不来。** 申请进入浏览器内置名单（`hstspreload.org`）后，移除的生效周期以「月」计。没有十足把握不 preload。

所以上 HSTS 用阶梯，每级观察至少一周再进下一级：

| 阶梯 | 头 | 观察什么 |
| --- | --- | --- |
| 1 | `max-age=300` | 有没有混合内容报错、子域是否被连坐 |
| 2 | `max-age=604800`（1 周） | 同上 + 监控报错率 |
| 3 | `max-age=2592000`（1 月） | 稳定后 |
| 4 | `max-age=31536000`（1 年） | 长期 |
| 5 | 1 年 + `includeSubDomains` | 所有子域 HTTPS 化之后 |
| 6 | 1 年 + `includeSubDomains; preload` | 想清楚了再进 |

HSTS 头引擎不发（它管不到 TLS），**由反代/CDN 加**——§8 第 3 项。

### 3.3 混合内容：一张 http 图片灭掉整页绿锁

页面通过 HTTPS 加载，但引用了 `http://` 的图片/脚本/字体，浏览器立即把锁标降级为「不安全」，B1 R3 的判定直接不过。引擎侧的防线：所有资产 URL 由 `baseURL`（填 https）生成，模板输出经转义处理。但两处仍要人工自查：

1. **内容里手写的 URL**：产品描述、案例正文、 richtext 块里手打的 `http://` 链接；
2. **第三方嵌入**：地图、视频、聊天组件给的 embed 代码。

上线前全量扫一遍（附录 A 第 12 条给了一行命令，产物里 grep `http://` 排除注释和 xmlns）。

### 3.4 到期监控：证书的运维在证书之外

一张账：HSTS preload 的站，证书过期 = **浏览器层面直接拒绝连接**，连「你的连接不是私密连接」的点继续按钮都没有。所以：

- 证书到期监控不是「运维部的美德」，是 §7.2 的 L3 监控项（每日检查，30 天内到期告警）；
- 附录 B 的 `check-cert.sh` 十行 openssl 就能干；
- 商业证书 + 人工续期的组合，提前 30 天告警起步——人工流程就要留人工的提前量。

## 四、CDN 与缓存分层：A3 的 1.6 秒在生产怎么保住

### 4.1 四层缓存账

A3 讲过 WordPress 语境的缓存三层。放到本引擎的部署形态里，账是四层，每一层的职责和失效方式都不同：

| 层 | 存什么 | 谁失效它 | 引擎侧的现状 |
| --- | --- | --- | --- |
| ① 浏览器 | 静态资产（一年 immutable）、HTML（协商缓存） | 用户刷新 / 头过期 | 头已由引擎发好（§1.3） |
| ② CDN 边缘 | 全部可缓存响应 | 发布后主动 purge | 引擎头 CDN 应当尊重；规则见 §4.3 |
| ③ 反代 | 压缩后的响应（可选微缓存） | 重载配置 | 引擎不管 |
| ④ 构建产物 | `.build/public` 本身 | `engine build` 重新生成 | 不可变，发布即整体替换（§5.1） |

关键认知：**静态站没有「缓存失效」难题，只有「发布后刷新」动作**。没有数据库查询缓存、没有对象缓存、没有页面碎片缓存——因为根本没有动态页面。A3 里 WordPress 那套三层缓存的复杂性，在本架构里坍缩成一行：发布后 purge CDN。

### 4.2 每类资源的正确策略（实测对账）

引擎发的三级缓存头（§1.3 实测）和正确策略的对照：

| 资源 | 引擎实测头 | 判定 | 边缘层要补的 |
| --- | --- | --- | --- |
| HTML 页面 | `no-cache` | ✅ 正确——HTML 小（75 KB 量级），协商缓存即可，内容更新零延迟 | 无。**警惕 CDN 默认策略覆盖它**（§8 第 3 项） |
| 哈希媒体（`brand-card.29b27b80.jpg`） | `public, max-age=31536000, immutable` | ✅ 正确——文件名含内容哈希，URL 变 = 内容变 | 无 |
| 无哈希资产（`inquiry.js`、皮肤 CSS） | `public, max-age=3600` | ✅ 保守正确——源码注释原话「没有哈希兜底，不敢更长」 | 可选：边缘覆写为 1 天，但发布 purge 必须覆盖它们 |
| `llms.txt` / `sitemap.xml` / `robots.txt` | `public, max-age=3600` | ✅ 合理——爬虫对小时级延迟无感 | 无 |
| 404 页 | **无 `Cache-Control`** | ⚠️ 引擎缺口 #1：RFC 允许 CDN 自行决定，个别厂商会缓存负响应 | **边缘规则：4xx 一律 bypass cache** |
| `/api/inquiry` | POST 天然不可缓存（RFC 9111） | ✅ 语义安全 | **仍显式配 `/api/*` bypass**——不赌 CDN 实现 |

第 4 行是本章第一个引擎缺口：`notFoundPage`（server.go:195 起）直接写 body，没设缓存头。**不修不致命**（主流 CDN 默认不缓存 404），但「不赌厂商默认值」是本篇的总原则。

### 4.3 CDN 配置的最小集

把主流厂商的几百个开关收敛成五条规则，全部有引擎实测依据：

| # | 规则 | 依据 |
| --- | --- | --- |
| 1 | `/api/*` → Bypass cache，不缓存任何方法 | 唯一写入口 + 限流计数在此发生 |
| 2 | 4xx/5xx → Bypass cache | 引擎 404 无缓存头（缺口 #1） |
| 3 | HTML 尊重源站 `no-cache`，不用 CDN 默认 TTL 覆盖 | 否则改了内容买家 24h 看不到 |
| 4 | 静态资产按源站头缓存（immutable 那一年随便缓存） | 内容哈希兜底 |
| 5 | **WSAF/速率限制放在 CDN 层**，阈值高于引擎限流（引擎 10/h/IP + 30/天/IP 是应用层最后防线，CDN 层挡的是洪水不是单客） | B1 R3「表单有蜜罐或 Turnstile 且有限流」——引擎已有蜜罐 + Turnstile + 双层限流，CDN 层补纵深 |

### 4.4 压缩：引擎不压，A3 的预算在这里兑现

实测坐实的缺口：kestrel 首页 HTML 74,991 B **裸传**，无 `Content-Encoding`（Go 标准库 `http.ServeFile` 不做压缩）。这个数字意味着什么：

```
74,991 B  原始
19,117 B  gzip -9 压缩后（3.9×，本机实测）
≈ 55 KB   每个首屏请求省下的字节数
```

A3 的 LCP 1.6 秒预算里，传输字节数是硬项。**反代/CDN 不开压缩，A3 做的全部优化平白丢一块。**配置要求：

- **Brotli (`br`) 优先**，压缩率比 gzip 再好 15–20%；CDN 场景直接开「Brotli + gzip 自动协商」；
- 压缩级别：反代静态文件场景用最高级（`gzip_comp_level 9` / brotli 11）——**静态产物压一次缓存一次，CPU 成本可忽略**，这是和动态站最大的不同；
- 别忘了非 HTML 文本资产：CSS、JS、SVG、CSV、`llms.txt` 都要进压缩类型表；图片（jpg/webp/woff2）**不要重复压缩**（已是压缩格式）。

### 4.5 purge 与发布绑定

发布流程的最后一步是 purge，不是「想起来再刷」：

```bash
engine build && rsync ... && curl -X PURGE ...   # 伪代码：purge 是发布命令的一部分
```

反例是真实发生过的交付事故：换 logo 改了品牌色，发布后客服收到的第一个问题就是「你们官网怎么还是旧的」——因为 CDN 把 HTML 缓存了 24 小时而没人 purge。静态站的一切缓存问题，答案都是同一句：**purge 写进发布脚本**。

### 4.6 回源与真实 IP：`--trust-proxy` 的两难必须想清楚

引擎限流按客户端 IP 计（10 次/小时 + 30 次/天，`rate_limit_per_day` 默认 30）。放在 CDN/反代后面，引擎看到的 `RemoteAddr` 全是代理 IP——于是：

- **不开 `--trust-proxy`**（默认）：所有买家共享一个 IP 的限流额度。极端算账：30 个买家各提交 1 单/天，合计 30 次，撞上 30/天 的全局限流——**第 31 个买家开始，所有人提交失败**。这不是拒绝服务攻击，是正常营业额。
- **开了 `--trust-proxy` 但反代不覆写 XFF**：引擎信任一个客户端可伪造的头，攻击者每次请求换个假 XFF，限流归零。

所以它是个**配对开关**：`--trust-proxy=true` 的前提是**你的反代/CDN 确实覆写（而非追加）X-Forwarded-For 或设置 CF-Connecting-IP**。引擎源码注释（salt.go:54）写得很直白：「直接信任 X-Forwarded-For 会让攻击者」伪造。验证方法：在预发环境带反代提交一次询盘，`engine inquiries -json` 看 IP 字段是不是真实买家 IP 而不是 127.0.0.1 或 CDN IP。

这是 §8 第 5 项，也是最危险的一项——**不开会漏单，开错了会被刷，两个方向都致命**。

## 五、发布流水线与运行时：构建产物不可变

### 5.1 构建与发布分离

原则一句话：**产物只构建一次，在 CI（或你的工作机）上；服务器只接收产物，永远不在服务器上构建。**

```
工作机/CI                          服务器
engine build                       /srv/kestrel/releases/
  ├─ 门禁：0 错 0 警                  ├─ 2026-11-01-1530/
  ├─ Lighthouse 四项 ≥ 基线            ├─ 2026-11-02-0900/   ← current → symlink
  └─ rsync → releases/新目录            └─ ...
                                 current symlink 原子切换
```

三条理由：

1. **可回滚**：回滚 = symlink 指回上一个目录，秒级、无构建过程（§6.2）；
2. **可重现**：发布出去的产物就是通过门禁的那份，不存在「服务器上再 build 一次结果不一样」（依赖版本漂移）；
3. **发布门禁有牙齿**：`engine build` 0 错 0 警是 B 系列铁律；Lighthouse 四项 100/97/100/100 的基线**必须随发版重测**——0.13.0 加区块曾把可访问性拉到 88，教训写在 B3 里。

原子切换的细节：rsync 到**新目录**（带时间戳），然后 `ln -sfn` 切换 symlink。两步之间没有中间态。静态文件服务器对 symlink 的支持是普遍的；Nginx 配 `disable_symlinks off` 即可。

### 5.2 运行时清单（systemd 单元）

`engine serve` 是一个长驻进程，生产环境用 systemd 管起来：

```ini
# /etc/systemd/system/kestrel.service
[Unit]
Description=Kestrel trade site (engine serve)
After=network.target

[Service]
User=kestrel
WorkingDirectory=/srv/kestrel/current
ExecStart=/usr/local/bin/engine serve --addr 127.0.0.1:8080 --trust-proxy=true /srv/kestrel/current
Environment=ENGINE_TURNSTILE_SECRET=***       # Turnstile 密钥走环境变量，不进 git
Environment=ENGINE_SMTP_HOST=***              # A4 的 SMTP 凭据同理
Restart=always
RestartSec=5
# 引擎优雅关闭给在途请求 10 秒（server.go:102），systemd 要等它
TimeoutStopSec=15
KillSignal=SIGTERM
# inquiries.db 落持久盘；ProtectSystem 只留写白名单
ReadWritePaths=/srv/kestrel/data

[Install]
WantedBy=multi-user.target
```

四个易漏点：

| 易漏点 | 后果 | 依据 |
| --- | --- | --- |
| `--trust-proxy=true` 漏了 | §4.6 的灾难（全体买家共担限流） | main.go:426 |
| 环境变量没配 | Turnstile 静默降级 / SMTP 不通，询盘照落库但通知失败——**V9 只判单向就发现不了** | A4 的教训：`mailOK||hookOK` |
| `WorkingDirectory` / 数据路径漂移 | `inquiries.db` 写到了别的地方，备份脚本备份了个空库 | store.Open 按解析路径建库 |
| `TimeoutStopSec < 10s` | 发布重启时硬杀在途询盘提交 | server.go:101–106 |

最后一行值得单独说：引擎特意给了 10 秒收尾「避免客户正在提交时被硬断」，systemd 的默认 90 秒够用，但如果你改了它，**别改到 10 秒以下**。

### 5.3 admin 与 studio：只走回环

`engine admin`（改文件）和 `engine studio`（改内容库）都只绑回环地址。生产服务器上想远程改内容：

```bash
ssh -L 9090:127.0.0.1:9090 deploy@kestrel-server
# 浏览器开 http://127.0.0.1:9090/admin
```

**永远不要**用 socat/frp/反代把 `/admin` 暴露到公网来「图方便」——admin 端点能读写站点内任意 YAML，一旦暴露等于把服务器根目录交给互联网。B1 R3 判定「后台不对外暴露」，引擎的回环绑定已经把下限焊死，运维这边别亲手拆。

### 5.4 发布间隔与通知队列

引擎的通知是异步的：询盘先落库，通知走队列（256 容量，失败按 2/6/18 秒重试）。发布重启时：

- 已落库未通知的询盘，重启后队列会重放（通知状态在库里有 `NotifiedAt` 标记）；
- 所以**发布不需要挑「没有询盘的时候」**——这正是「落库 + 双通道」设计的运维红利，A4 §「丢单 12 成因」里第 1 条（写库成功通知失败）在这里被架构兜住了。

## 六、备份与回滚：备份数 ≠ 可恢复

### 6.1 备份对象五件套

| # | 对象 | 位置 | 特点 | 频率 |
| --- | --- | --- | --- | --- |
| 1 | **询盘数据库** `inquiries.db` | 服务器数据盘 | **唯一不可再生资产**——站点丢了能 build，询盘丢了就没了 | **每日**，另加每次恢复演练前 |
| 2 | 内容源（YAML + theme + skins） | git 仓库 | 已有版本控制，push 到远端即可 | 每次 commit |
| 3 | **媒体原图**（sources.yaml 声明的那些） | git 或对象存储 | 引擎产物里的图是 4:3 处理版，**原图丢了重处理无从谈起** | 进 git 或同步对象存储 |
| 4 | 服务器配置（nginx/systemd/脚本） | git（infrastructure repo） | 重建服务器的全部依据 | 每次变更 |
| 5 | DNS 记录导出 | 离线文档 | DNS 服务商故障时 10 分钟内可在别处重建 | 每次变更 |

3-2-1 原则照常适用：3 份副本、2 种介质、1 份离站。第 1 行单独强调：**`inquiries.db` 是这套架构里唯一「丢了就是真丢了」的东西**。

### 6.2 回滚：静态部分 30 秒，数据部分按天

**静态回滚**（改坏了页面、发错了内容）：

```bash
ln -sfn /srv/kestrel/releases/2026-11-01-1530 /srv/kestrel/current
# 30 秒完成。purge CDN（§4.5），结束。
```

**数据回滚**（误删询盘、库损坏）：SQLite 的正确备份方式是 `.backup` 命令（在线一致快照），不是拷贝文件（拷贝可能拷到 WAL 半途状态）：

```bash
sqlite3 /srv/kestrel/data/inquiries.db ".backup /backup/inquiries-$(date +%F).db"
```

恢复 = 停服 → 换库文件 → 起服，窗口以分钟计。保留策略建议：7 天日备 + 4 周周备 + 12 月月备，询盘数据没有「过期」一说。

### 6.3 恢复演练：备份的价值由演练定义

B1 R6 对「有人在管吗」的判定问法是：**「上次备份恢复是什么时候」**。备份没演练过 = 不存在。季度演练的最小流程（30 分钟）：

1. 在预发机（或本机 Docker）起一套空白环境；
2. 拉最近一份日备，恢复 `inquiries.db`；
3. `engine serve` 起来，`engine inquiries -json` 数条数，和备份时点核对；
4. 随机抽一条询盘，核对字段完整（附件、来源页）；
5. 记录：耗时、遇到的问题。**演练记录本身是 R6 的证据。**

### 6.4 询盘数据的双保险：每日 CSV 导出

SQLite 库 + 每日备份已经两层。再加一层**格式无关**的出口——每日 CSV 导出（邮件或对象存储）：

- 理由：备份解决「文件丢了」，CSV 解决「格式/工具不可用」——三年后库结构变了、引擎升级了、甚至不用这个引擎了，CSV 谁都读得开；
- 引擎已有现成命令（`engine inquiries` 支持导出），脚本见附录 B 第 4 段；
- 频率每日一次，和 DB 备份同一任务里串行跑。

### 6.5 外贸站的 RTO/RPO 参考值

不用照搬企业级 15 分钟 RTO。静态站 + 单写入口的架构，合理目标是：

| 场景 | RTO（恢复耗时） | RPO（数据丢失量） | 手段 |
| --- | --- | --- | --- |
| 内容发错 | 秒级 | 0 | symlink 回滚 |
| 服务器整机故障 | < 2 小时 | ≤ 1 天询盘 | 重建（配置全在 git）+ 日备恢复 |
| DNS 服务商故障 | < 30 分钟 | 0 | DNS 记录导出 → 备用解析商 |
| 域名被抢/被锁 | 天–月级（法律途径） | — | 铁律 §2.2 前置预防 |
| 询盘库损坏 | < 15 分钟 | ≤ 1 天 | SQLite 日备恢复 |

## 七、监控与告警：「站挂了谁先知道」

### 7.1 三种答案

「站挂了谁先知道」这个问题只有三种答案，按糟糕程度排序：

| 答案 | 发现渠道 | 典型延迟 | 代价 |
| --- | --- | --- | --- |
| ① 买家 | 询盘突然变零，或买家微信/邮件来问 | 数小时–数天 | **沉默流失**：买家不会告诉你，直接去同行 |
| ② 客户老板 | 看后台数据/听销售抱怨 | 数天 | 信任损失：交付方的专业度破产 |
| ③ 你 | 监控告警 | 1–5 分钟 | 处理成本，但客户无感 |

**判定：答案①出现过的交付方，下一个单子不会再来。**监控不是技术美德，是商业续约条款。

### 7.2 五层监控账

B1 R6 要求的「uptime 监控与告警、SSL 到期提醒」，展开成五层。每层有明确的探针、频率和告警阈值：

| 层 | 监什么 | 探针 | 频率 | 告警阈值 |
| --- | --- | --- | --- | --- |
| **L1 探活** | 站点活着、引擎活着 | `GET /healthz`（引擎自带，回 `ok` + `version`） | 1 分钟 | 连续 3 次失败 |
| **L2 询盘链路** | V9 双向通 | 专项探针（见下方约束） | 见下 | 任一方向断 |
| **L3 到期** | 证书、域名、DKIM 密钥轮换 | `openssl s_client` / `whois` | 每日 | < 30 天 |
| **L4 邮件链路** | R4：SPF/DKIM/DMARC 有效 + 测试信进收件箱 | DNS 查询 + 双 ESP 测试信 | 每周 | 任一记录消失/测试信进垃圾箱 |
| **L5 业务面** | GSC 覆盖错误、GA4 实时、被黑迹象（V8） | GSC 邮件告警 + 周检脚本 | 每周 | GSC 安全问题 = 立即 |

**L2 的一个真实约束：探针会撞限流。**引擎限流 10 次/小时/IP，常规 uptime 探针每 1–5 分钟 POST 一次 `/api/inquiry`，一小时就把自己限死了——然后你会收到两种假信号：要么探针 429 报警（假阳性：站没挂），要么你把探针关了（假阴性：真挂了没人知道）。这是**引擎缺口 #4：没有探针白名单**。当下可行的三种处置：

1. **探针降频到每小时 ≤ 2 次**，接受「最坏 1 小时才发现询盘断」（对询盘这种低频高值场景可接受）；
2. 探针流量走独立出口 IP，并接受它也只提交 2 次/小时；
3. （不推荐）临时调大限流——等于给真攻击者开门。

L2 探针的正确姿势还有一层：**V9 是双向判定**（B1 明文），探针也要测两个方向——POST 落库（查 `engine inquiries -json` 或 admin API）+ 检查通知发出（A4 的 `digest` / 收件箱规则）。附录 B 给了完整脚本。

### 7.3 告警三要素

监控产生事件，告警产生行动。三条铁律：

1. **至少两个人收得到**。单人告警 = 单点故障的人生版。
2. **通道独立于被监控对象**。告警发到站点同服务器的邮箱 = 站挂了告警跟着挂。WhatsApp/Telegram 推送或短信是合理选择——买家的询盘通知走 SMTP，你的告警必须走另一条路。
3. **有升级机制**。15 分钟未确认 → 升级到第二人。凌晨三点的告警没人理，等于没告。

### 7.4 假阳与假阴

监控系统的两种失败模式都要设计掉：

| 失败 | 场景 | 对策 |
| --- | --- | --- |
| 假阳性 | 429 探针撞限流（§7.2）；探针所在地区网络抖动；DNS 抖动 | 连续 N 次失败才告警；多地域探针 |
| 假阴性 | 探针从机房内网发 → 测不出 CDN 边缘挂；探针只测首页 → 测不出 API 挂 | 探针放在外部（多地域）；L1 探 `/healthz`、L2 探 `/api`，两层分开 |

一条实用主义规则：**告警不可信（假阳太多）比没有告警更糟**——团队会养成「又是误报」的肌肉记忆。宁可阈值保守（连续 3 次失败再报），不要让告警失去信用。

### 7.5 被黑监控（V8 视角）

B1 V8「站点已被入侵」和 R3「没被黑没被刷」放到运维节奏里，就是三件常态化的事：

1. **GSC 安全问题报告**每周看（有安全问题 GSC 会邮件通知，前提是你验证过 GSC——§8 第 7 项）；
2. **外链扫描**：`grep` 构建产物里的 `http://` 外链 + `site:你的域名` 抽查异常关键词（V8 的判定法）——静态站的「被塞暗链」发生在源码或服务器层，全量 grep 产物是最直接的体检（附录 B 第 5 段）；
3. **询盘洪水告警**：单日询盘量超过基线 3 倍告警（在 CSV 导出任务里加一行行数比对）——洪水意味着要么被刷（限流拦没拦住），要么真有大单（是好事，但也要人看）。

静态站被黑的面本来就小（没有可注入的动态执行），但**服务器层（SSH、面板、依赖）仍在**——那是另一个话题，本篇只画监控线。

## 八、A3–A5 落生产最容易漏的九项配置

本篇的核心承诺。A3–A5 的每一项优化都「在测试环境成立」，但生产环境的默认配置和测试环境**不一样**，于是出现了「测试时都快、上线后都忘」的经典剧本。九项，按危险度排序，每项给一分钟检查法：

### 第 1 项（最危险）：限流与真实 IP —— A4 的 `--trust-proxy`

- **测试环境成立的前提**：直接访问 `localhost:8080`，每个请求都是独立 IP。
- **生产最常漏的配置**：反代后不开 `--trust-proxy=true` → 全站买家共享一个限流额度（§4.6 的算账：第 31 个/天 的买家开始提交失败）；或开了但反代不覆写 XFF → 限流可伪造。
- **一分钟检查**：预发带反代提交一单 → `engine inquiries -json` 看 IP 字段；再用伪造 XFF 头提交 → 应被识别为同一 IP。

### 第 2 项：压缩没开 —— A3 的字节预算作废一半

- **测试环境成立的前提**：本地 dev server 或框架自带压缩。
- **生产最常漏的配置**：引擎不压缩（实测 74,991 B 裸传），反代/CDN 默认模板没开 brotli/gzip。
- **一分钟检查**：`curl -sI -H 'Accept-Encoding: br,gzip' https://站点 | grep -i content-encoding`——空 = 没开。开了之后 A3 报告里的字节数要全部重测（约 3.9× 折减，本节实测）。

### 第 3 项：CDN 无视了引擎的缓存头

- **测试环境成立的前提**：没有 CDN，「改了立刻生效」是天然的。
- **生产最常漏的配置**：CDN 默认策略把 HTML 也缓存（有的厂商默认 2 小时 TTL），或对无缓存头的 404 做负缓存；发布后没人 purge。
- **一分钟检查**：发布一次改标题的测试内容 → `curl` 线上 HTML 看 `Cache-Control` 与内容新旧；对照 §4.3 的五条规则逐条过。

### 第 4 项：邮件三记录没从测试域抄到生产域 —— A4 的 R4

- **测试环境成立的前提**：测试域dig 三条 TXT 齐全、测试信进收件箱。
- **生产最常漏的配置**：SPF/DKIM/DMARC 停留在测试域；或生产域 MX 指向了「域名的原邮件托管」而不是询盘通知用的 ESP。
- **一分钟检查**：`dig +short TXT example.com | grep spf`、`dig +short TXT _dmarc.example.com`、`dig +short MX example.com` 三连；再按 A4 的双 ESP 测试信各发一单看落点。

### 第 5 项：GA4 数据流还是测试 URL —— A4/R5

- **测试环境成立的前提**：GA4 数据流配的是 `localhost` 或测试域，事件照收。
- **生产最常漏的配置**：GA4 数据流的站点 URL 没改成生产域（实时报告看不到生产流量）；Consent Mode v2 没接（R1 对 EU 的要求）。
- **一分钟检查**：线上站提交一单（Consent 同意）→ GA4 实时报告应出现 `generate_lead` 事件（引擎致谢页已埋，引擎侧无活）。

### 第 6 项：preload 字体丢了 `crossorigin`

- **测试环境成立的前提**：A3 修好的 preload 写在产物里，本地一切正常。
- **生产最常漏的配置**：产物质变不变，但**新加 CDN 域名**后若字体走了另一域，preload 的域不匹配 → 双重下载（A3 四坑之一在生产复活）。
- **一分钟检查**：Lighthouse 随发版重测（本就是门禁），专项看「Preload key requests」与「Ensure fonts...」两项。

### 第 7 项：根路径 404 + hreflang 生产域 —— A5 的两个尾巴

- **测试环境成立的前提**：A5 已记录根路径 404 缺口但本地预览无碍（大家直接访问 `/en/`）；hreflang 由 `baseURL` 同源生成。
- **生产最常漏的配置**：① `/` 没配 301 → `/en/`（实测：引擎对 `/` 返回 404，**买家手输裸域直接撞 404 页**，这是买家体验的第一跳）；② `baseURL` 忘改生产域 → 全站 canonical/hreflang/og:image/sitemap 都指向测试域。
- **一分钟检查**：`curl -sI https://站点/` 应 301 → 默认语言；`curl -s https://站点/en/ | grep -o 'hreflang="[^"]*"' | head` 核对绝对地址域名的正确性。

### 第 8 项：爬虫三件套没对账 —— A5/E3

- **测试环境成立的前提**：sitemap、robots、llms.txt 都在产物里，引擎构建校验过。
- **生产最常漏的配置**：GSC 资源没建（或验证 meta 用的是测试值）、sitemap 没提交 → E6 永远拿不到分。
- **一分钟检查**：`curl -s https://站点/robots.txt | grep -i sitemap`、`curl -s https://站点/sitemap.xml | head -5`、`curl -s https://站点/llms.txt | head -3` 三连，然后 GSC 提交 sitemap。

### 第 9 项：分享卡与数据出口的绝对 URL

- **测试环境成立的前提**：brand-card、datasheet、图片 zip 的链接都由 `baseURL` 生成，本地点击正常。
- **生产最常漏的配置**：同第 7 项的 baseURL 问题，但后果不同——**og:image 指向测试域 = 社交分享出图全挂**（WhatsApp/LinkedIn 的爬虫不重试）；`/data/` 出口链接失效 = 页脚 Data 出口和 E7 的「机器可读」全废。
- **一分钟检查**：WhatsApp 里发一次站点链接看卡片出图；`curl -sI https://站点/data/sku-list.csv` 应 200 且 `text/csv`。

### 九项收敛成一句话

> **A3–A5 的优化都长在 `baseURL` 和反代这两棵树上：baseURL 改对，九项里的 4、7、9 自动解决；反代配对，1、2、3、7 自动解决；剩下 5、6、8 是「在正确的域名上把账号体系接好」的一次性动作。**

## 九、五个坑与三件别做的事

### 五个坑

1. **CDN 把 HTML 缓存了 / 404 负缓存**。症状：内容改了买家看到旧的、或错误页被缓存扩散。对策：§4.3 规则 2、3 + purge 进发布脚本。
2. **`--trust-proxy` 方向配错**。不开 → 正常买家撞限流（漏单）；开了不覆写 XFF → 被刷。两向都致命，预发环境验证后再上生产（§4.6）。
3. **HSTS `includeSubDomains` 连坐子域**。证书没覆盖的子域在老访客浏览器里直接打不开，且老访客的 max-age 没法远程撤销。阶梯推进，每级观察一周（§3.2）。
4. **有备份、没演练**。B1 R6 的问法是「上次恢复是什么时候」，不是「有没有备份」。季练 30 分钟，换一个「敢回答」的底气（§6.3）。
5. **探针撞限流**。常规 uptime 探针每分钟 POST 询盘接口，一小时后变成「站点假死」告警。探针降频到 ≤2 次/小时，或等引擎补白名单（§7.2，缺口 #4）。

### 三件别做的事

1. **别在到期前 48 小时才动域名和证书**。迁移先降 TTL（§2.3），证书提前 30 天——所有「域名/证书类事故」的共同点是事前有提醒、没人当回事。
2. **别让服务器自己构建**。构建产物不可变（§5.1），两台机器 build 出来的东西没有可比性，回滚也就无从谈起。
3. **别把告警发进没人看的群**。告警三要素（两人、独立通道、升级机制）缺一条，监控就是花钱买心理安慰（§7.3）。

## 附录 B：监控探活脚本

### B.1 L1 探活（每分钟，监控服务或 cron）

```bash
#!/usr/bin/env bash
# healthz-probe.sh —— 失败时输出原因并以非零码退出，供监控服务接管告警
URL="https://example.com/healthz"
BODY=$(curl -fsS --max-time 10 "$URL" 2>&1) || { echo "FAIL: healthz unreachable"; exit 1; }
grep -q '"ok":true' <<<"$BODY" || { echo "FAIL: ok!=true: $BODY"; exit 1; }
echo "OK $(date -u +%FT%TZ) $BODY"
```

引擎的 `/healthz` 回显 `version`，顺带成为「发布是否生效」的旁证。

### B.2 L2 询盘链路双向探针（每小时 ≤ 2 次，§7.2 的限流约束）

```bash
#!/usr/bin/env bash
# inquiry-probe.sh —— V9 双向：落库方向 + 通知方向
# 频率红线：引擎限流 10/h/IP，本探针每小时至多 2 次（缺口 #4：无探针白名单）
API="https://example.com"

# 方向一：POST 落库（探针询盘用独立标识，便于后台清理）
RES=$(curl -fsS --max-time 15 -X POST "$API/api/inquiry" \
  -H 'Content-Type: application/json' -d '{
    "name":"SITE-PROBE","email":"probe@monitor.example.com",
    "message":"automated liveness probe","_company":"__honey__"}') || { echo "FAIL: POST"; exit 1; }
ID=$(jq -r '.id // empty' <<<"$RES")
[ -n "$ID" ] || { echo "FAIL: no id in response: $RES"; exit 1; }

# 落库方向核验：等 5 秒查后台（同机执行；远程用 admin API）
sleep 5
engine inquiries -json | jq -e --arg id "$ID" 'map(select(.ID==$id)) | length==1' \
  || { echo "FAIL: id $ID not in store"; exit 1; }

# 方向二：通知方向——A4 的 digest 查该探针单的 NotifiedAt
# （探针邮箱同时做收件箱规则：probe@ 的邮件 15 分钟内到 = 双向通过）
echo "OK: inquiry $ID stored; check probe inbox for notification"
```

> 探针询盘会真实落库——每月人工（或 cron）清理一次带 `SITE-PROBE` 标识的记录，别让它们污染客户的数据视图。

### B.3 L3 证书与域名到期（每日）

```bash
#!/usr/bin/env bash
# expiry-check.sh —— 30 天内到期告警（退出码 1）
DOMAIN="example.com"
DAYS=$(echo | openssl s_client -servername "$DOMAIN" -connect "$DOMAIN:443" 2>/dev/null \
  | openssl x509 -noout -enddate | cut -d= -f2 \
  | xargs -I{} expr \( $(date -d {} +%s) - $(date +%s) \) / 86400)
[ "$DAYS" -lt 30 ] && { echo "WARN: cert expires in $DAYS days"; exit 1; }
echo "OK: cert $DAYS days left"
# 域名到期（注册商 API 或 whois，各家输出不同，按你的注册商适配）
```

### B.4 每日备份 + CSV 导出（cron，§6.2/§6.4）
