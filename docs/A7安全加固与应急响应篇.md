# 外贸站开发系列 · A7 安全加固与应急响应篇

> **系列定位**：A6 把站送上了生产环境、架上了监控；本篇回答两个随之而来的问题——**这站到底有什么可被攻击的**（答案是：比你想象的少得多，但剩下的那一层在服务器上），以及**真出事的时候该怎么办**（答案是：按一张写好的剧本卡执行，而不是现场发明流程）。
> **适合读者**：第一次独立对客户站点负安全责任的开发者与交付方；以及读过 B1 的 V8/R3 却不知道从哪下手的人。
> **读完之后你应该能**：把引擎站点的攻击面画在一张表里（附实弹测试证据）；理解引擎十一步防线的三个设计裁决为什么是对的；给服务器层列一张加固清单；写出自己站点的应急响应剧本卡；并在 V8 之外向客户交付一份说得出口的安全基线。

> **口径声明（先读这一段）**
> 1. **引擎侧行为以 engine 0.13.4 源码 + 本机实弹测试为准**。写作本章前，我对 kestrel 的测试实例做了四组实弹测试（蜜罐注入、路径穿越、1.1MB 灌包、限流连发），全部记录在附录 C，可照跑复现。**测试落库的 10 条探针询盘已从测试库中清理**。
> 2. **服务器与流程侧以通用实践与法规原文为准**（GDPR 第 33/34 条、OWASP ASVS 的思路），凡引用条款处注明编号；涉及具体厂商（Cloudflare、注册商）的功能以厂商文档为准。
> 3. **这一篇照例写引擎的真实缺口**：Turnstile 网络失败时静默放行**且不留日志**（§2.4）、CSP/X-Frame-Options 未输出（反代补）、日志只到 stderr 不落盘（§4.6）。缺口清单在 §2.4 汇总。
> 4. 安全篇的特殊纪律：**不写「绝对安全」，只写「面有多大、代价几何」**。任何声称某站「不可攻破」的文档都应被扔掉。

## 一、攻击面盘点：四个入口与一个前提

### 1.1 一张表说清「能被碰的东西」

对公网访问者而言，`engine serve` 暴露的路由实测只有四条（server.go:57–63），逐个实测过（附录 C 第 1–3 项）：

| 入口 | 方法 | 实测行为 | 有状态吗 |
| --- | --- | --- | --- |
| `/healthz` | GET | 回 `{"ok":true,"version":"0.13.4"}`，`no-store` | 无 |
| 静态产物 `/…` | GET/HEAD | 文件服务，目录补 index.html，其余 404 | 无 |
| `/api/inquiry` | **仅 POST** | GET → 404；OPTIONS → preflight | **唯一写入口** |
| `/admin` | 任意 | **404**——admin 是独立命令 `engine admin`，且只绑回环地址（main.go:817） | 公网不存在 |

这个表就是静态站安全叙事的全部起点：**没有登录、没有会话、没有上传、没有模板注入面、没有 SQL 拼接面**（SQLite 全参数化）、没有用户可控的服务端执行。公网能改变这台机器状态的入口，**只有 `/api/inquiry` 一个，且它只能往一张表里 INSERT**。

### 1.2 「面小」不是「没面」：两个剩余攻击面

面小不等于零，剩下两个面要诚实列出：

1. **静态文件服务本身的解析面**——路径穿越、编码变体、Range 请求这些 HTTP 语义层的问题。实测：`/../inquiries.db` 被 Go 路由清洗成 307 重定向到 `/inquiries.db`，跟进后 404；URL 编码变体 `%2e%2e%2f` 同样 404（附录 C 第 3 项）。数据库文件在 `.data/` 目录、产物目录之外，**公网拿不到**。引擎侧还有第二道自查：`path.Clean` 消掉 `..` 后再挡一次编码变体（server.go:162–167），双保险。
2. **请求体积与频率面**——不试图入侵、只试图耗资源。这是 §3 的正题。

### 1.3 一个前提：真正的大面在服务器层

攻击者打不进引擎，不代表打不进这台机器。SSH 弱口令、过期依赖、面板漏洞、被钓鱼的运维邮箱——**静态站被黑的几乎全部现实路径都要先黑服务器**（§5 逐条展开）。所以本篇的结构是：§2 讲引擎把小面守得多严，§4 讲大面怎么收敛。

## 二、唯一的写入口：十一道防线与三个设计裁决

### 2.1 流水线全图：先便宜后贵

`/api/inquiry` 的处理顺序严格按「先便宜后贵」排布（handler.go:94–228），每一步的裁决都有明确理由：

| # | 防线 | 逻辑 | 命中后的行为 |
| --- | --- | --- | --- |
| ① | 方法白名单 | 只收 POST | 405 + `Allow` |
| ② | 体积限制 | `MaxBytesReader` 32KB——「一个 6 字段的表单不可能超过 32KB」（input.go:90 注释） | `payload_too_large` |
| ③ | **蜜罐 `_hp`** | 填了 = 机器人 | **静默假成功**（见 2.2） |
| ④ | **提交速度** | 页面渲染后 3 秒内提交不可能是真人（时间戳在未来或超 24h 不判——客户端时钟不可信） | 静默假成功 |
| ⑤ | 限流 | 小时闸 10 次 + 日闸 30 次（`rate_limit_per_day` 默认 30），计数持久化，**重启不清零** | 429 + 重试窗口 |
| ⑥ | 人机校验 | Turnstile（选型理由 D8：不依赖 Google、不用 Cookie、免费——欧盟合规解释成本低） | 校验失败 400 |
| ⑦ | 字段校验 | 长度上限（name 80 / company 120 / email 254 / phone 40 / message 4000）挡「往表单里灌 1MB 文本」；错误只回字段名和规则码，**不回显原始内容**（防探测） | 400/422 |
| ⑧ | 内容启发式 | SpamScore 0–100（评分细则见 2.3） | **只标记不删单** |
| ⑨ | 锁内复检 + 落库 | 同一 IP 的检查与写入在同一把分片锁内完成 | 落库失败才 500 |
| ⑩ | 异步通知 | spam 状态**不通知**——垃圾不打扰销售邮箱 | — |
| ⑪ | 结构化日志 | id/国家/产品/垃圾分/来源/UTM/耗时 | — |

两处值得单独记的工程细节：

- **⑤ 的双闸分工**（handler.go:230–236 注释）：小时闸挡突发（脚本一次灌几百条），日闸挡慢速渗透（每小时 9 个、连发一整天）。**只有小时闸时，单 IP 一天能灌 240 条**——这个数字是双闸存在性的证明。
- **⑨ 的锁内复检**：⑤ 的检查到这里之间隔着 Turnstile 网络调用和字段校验，同一 IP 的并发请求会一起读到「尚未到上限」而同时放行。B3 9.5 的实测：100 并发下阈值 10 被放过 18 条，锁内复查后精确为 10。**A7 写作时的实弹复测一致：12 连发 = 10×201 + 2×429**（附录 C 第 6 项）。

### 2.2 设计裁决一：对机器人「假成功」

蜜罐命中和提交过快的响应是 `{"id":"01M…","ok":true}`——**编造一个 ULID 返回成功，不落库**。实测验证：向蜜罐字段塞值提交，拿到了一个格式完全合法的询盘 ID，随后查库确认该 ID **不存在**（附录 C 第 5 项）。服务端日志同时记 `Warn "蜜罐命中，静默丢弃"` 带匿名化 IP。

为什么不直接 403？因为**拒绝响应本身就是探测信号**：攻击者收到 403 就知道这条防线存在，转头调整脚本绕过；收到 200 则完全无法分辨哪次提交被识别了。防线一旦对攻击者不可见，他就只能永远蒙在鼓里。

### 2.3 设计裁决二与三：fail-open 与「只标记不删单」

三个裁决其实是同一条价值观的三个投影——**「漏掉一条真询盘」的代价远大于「多收一条垃圾」**（B2B 询盘单条价值以千美元计，垃圾的处理成本是 3 秒的删除键）：

| 裁决 | 内容 | 兜底 |
| --- | --- | --- |
| 假成功 | 蜜罐/过快静默丢弃 | 服务端日志可查（§4.6 的 journald） |
| **Turnstile fail-open** | Cloudflare 校验服务网络失败时**放行**（turnstile.go:45–47 注释：Turnstile 挂了不该让客户无法询盘） | 限流 + 蜜罐 + 过快仍在；spam 人工复核 |
| 只标记不删 | SpamScore ≥ 60 → `status="spam"`，照常落库、不通知 | 后台可人工捞回误判 |

SpamScore 的细则（input.go:329–408），评分每一项都为误判付过学费：

| 信号 | 加分 | 误判防御 |
| --- | --- | --- |
| 链接 >3 个 | +40 | 正常询盘极少贴链接 |
| 链接 1–3 个 | 每个 +15 | 允许客户贴一个参考链接 |
| 14 个垃圾词表命中（en + zh） | +40（封顶一次） | 「seo services」「代开发票」「加微信」… |
| 非中文页出现中文 | +25 | **只加 25 不拒绝**——华人采购是真实客群 |
| 整段全大写 | +10 | **至少 20 个字母才判**——中文留言里的 CIF/FOB 全大写否则 100% 误报 |
| 40 字以上无空格 | +20 | 机器拼接特征 |

### 2.4 引擎侧仍欠的三样（诚实清单）

| # | 缺口 | 影响 | 当下处置 |
| --- | --- | --- | --- |
| 1 | **Turnstile fail-open 无日志**。三处网络失败分支直接 `return nil`，一行日志都不留（turnstile.go:69–85） | 人机校验失效了你也永远不知道——fail-open 的代价被静默化 | journald 里没有 `turnstile` 关键字 = 正常；**真要确认，只能在 Cloudflare 控制台看校验量与询盘量的差值**。已列入改进待办 |
| 2 | **无 CSP / X-Frame-Options**（A6 附录 C 实测全站只有 nosniff + Referrer-Policy） | 点击劫持与外链脚本风险。静态站无会话可劫持、模板输出已转义，风险低但非零 | 反代层补，见 §5.5 的一行配置 |
| 3 | **探针白名单**（A6 缺口 #4 重申） | L2 监控探针会撞 10/h 限流 | 探针 ≤2 次/小时（A6 §7.2） |

蜜罐还有第四个半缺口——**它是 CSS 藏的，不是 DOM 删的**。模板里 `.hp` 用 `position:absolute;left:-9999px` 离屏（base.tmpl:221），标签写着「Leave this field empty」。审过三个极端人群：禁 CSS 的文本浏览器会看见这个字段，但标签本身就叫「留空」；屏读器被 `aria-hidden` 挡住；键盘用户因 `tabindex="-1"` 聚焦不到。误伤面收敛到「既禁 CSS 又不看标签」的极端情况，可接受，但要知道它在那。

## 三、表单洪水与撞库：两个真实剧本

### 3.1 剧本 A：脚本灌单（洪水）

攻击者用脚本循环 POST 假询盘，目标：污染销售邮箱（通知轰炸）或把垃圾 SEO 塞进客户后台。防线逐层接住的过程：

| 攻击形态 | 哪层防线接 | 结果 |
| --- | --- | --- |
| 高速循环（>10 次/分，蜜罐不填） | ⑤ 小时闸 | 第 11 次起 429；**计数持久化，重启也躲不掉** |
| 慢速渗透（每小时 9 次） | ⑤ 日闸 30/天 | 第 31 次起 429；没有日闸时单 IP 一天 240 条——这就是日闸存在的理由 |
| 换 IP 继续灌 | CDN 层 WAF/速率限制（A6 §4.3 第 5 条：CDN 阈值高于引擎，挡洪水不挡单客） | 纵深：引擎管精准，CDN 管容量 |
| 填蜜罐绕过 | ③ 假成功，无痕 | 攻击者以为成功了 |
| 3 秒内提交 | ④ 假成功 | 同上 |
| 全部绕过后人肉填写 | ⑧ 打分 → spam 状态、不通知 | 销售邮箱安静，后台可批量清 |
| 洪水本身打带宽/CPU | 静态请求走 CDN 缓存，origin 只剩 /api；fsync 上限 600 rps（B3 9.5） | 引擎侧打不死；CDN 层 absorbs |

**监控闭环**（A6 §7.5 第 3 条的洪水告警在这里兑现）：单日询盘量超基线 3 倍告警。洪水即使没造成损失，**告警本身告诉你「有人在试」**——这是侦察情报。

### 3.2 剧本 B：撞库与枚举

「撞库」的前提是存在登录。这张攻击面清单（§1.1）里没有登录、没有会话、没有密码——**静态站没有撞库面**。攻击者能枚举的只有：

1. **URL 结构**（产品 slug）——本来就是公开的，无所谓；
2. **询盘 ID**（ULID）——但 API 没有「按 ID 查询」的公网路由，ID 只在提交响应里返回，枚举它没有对象；
3. **邮箱地址**（给 `sales@` 群发钓鱼）——这不打站点，打人。防线是 §7 的人员侧基线（DNS 三记录里 DMARC 的 `rua` 报告能看见伪造你域名的发信量）。

一句话给客户：**你的站没有「账号被撞开」这种事故剧本；你的事故剧本是「服务器被进」或「域名/CDN 账户被接管」**——两者都归 §4/§5 管。

### 3.3 剧本 C：只打不打的应用层 DoS

纯耗资源型攻击对这套架构的性价比极低：静态部分全部命中 CDN 边缘（A6 §4.1），origin 只需要回答 /api 和少量回源；引擎单进程无外部依赖，fsync 600 rps 的天花板意味着 SQLite 写满负荷也远在普通 VPS 的能力内；64 片 IP 锁保证不同 IP 完全并行、只有同 IP 串行（ratelimit.go:5–15），攻击者自己排队堵不死别人。**剩下的 DoS 风险在网络层，那是 CDN/主机商的 DDoS 防护合同管的，不是应用代码管的。**

## 四、服务器层：面最大的那一层

引擎把应用面守得很窄，于是**整台机器的安全 ≈ 服务器层的安全**。清单按「攻击者实际利用频率」排序：

### 4.1 SSH：最常见的初始入侵点

| 措施 | 说明 |
| --- | --- |
| 密钥登录、禁用密码认证 | `PasswordAuthentication no`——弱口令爆破是服务器被黑的第一大路径 |
| 禁 root 直接登录 | `PermitRootLogin no`，用普通用户 + sudo |
| fail2ban | SSH 爆破自动封禁；告警邮件接 §7 的独立通道 |
| 改端口 | 仅降噪作用（把扫描噪音降一个数量级），**不是安全措施**，别指望它 |

### 4.2 系统最小化

- **不装控制面板**。宝塔/cPanel 类面板是历史上最大的单点漏洞来源之一——为省 30 分钟的配置引入一个永久攻击面，是交付方最容易犯的错；
- 不装用不到的服务（`ss -tlnp` 应该只有 22/80/443 和回环上的 8080/9090）；
- **自动安全更新开启**（Debian/Ubuntu 的 unattended-upgrades，只自动装安全补丁）；
- 内核与 libc 的漏洞（如多年前的 dirtycow 一类）靠的从来不是你的警觉，是补丁节奏。

### 4.3 运行用户与文件权限

A6 的 systemd 单元已经埋了这部分：引擎跑在专用 `kestrel` 用户下（不是 root——**进程被攻破时的爆炸半径 = 该用户的权限**）；`ReadWritePaths` 只放行数据目录；`ip_salt` 文件 `0600`（salt.go:37）——这个文件泄露意味着库里的 IP 哈希可被离线还原（GDPR 意义上的个人数据事件，§6.5 会再遇到它）。

### 4.4 防火墙与暴露面

```
入站只开：22（限源 IP 更好）、80（仅供 ACME/跳转）、443
回环：8080（engine serve）、9090（engine admin，SSH 隧道可达）
不出站管控：引擎需要访问 Cloudflare siteverify + SMTP——默认允许即可
```

**admin/studio 永不出公网**（A6 §5.3 的铁律在安全篇的表述：引擎把下限焊死在回环绑定上，运维别亲手拆）。

### 4.5 供应链：Go 单二进制的优势与残余风险

引擎是静态编译单二进制，没有运行时依赖、没有 npm 式的依赖树——供应链面天然小。残余的两件事：

1. **Go 依赖审计**：`govulncheck ./...` 进季度巡检（附录 A 第 24 条）；
2. **二进制完整性**：引擎二进制本身在服务器上，谁改了它谁知道——配合 §5.2 的产物哈希对账一起管。

### 4.6 日志：被攻击后的取证原料

引擎把结构化日志打到 stderr（slog），**自己不落文件**——生产上由 journald 接住：

```ini
# systemd 已含；确认 journal 持久化（默认易失）：
# mkdir -p /var/log/journal && systemctl restart systemd-journald
```

- 留存策略：`SystemMaxUse=2G` + `MaxRetentionSec=90day`（90 天覆盖一次季度演练窗口）；
- **隐私注意**：引擎日志里记录的 IP 是**哈希前 12 位**（handler.go:114），明文 IP 从头到尾不落任何日志和库——这既是隐私设计，也是 §6.5 通报义务评估时的一项事实；
- 取证时最有用的三条日志：「收到询盘」（⑪，含垃圾分与来源）、「蜜罐命中，静默丢弃」、「提交过快，静默丢弃」——后两条是**攻击在场的直接证据**。

## 五、静态站怎么才会被黑：五条路径与产物完整性

### 5.1 五条现实路径

应用面守死后，剩余的入侵路径全部绕过代码：

| # | 路径 | 前置条件 | 早期信号 |
| --- | --- | --- | --- |
| 1 | **服务器被进 → 改产物/塞暗链** | SSH/依赖/面板失守 | §5.3 哈希对账报警 |
| 2 | **DNS 劫持**（注册商账户被盗） | 注册商密码弱/无 2FA/钓鱼 | 解析记录变化；A6 §2.2 的转移锁与到期告警 |
| 3 | **CDN 账户接管**（改规则、注脚本） | CDN 密码/Api token 泄露 | 页面出现陌生 `<script>` |
| 4 | **证书劫持**（CA 账户或 ACME 邮箱失守） | 证书账户失守 | CAA 记录（A6 §2.4）限定 CA 缩小爆炸半径 |
| 5 | **供应链**（构建机被进 → 产物带毒发布） | 工作机/CI 失守 | 发布门禁 + 产物哈希 |

注意五条有四条是**账户安全**问题——静态站的安全重心从代码转向了凭据。

### 5.2 产物完整性：把 V8 的体检做成自动对账

V8 判定「站点已被入侵」靠人工抽查（`site:` 搜索 + 源码搜外链）。静态站有一个 V8 用不上的独特武器——**产物是确定性的，可以哈希对账**：

```bash
# 发布时生成清单（进发布脚本，与产物同存）
cd /srv/kestrel/current && find . -type f -exec sha256sum {} \; > /srv/kestrel/manifests/$(date +%F).sha256
# 巡检时对账（附录 A 第 22 条；被人改过任何一个字节都会现形）
sha256sum -c /srv/kestrel/manifests/latest.sha256 --quiet && echo INTEGRITY-OK
```

配合 A6 §7.5 的外链扫描与 GSC 安全报告，V8 的三项判定全部常态化。

### 5.3 账户安全基线（五条路径里四条的对症药)

| 账户 | 措施 |
| --- | --- |
| 注册商 | 独立强密码 + **2FA** + 转移锁（A6 §2.2）；注册邮箱 ≠ 站点服务器上的邮箱 |
| CDN | 2FA；API token 最小权限（purge 用 purge-only token，别用全局 token 写发布脚本） |
| 服务器 | §4.1–4.4 |
| GA4/GSC | 2FA；GSC 验证方式别放在「能被 DNS 劫持连坐」的单点上（首选文件/meta 验证而非 DNS CNAME，视客户管理能力权衡） |
| 邮件 ESP | 2FA；SMTP 凭据泄露 = 有人替你发信（R4 的 DKIM 会替你签——**凭据泄露时 DKIM 照常工作，这是它防不了的事故**，要靠 ESP 的发送量告警） |

## 六、应急响应：取证 → 断源 → 恢复 → 报告

### 6.1 总原则：顺序有讲究

网上流传的直觉是「先下线再慢慢查」。对本架构有一个**特殊的排序约束**：`inquiries.db` 是唯一不可再生资产（A6 §6.1），**任何断源动作都不得危及它**。于是顺序是：

> **取证快照先行 → 断源 → 恢复 → 报告 → 复盘**。快照只要 10 分钟，先拍再动手。

静态站的另一张底牌：**干净产物始终在 git 和发布清单里**。「恢复」在很多架构里是重建数据，在这里只是「把被污染的副本换成干净副本」——这也是把「构建不可变」（A6 §5.1）当作安全属性的原因。

### 6.2 第一步：取证（目标 1 小时内完成）

| 动作 | 命令/方法 | 目的 |
| --- | --- | --- |
| 磁盘快照 | 主机商快照功能（或 `dd` 到外置盘） | 之后随便折腾，证据都在 |
| 导出询盘库 | `sqlite3 … ".backup /tmp/evidence/inquiries-$(date +%F-%H%M).db"` | 数据资产先隔离 |
| 保存日志 | `journalctl -u kestrel --since "-7 days" > /tmp/evidence/journal.log` | 时间线的原料 |
| 记录时间线 | 人写：发现途径、首个可疑时间、做过什么操作 | 报告与复盘的骨架 |
| 识别入侵点 | `last -20`、`ss -tlnp`、`crontab -l`、`~/.ssh/authorized_keys`、进程列表 | §6.3 断源的靶子 |

**别急着杀进程**——先拍快照。杀掉进程会丢内存态，也丢「攻击者是否还在线」的观察机会。

### 6.3 第二步：断源（按入侵点对症）

| 入侵点 | 断源动作 |
| --- | --- |
| 服务器被进 | 吊销所有 SSH 密钥 → 改全部密码 → 卸载可疑 crontab/进程 → 若范围不明，直接换机器重建（产物在 git，重建成本 2 小时） |
| DNS 劫持 | 注册商改密码 + 2FA → 改回正确解析（用 A6 §6.1 的 DNS 记录导出）→ 检查转移锁 |
| CDN 接管 | 改密码 + 吊销全部 API token → 清除被注入的规则 → **purge 全站缓存**（被污染的边缘副本是传染源） |
| 证书相关 | 吊销并重签（CAA 记录已限定 CA，攻击者拿不到第二家） |
| SMTP 凭据泄露 | 换密码 + 换 DKIM selector → 重发 DMARC 记录 |

### 6.4 第三步：恢复

1. 从 git 重建产物（或直接用上一个未污染的 releases 目录，symlink 秒切——A6 §6.2）；
2. **哈希对账后再上线**（§5.2 的 manifest），确认干净；
3. 换 `ip_salt`：若库或服务器被读走，旧哈希可被离线还原。**注意换盐的代价**——限流历史按 ip_hash 对账，换盐后旧记录对不上 = 限流清零一次（salt.go:18–20 注释明说过这个设计）。安全事件场景下，这个代价认；
4. purge CDN；重发一次 V9 双向验收（A4 脚本）确认询盘链路完好；
5. 核对询盘库：`engine inquiries -json` 与最近备份比对，确认没有数据被删改（攻击者删库的情况，用 §6.2 的备份恢复）。

### 6.5 第四步：报告（含法定义务）

| 对象 | 内容 | 依据/时限 |
| --- | --- | --- |
| **客户** | 事实清单：时间线、影响范围、入侵点、已采取措施、遗留风险 | 合同义务，24h 内 |
| **监管机构** | 若个人数据泄露（询盘库含姓名/邮箱/电话 = 个人数据；`ip_salt` 泄露 = 哈希可还原）且风险达到门槛，**72 小时内通报** | GDPR 第 33 条——申报主体是客户（数据控制者），**交付方提供事实清单**，是否申报由客户及其法律顾问定 |
| **数据主体** | 若风险高，还须通知受影响买家 | GDPR 第 34 条 |
| **托管商/CDN** | 滥用与事件报告 | 各家安全页面 |

这条义务链平时看不出价值，出事时是交付合同里「专业度」的分水岭——**交付方至少要能把「哪些数据在哪、是否可还原」说清楚**，本章的架构设计（哈希 IP、单一 DB、备份体系）让这份清单很短。

### 6.6 复盘

事件归档进 A6 §7.6 的运维日历：入侵点变成新的加固项（附录 A 加一行）、剧本卡（附录 B）按实战修订、季度演练增加对应场景。**没有复盘的事故会以更大的规模重演。**

## 七、V8 之外：交付给客户的安全基线

B1 只考核结果（V8 没被黑、R3 没被刷），交付方应该交的是**让结果可延续的机制**。交付包五件套：

| # | 交付物 | 内容 | 回答客户哪个问题 |
| --- | --- | --- | --- |
| 1 | **账户清单 + 2FA 覆盖表** | 域名/CDN/服务器/GA4/GSC/ESP 六类账户：归属、密码策略、2FA 状态、恢复邮箱 | 「万一你离职/失联，我们还有哪些门没锁？」 |
| 2 | **密钥与凭据轮换表** | TURNSTILE secret、SMTP、API token、ip_salt：位置、上次轮换、轮换方式 | 「密码多少年没换了」 |
| 3 | **运维日历**（A6 §7.6） | 日/周/月/季/年节奏 + 每项 owner | 「有人在管吗」（R6 原题） |
| 4 | **剧本卡**（附录 B） | 被黑/宕机/询盘断流三张卡，一页一张 | 「真出事了找谁、按什么做」 |
| 5 | **数据资产说明** | 询盘库存什么字段、存哪、备份在哪、IP 是否明文（否，哈希+盐）、删除流程 | GDPR 问询与 DSAR 的第一响应 |

第 5 件值得多说一句：**「引擎不存明文 IP、日志记哈希、单一 SQLite 库、每日备份」这套架构让客户的数据地图只有一页纸**——这是架构决策回馈合规的真实案例，也是选择单二进制 + 单库方案时没预料到的红利。

## 八、五个坑与三件别做的事

### 五个坑

1. **把 fail-open 当漏洞报**。Turnstile 网络失败放行是显式裁决（兜底在限流+人工），不是疏忽。别在巡检时「修」它——要修的是它无日志的问题（§2.4 缺口 1）。
2. **假成功造成的排查困惑**。客户问「买家说提交成功了怎么没收到」——先查蜜罐/过快日志再怀疑链路。三步排查：journald 搜 `蜜罐` / `提交过快` → `engine inquiries -json` 查库 → 查 `NotifiedAt`（A4 的 L2/L3 分层）。
3. **日志没持久化**。journald 默认易失（重启即清）——不建 `/var/log/journal`，出事时取证原料正好是空的。
4. **恢复时先格式化重装**。证据烧掉了，攻击路径永远成谜，同一个洞还会再被打。顺序永远是：快照 → 断源 → 恢复（§6.1）。
5. **演练时才第一次发现备份是空的**。A6 §6.3 的季度恢复演练是 R6 判定原题；没演练过的备份等于没有。

### 三件别做的事

1. **别把 admin/studio 暴露到公网**——引擎焊死的下限，亲手拆掉等于把整站 YAML（含 settings.compliance、全部客户内容）交给互联网。
2. **别用一套密码走天下**——§5.3 的账户里任何一个被撞库，五条入侵路径里四条同时打开。
3. **别在自己机器上保存客户密码的明文清单**——用密码管理器共享 vault；交付包第 1 件记录的是「账户与状态」，不是密码本身。
