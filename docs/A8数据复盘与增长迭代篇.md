# 外贸站开发系列 · A8 数据复盘与增长迭代篇

> **系列定位**：A6 让站活着、A7 让站安全，本篇回答上线之后**最容易被回避的问题——这站到底有没有用**。把「感觉还行」变成四段漏斗上的五个数字，把「该做点什么」变成按数据排序的三张内容清单，把月度复盘变成客户续约的固定议程。
> **适合读者**：交付完成后不知道如何证明价值的承接方；以及被客户问过「这网站每月给你交钱，带来了什么」的人。
> **读完之后你应该能**：盘点自己手上有哪几份数据、各自的盲区在哪；搭起曝光→会话→表单→落库的四段漏斗并给每段定健康值；用引擎自带的第一方归因字段回答「哪个页面带来询盘」——**不依赖 GA4**；把 GSC 的 query 报告变成内容迭代的输入；并用一页纸的月度复盘模板把数据工作变成收入。

> **口径声明（先读这一段）**
> 1. **引擎侧行为以 engine 0.13.4 源码 + 本机实测为准**。写作本章前我做了一组归因实测：向 `/api/inquiry` 提交带 `utm` 与 `source_page` 的询盘，逐字段核对落库结果（附录 C）——顺带发现一个新坑：**JSON 路径的 utm 必须是嵌套对象，扁平键会被静默丢弃**（§3.4）。
> 2. **漏斗健康值是行业经验基准，不是本仓实测**——三个交付站尚未上线，没有真实流量可测。凡属经验值的地方都明确标注「经验值」，且只做「发现异常的参照系」，不做 KPI 承诺。
> 3. **这一篇的引擎缺口比前几篇多**：无 `form_start` 埋点（漏斗中段靠推断）、无 `client_id/gclid`（GA4 与询盘库无法 join）、拒绝 Cookie 的买家在 GA4 里不可见。缺口汇总在 §7，每个都给了当下的替代做法。
> 4. 数据篇的特殊纪律：**分子分母必须同源**。GA4 的会话做分母、询盘库的询盘做分子是最常见的自欺——两套系统的口径差异足够吃掉整个转化率（§2.3）。

## 一、你有哪几份数据：四份数据源与各自的盲区

复盘质量的上限由数据源决定。这套架构里一共四份数据，先把每份「能看到什么、看不到什么」说清楚：

| 数据源 | 看到什么 | 盲区 | 留存 |
| --- | --- | --- | --- |
| **询盘库**（`inquiries.db`） | 每条询盘的来源页、referrer、UTM、国家、产品、垃圾分、通知状态——**第一方、无采样、永久** | 只看得到转化的人，看不到没转化的人 | **永久**（自主可控） |
| **GA4** | 会话数、渠道、落地页、设备、地域、`generate_lead` 转化 | **拒绝 Cookie 的买家完全不可见**（引擎是同意后才注入 gtag，base.tmpl:389–393——R1 合规的代价）；GA4 自己的采样与阈值 | 默认 14 个月 |
| **GSC** | 曝光、点击、query、覆盖状态、hreflang 报告 | 只覆盖 Google（Bing 占部分市场）；延迟 1–3 天；无转化数据 | 16 个月 |
| **服务器日志**（journald） | 每个请求的路径与状态码（IP 哈希） | 无会话概念、无用户维度 | 按留存策略 90 天（A6 §4.6） |

一个值得强调的结构性事实：**这套架构里，询盘库是唯一没有盲区的转化数据源**。GA4 的转化数会因 Cookie 拒绝而低估，GSC 压根没有转化——只有询盘库里的每一行都是真的。所以本篇的复盘框架是**以询盘库为锚、GA4 与 GSC 为两翼**，而不是常见的「以 GA4 为中心」。

### 1.1 引擎的第一方归因：每条询盘自带三组来源字段

`inquiry.js` 在提交前把三组来源数据塞进隐藏字段（inquiry.js:17–22），随询盘一起落库：

```js
setValue('source_page', location.pathname + location.search);  // 买家提交时所在页
setValue('referrer',    document.referrer || '');              // 上一跳
// utm_source / utm_medium / utm_campaign —— URL 参数原样带进
```

这意味着「哪个页面带来询盘」这个问题，`SELECT source_page, COUNT(*)` 就能回答——**不需要 GA4、不受 Cookie 同意影响、不受 14 个月数据期限约束**。实测验证见附录 C：`source_page`、`referrer`、`utm` 三组字段逐一对上。

## 二、询盘漏斗四段：每段的口径与健康值

### 2.1 四段漏斗

外贸站的转化漏斗比零售电商简单——没有购物车，终点是询盘。四段各有权威数据源：

```
① 曝光            ② 会话            ③ 表单交互         ④ 落库
GSC impression  →  GA4 sessions   →  GA4（推断）     →  inquiries 表
(你的页被看了      (有人真来了)       (有人开始填)        (询盘 100% 权威)
 多少次)
```

| 段 | 指标 | 权威源 | 口径要点 |
| --- | --- | --- | --- |
| ①→② | 曝光→点击（CTR） | GSC | 按 query 和按页面两套口径，别混 |
| ② | 会话数 | GA4 | 与询盘库无关，纯分母 |
| ②→③ | 会话→表单页到达 | GA4（表单所在页的会话） | **引擎没埋 `form_start`**，中段是推断值（§7 缺口 1） |
| ③→④ | 提交→落库 | 询盘库 | 含 `status='spam'` 的要单独拎出——垃圾流量会污染转化率 |
| ②→④ | **会话→询盘（整段转化率）** | 分子询盘库 / 分母 GA4 | ⚠️ 异源口径，见 2.3 |

### 2.2 每段的经验健康值

以下为 B2B 外贸独立站的经验基准（**经验值，非本仓实测**，用途是发现异常而非考核）：

| 段 | 低迷 | 正常 | 优秀 | 异常时先查什么 |
| --- | --- | --- | --- | --- |
| GSC CTR | <1.5% | 2–4% | >5% | 标题/description 与 query 错位（§5 改清单） |
| 会话→询盘（整段） | <0.5% | 1–3% | >4% | 先查分母口径（2.3），再查表单可用性（B1 V3） |
| 表单所在页占比 | <3% | 5–15% | — | 产品页有没有足够近的表单入口（B1 A 维） |
| spam 占比 | >50% | <30% | <15% | 限流/Turnstile 配置漂移（A7 §3.1） |

**spam 占比单独一行的原因**：垃圾询盘占比是前几篇所有防线（A7 十一道）的运行时体检指标——占比突然飙高，先怀疑防线漂移（比如 trust-proxy 被改、Turnstile 密钥掉了），而不是「生意变好」。

### 2.3 异源口径：转化率的分母陷阱

最常见的一类假异常：「GA4 里上月 2,000 会话、询盘库 30 条，转化率 1.5% 正常」vs「GA4 里 800 会话、30 条，3.8%」——**哪个对？都可能不对**。三个系统性偏差：

1. **Consent 盲区**（本架构特有）：拒绝 Cookie 的买家不进 GA4 分母，但他们的询盘进分子 → **转化率被系统性高估**。方向可预测，量级不可知；
2. **bot 过滤差异**：GA4 默认滤掉已知爬虫，服务器日志和部分直访流量不滤 → 分母偏小；
3. **会话归因差异**：GA4 的归因模型（最后非直接点击）会把「Google 搜品牌名回来」的会话记给 organic，而买家实际两周前看过你的 LinkedIn 广告。

对策不是「找一个完美数字」，是**固定口径、纵向比较**：每月同一天、同一套 SQL（附录 B.3）、同样的分母来源出数——趋势比绝对值可信。

## 三、归因：哪个页面带来询盘

### 3.1 三层归因体系

| 层 | 数据 | 回答的问题 | 可信度 |
| --- | --- | --- | --- |
| **第一层：询盘库 `source_page`** | 每条询盘的提交时所在页 | 「询盘从哪个页面产生」 | ★★★ 第一方、逐条、永久（§1.1 实测） |
| **第二层：询盘库 `utm_*`** | URL 上的投放参数 | 「这条/这批询盘来自哪次投放」 | ★★★ 前提是外链带 utm（§3.3） |
| **第三层：GA4 转化路径** | `generate_lead` 事件 + 转化探索 | 「从会话到表单的完整路径」 | ★★ 有 Consent 盲区 |

第三层有一个结构性的坑要先说：**`generate_lead` 打在致谢页（thanks.tmpl），参数只有 `form_id:'inquiry'`**——它不知道是哪条询盘、来自哪个页面。所以 GA4 能告诉你「今天有 3 个转化」，但「这 3 个是询盘库里的哪 3 条」**答不了**：引擎不存 `client_id`（grep 全库 0 命中），两套系统没有 join 键（A4 遗留缺口在本篇成为核心痛点）。

### 3.2 第一层怎么用：一条 SQL

```sql
-- 上月询盘按来源页聚合（附录 B.1 有完整版）
SELECT source_page, COUNT(*) AS n
FROM inquiry
WHERE created_at >= '2026-11-01' AND status != 'spam'
GROUP BY source_page ORDER BY n DESC;
```

读这张表的方式比写它重要，三个动作：

1. **头部集中度**：前 3 个页面占询盘多少？外贸站通常 60–80% 集中在「产品页 + 联系页」——偏离这个形状（比如全落在首页）通常意味着产品页缺近场表单或入口（B1 A 维自查）；
2. **`source_page` 是 `/thank-you` 或空**：噪音信号——303 跳转链或无 JS 提交的表单，量应该很小，量大了要查 inquiry.js 是否正常加载；
3. **按语言切一刀**（`lang` 字段现成）：en 和 zh 的头部页面不同是常态，混在一起看会得出错误结论。

### 3.3 第二层怎么用：utm 纪律

utm 字段引擎侧已备好落库通道，**价值取决于纪律**：所有外部投放/外联链接统一带 `utm_source/utm_medium/utm_campaign`（哪怕只是 LinkedIn 帖子和 WhatsApp 群发）。没有 utm 的渠道在第二层不可见——那时只能靠第三层 GA4 或 referrer 域名近似。

命名纪律一句话：**小写、下划线、campaign 带日期**（`uav-90d` 不是 `UAV 90D`）——utm 是字符串精确匹配，大小写混用会让同一渠道在报表里裂成三行。

### 3.4 本轮实测发现的新坑：JSON 路径的 utm 必须嵌套

附录 C 的实测过程本身抓到一个此前无人踩过的坑：向 `/api/inquiry` 发 JSON，**扁平键 `utm_source` 会被静默丢弃，必须发嵌套对象 `"utm":{"source":…}`**（parseJSON 只认嵌套 map，input.go:174–182；扁平键只在表单编码路径 parseForm 生效）。三个后果：

1. **用 curl/脚本直连 API 集成的人**（A6 的探针脚本就是）——utm 静默丢失，归因数据缺一列且无任何报错；
2. 正常页面表单不受影响（inquiry.js 发的就是嵌套格式）；
3. 稳妥做法：集成脚本统一走 `application/x-www-form-urlencoded`（扁平键），或发嵌套 JSON。

这个坑已记入 §7 缺口 4。**「静默丢弃」在归因场景比在提交场景更伤**——提交失败你会知道，归因字段丢了报表只是空着。

## 四、GSC：90 天里每周看什么

GSC 是唯一能看到「Google 怎么看你」的窗口。90 天里它提供三类信号：

### 4.1 覆盖报告（每周，5 分钟）

- **收录曲线**：sitemap 提交后 2–4 周内应持续上升；停滞或回落先查 GSC 覆盖错误详情（E6 的判定源）；
- **软 404 / 重定向错误**：出现即处理——这是 E5「没有死路」的线上实证；
- **hreflang 报告**：A5 的构建期校验保证了发送侧正确，GSC 报告的是 Google 接收侧的反馈，两侧对上才算闭环。

### 4.2 Query 报告（每月，内容迭代的原料）

按 query 看两件事：

1. **有曝光、无点击的词**——你的页在搜索结果里出现过但没人点：标题与搜索意图错位，进 §5 的「改」清单；
2. **有曝光但站点没有对应页的词**——市场在问你没有答案的问题，进 §5 的「加」清单。这是**内容路线图的免费情报**，比任何关键词工具都真实（真实买家在真实搜索）。

### 4.3 第 90 天的里程碑检查

上线 90 天做一次正式对账（对应 B1 E6 的判定时点）：核心页（首页/主力产品/联系）是否已收录、覆盖错误是否为 0、品牌词搜索是否首位、`llms.txt` 与结构化数据在 Rich Results Test 是否正常。未达标的每一项都该有明确的下一步与责任人。

## 五、内容迭代：数据说话的三张清单

数据不复盘就是硬盘占用。每月从数据生成三张清单，迭代才有依据：

### 5.1 「加」清单（来自 GSC query 与询盘库的空白）

| 信号 | 动作 |
| --- | --- |
| GSC 有曝光、站点无对应页的 query（§4.2） | 新页面/新 FAQ——B1 C 维的 Q13 十三问是现成的内容框架 |
| 询盘库 `message` 里反复出现的产品/规格提问 | FAQ 或产品页参数段补充——**买家自己写的需求书** |
| `utm` 报表里某个 campaign 的落地页质量差（会话高询盘低） | 该 campaign 专属落地页 |

### 5.2 「改」清单（按 ROI 排序）

| 信号 | 优先级 | 动作 |
| --- | --- | --- |
| 高曝光 + 低 CTR（GSC） | 最高——流量在门口流失 | 改 title/description：把 query 的原词放进标题 |
| 高会话 + 低表单到达（GA4 + 询盘库） | 高 | 页面内容问题：用 B1 九问自查（有没有价格锚点/交期/验厂证据） |
| 高表单开始 + 低提交 | 高——A4 的字段流失数据在这里上线复验 | 字段砍削 + 错误提示优化（A4 §3） |
| 高询盘 + 低产品质量（spam 边缘分） | 中 | 表单蜜罐/时间阈值微调，别动限流（A7 §3.1） |

### 5.3 「删/合并」清单（最克制的一张）

| 信号 | 动作 | 克制条款 |
| --- | --- | --- |
| 连续 90 天 0 曝光 + 0 会话的旧页 | 候选删除/合并 | **先排除**：新页（<90 天）、季节性页、法务必需页 |
| 内容重叠、互相抢排名的两页 | 合并 + 301 | 合并对象必须是同搜索意图（A5 §5 重复内容陷阱的正解） |
| 低质量外链指向的垃圾页 | 不存在——静态站没有用户生成页 | （这一行是静态站的红利：零售 CMS 的「垃圾 UGC 页」问题在这里结构性不存在） |

**每张清单的执行都要过 B1 复评**：改版后重跑构建门禁（0 错 0 警）+ Lighthouse 四项（0.13.0 的教训：内容迭代是可访问性回退的高发期）。

## 六、月度复盘与第一个 90 天

### 6.1 第一个 90 天的里程碑

| 时点 | 目标 | 未达标的动作 |
| --- | --- | --- |
| 第 7 天 | GSC 验证完成、sitemap 已提交、V9 双向验收通过 | —（这是 A6 附录 A 的收尾） |
| 第 30 天 | 首批页面开始出现在覆盖报告；GA4 有真实会话；询盘库有首批真实询盘 | 检查 robots/收录障碍；确认 GA4 数据流配置（A6 §8 第 5 项） |
| 第 60 天 | 覆盖错误 0；首个完整月度复盘跑完；三张清单初版 | 覆盖错误逐条处理 |
| **第 90 天** | **正式对账（§4.3）+ 复盘会**：四段漏斗有基线、归因报表能出、下季度内容路线图获批 | 任何一段无数据 = 回查该段的数据链路（不是没流量，是没数据） |

### 6.2 月度复盘会：一页纸，四个问题

复盘会的全部内容（模板见附录 A）：

1. **漏斗四段各是什么数？**（同口径 SQL，附录 B）
2. **头部页面还是它们吗？**（source_page 聚合的月度对比）
3. **上月的行动验证了吗？**（上月清单的每一项：做了→数据动没动）
4. **下月做哪三件事？**（不超过三件——内容迭代的最大敌人是清单过长没有一件做完）

**这条节奏本身就是 B1 R5/R6 的判定项**（「能回答哪个页面带来询盘」「月度复盘节奏与责任人」）——数据工作做完，评分表上两个格子自动有了证据。

### 6.3 复盘即续约

对交付方，这个会议的角色超出了数据：**它是每月一次的价值陈述**。四段漏斗的数字、头部页面的变化、上轮迭代的因果，都是「这站值得继续投入」的证据链。反过来，**没有月度复盘的交付关系，续约时只剩「我觉得还行」**——这就是为什么把复盘会放进交付合同（B6 的交付门禁）而不是当增值服务。

## 七、引擎与流程缺口汇总

| # | 缺口 | 影响 | 当下替代 |
| --- | --- | --- | --- |
| 1 | **无 `form_start` 埋点**（GA4 里只有 `generate_lead`，没有「表单开始」事件） | 漏斗中段（②→③）只能用「表单所在页的会话数」推断，字段流失分析（A4 §3）在线上无法直接复验 | GA4 自定义事件要自己加代码；或将推断值标注为推断 |
| 2 | **无 `client_id`/`gclid`**（grep 全库 0 命中，A4 遗留） | GA4 会话与询盘库无法 join，「这次会话 = 这条询盘」不可答；广告 ROI 只能靠 utm 对账近似 | utm 纪律（§3.3）+ 致谢页时间戳与 GA4 转化时间对齐 |
| 3 | **拒绝 Cookie = GA4 盲区** | 分母缺失、转化率高估（§2.3）；EEA 流量占比高的站偏差更大 | 接受并固定口径；询盘库作为真值锚 |
| 4 | **JSON API 的 utm 扁平键静默丢弃**（§3.4，本轮实测新发现） | 直连 API 的集成（监控探针、CRM 同步）丢归因数据且无报错 | 集成统一用表单编码或嵌套 JSON |
| 5 | GA4 数据 14 个月期限 vs 询盘库永久 | 两套数据的可回溯窗口不同——年度对比只能对询盘侧 | 复盘 SQL 从第一天就跑询盘库口径（附录 B.1） |

缺口 1、2 是同一根因的两面：**引擎在「不依赖第三方追踪」上做得很彻底（隐私上加分），代价是放弃了两套系统的精确对齐**。这是架构裁决不是疏忽，但要知道它买了一边、卖了另一边。

## 八、五个坑与三件别做的事

### 五个坑

1. **异源转化率当真值**。GA4 分母 × 询盘库分子天然带 Consent 盲区——固定口径、看趋势，别把 1.5% 和 3.8% 的差异当业务事实（§2.3）。
2. **spam 污染转化率**。垃圾询盘进分子会让「转化率上升」实为「被刷」——所有转化口径先 `status != 'spam'`，spam 占比单独监控（§2.2）。
3. **utm 大小写混用**。`Bing/bing/BING` 在报表里是三个渠道——第一天的命名纪律决定第 90 天的报表能不能看（§3.3）。
4. **「删页」清单一上来就执行**。0 流量页先排除新页与季节性页，删前看 90 天——合并错页面会连排名一起删掉（§5.3）。
5. **复盘会开成汇报会**。只有数字没有行动的复盘是成本；每月三件带 owner 的事，下月先验证上月（§6.2）。

### 三件别做的事

1. **别用 GA4 的转化数对账询盘库**。两个数永远对不齐（盲区+去重+时区），对齐失败会消耗所有人对数据的信任——各自口径、各自用途。
2. **别在拿到基线前做改版**。没有 90 天基线，「改了之后变好」无法证明——先让数据跑起来，再动内容。
3. **别把客户数据截图发进公开渠道**。询盘库是个人数据（GDPR 意义），复盘物料里的邮箱/电话先脱敏——A7 的数据资产说明在这里兑现。

## 附录 B：复盘 SQL 与脚本

### B.1 归因头部报表（每月复盘主表）

```bash
#!/usr/bin/env bash
# attribution-report.sh —— 来源页 Top 10 + 渠道汇总（询盘库口径，无盲区）
DB=/srv/kestrel/data/inquiries.db
sqlite3 -header -column "$DB" "
SELECT source_page, COUNT(*) n FROM inquiry
WHERE created_at >= date('now','start of month','-1 month')
  AND created_at <  date('now','start of month')
  AND status != 'spam'
GROUP BY source_page ORDER BY n DESC LIMIT 10;
SELECT utm_source, utm_medium, COUNT(*) n FROM inquiry
WHERE created_at >= date('now','start of month','-1 month')
  AND created_at <  date('now','start of month')
  AND status != 'spam'
GROUP BY utm_source, utm_medium ORDER BY n DESC;"
```

### B.2 spam 占比（防线体检）

```bash
sqlite3 "$DB" "
SELECT status, ROUND(100.0*COUNT(*)/(SELECT COUNT(*) FROM inquiry
  WHERE created_at >= date('now','-30 days')),1) pct
FROM inquiry WHERE created_at >= date('now','-30 days')
GROUP BY status;"
```

### B.3 漏斗口径说明（固定下来，每月同版）

```text
曝光→CTR：GSC 页面报告，全站合计
会话数：GA4 报告库 → 会话（声明 Consent 盲区）
表单所在页占比：GA4 落地页/路径中表单页的会话 ÷ 总会话（推断值）
询盘数：SELECT COUNT(*) … status != 'spam'（询盘库，权威）
整段转化率：询盘数 ÷ 会话数（异源口径，仅看趋势）
```
