# 外贸站开发系列 · A9 维护合同与长期客户成功篇

> **系列定位**：A1–A8 解决「把一个站做出来并让它持续活着」；本篇解决最后一块——**让做站这件事本身可持续**。交付日是合同关系的起点而不是终点：维护合同把 A6 的运维日历、A7 的剧本卡、A8 的复盘模板从「交付方的好习惯」升格为「有对价、有 SLA、有退出机制的契约义务」。
> **适合读者**：刚交付第一个单、正被问「以后怎么办」的承接方；以及想把一次性项目变成稳定现金流的独立开发者。
> **读完之后你应该能**：说清「不维护的站会怎样」并用 B1 评分讲出衰减机制；把维护服务写成一张合同条款清单和一份分档价目结构；算清多站并管时第 N 单的边际成本；准备好自己的单点风险预案；并能把一次交付体面地交接出去——**收官篇的承诺是：你随时可以离开，但你一直被需要。**

> **口径声明（先读这一段）**
> 1. 本篇是**流程与商业篇**：引擎行为不再新做实弹，全部引用 A6–A8 的已取证结论与 B6 的既有 SOP；涉及 B6 的条目注明章节号（B6 止于「S6 交付与移交」，本篇即它语义上的 S7）。
> 2. **定价不给绝对数**。工时账可以按运维日历逐项推导（§4.1），但费率随市场、地域、客户体量浮动——给结构不给价格，是本篇的诚实边界。
> 3. **「评分衰减」是推演不是实测**：三个交付站尚未上线，没有 12 个月的衰减数据可测。推演逻辑全部锚定 B1 的具体条目，你可以逐条质疑（§1.2）。
> 4. 收官篇附带 A 系列总览与阅读路径（§八后），A1–A8 的每一篇在此归位。

## 一、交付时点值 vs 时间函数：不维护会怎样

### 1.1 交付的是时点值，客户买的是时间函数

B6 交付门禁出的评分（当前三站 96 / 94 / 94）是**交付日的时点值**。客户真正买的不是这个快照，是未来 12–36 个月里「站一直处于可用、可信、可被搜到的状态」——一个时间函数。两件事的差值，就是维护合同的对价基础：

> **交付评分 − 第 N 月实际状态 = 维护不足的代价。**

### 1.2 衰减推演：12 个月不维护，分数怎么掉

逐条锚定 B1 的衰减机制（**推演，非实测**）：

| B1 条目 | 衰减机制 | 12 个月不维护的典型结局 |
| --- | --- | --- |
| **证书相关（Veto 级连带）** | 90 天证书靠自动续期，续期失败无告警即过期 | 过期 → 浏览器拒绝连接 → V3 移动不可用、V9 通道全灭 → **一次到期即可从 94 掉到「不合格」** |
| **V9 询盘通道** | DNS 记录漂移、SMTP 凭据过期、ESP 政策变更、收件箱规则被清 | 双向验证无人跑 → 断流数周后才被买家发现（A6 §7.1 答案①：沉默流失） |
| **E6 索引健康** | 改内容引入死链、GSC 覆盖错误无人处理 | 收录曲线停滞回落，曝光下滑 |
| **E5 死链 / E1 TDK** | 内容更新不规范（B6 10.6 的「内容错」没有走构建门禁） | 死链与重复 TDK 缓慢累积 |
| **R4 邮件三记录** | 域名续费、DNS 服务商迁移、DKIM 密钥轮换没人管 | 三记录失效 → 询盘进垃圾箱 → R4 直接不过 |
| **R5/R6** | 复盘会与运维日历没有 owner 就是没跑 | 这两条**交付时就不过**——它们本来就是维护合同义务的评分化 |

两条结论：

1. **衰减不是线性的，是断崖式的**——大多数字段缓慢掉 1–2 分，但证书/域名/邮件三个「漂移点」任何一个失效都是 Veto 级跳崖。维护合同的本质是**给断崖点装告警**（A6 五层监控的 L1–L4 恰好覆盖全部断崖点——这不是巧合，A6 就是照着这张衰减表设计的）；
2. **R5/R6 两条评分项只有签了维护合同才可能通过**。B1 在结构上就区分了「交付能拿的分」和「运营才拿的分」——评分体系和商业模式是自洽的。

## 二、维护合同七要素

把 A6–A8 的全部交付物合同化，一份维护合同要有七个要素：

| # | 要素 | 内容 | 引用的既有交付物 |
| --- | --- | --- | --- |
| 1 | **服务范围** | 服务目录逐项列明（§3）——**写进附件，正文只写「以附件 A 目录为准」** | A6 §7.6 运维日历 |
| 2 | **响应 SLA** | 分级响应时间 + 升级路径（§3） | A7 剧本卡三张 |
| 3 | **例行节奏** | 月度复盘会（固定议程、固定出数口径）+ 季度巡检 | A8 附录 A、B、A6 附录 A |
| 4 | **变更管理** | 内容更新走什么通道（studio/admin + 构建门禁）、改版谁审、紧急变更的授权 | B6 10.3、10.6 |
| 5 | **数据与知识产权** | 询盘数据归客户（第一方数据是客户的资产）；内容源 git 归属；引擎代码许可边界；**盐文件与备份的所有权** | A6 §6.1、A7 §7 第 5 件 |
| 6 | **安全与通报** | 安全事件的事实清单义务（24h 内交客户）、GDPR 33/34 条的角色分工（控制者是客户，处理者是交付方） | A7 §6.5 |
| 7 | **退出条款** | 交接包内容、交接期、退出后 30 天内数据可用性承诺（§7） | A7 §7 五件套 |

两条起草纪律（对应 B6 §3.4「不要在销售阶段埋雷」的维护版）：

- **范围用白名单不用黑名单**：「包含每周 GSC 检查」是可执行的；「不包含大改版」留不住边界感——客户读不到你**会**做什么；
- **一切承诺指向附件里的可验证动作**：SLA 写「P1 1 小时响应」的前提是 A6 的 L1 探针真的在跑——**合同义务必须能被监控数据自证**，否则签约即违约。

## 三、服务目录与 SLA：把承诺写成表格

### 3.1 服务目录：运维日历的合同化

A6 §7.6 的日历逐项变成目录行，每行带频次与工时（这是 §4 定价的原料）：

| 频次 | 目录项 | 来源 | 月均工时（推演） |
| --- | --- | --- | --- |
| 每分钟（自动） | L1 探活 + 告警值班 | A6 §7.2 | 摊销 0.5h |
| 每小时（自动） | L2 询盘链路双向探针 | A6 §7.2 | 摊销 0.2h |
| 每日（自动） | L3 到期检查、DB 备份 + CSV 导出 | A6 §7.2 | 摊销 0.3h |
| 每周 | L4 邮件测试信、L5 GSC 安全报告 + 外链扫描 | A6 §7.2、A7 §7.5 | 0.5h × 4.3 ≈ 2.2h |
| 每月 | 复盘会（四问 + 一页纸）+ 内容小迭代 | A8 §6.2 | 2–3h |
| 每季 | 恢复演练、死链巡检、Lighthouse 重测、哈希对账、govulncheck | A6 §6.3、A7 附录 A | 4h ÷ 3 ≈ 1.4h |
| 每年 | 域名/证书/密钥复审、DR 演练 | A6 §7.6 | 0.5h |
| 事件驱动 | P1–P4 响应（§3.2） | A7 剧本卡 | 按实际，P1/P2 应有月度预算 |

基础托管合计约 **6–9 工时/月**（推演值，作为结构与量级参考）。这个数就是「维护费至少要覆盖什么」的物理下限——**低于这个工时支撑范围的价格，等于承诺了做不到的节奏**。

### 3.2 SLA 分级（模板见附录 B）

| 级 | 定义 | 对应剧本卡 | 首响 | 目标恢复 | 月度预算 |
| --- | --- | --- | --- | --- | --- |
| P1 | 站不可用 / 询盘双向断 | 卡一、卡三 | 1h | 4h | 含在月费 |
| P2 | 询盘单向断 / 性能劣化 / 安全告警 | 卡二、卡三 | 4h | 24h | 含在月费 |
| P3 | 内容更新（每次 ≤N 页） | — | 1 个工作日 | 2 个工作日 | 目录内含次数 |
| P4 | 咨询与小改动 | — | 2 个工作日 | 按约 | 超出按次计 |

两处容易签出问题的细节：

- **P3 的「≤N 页」必须写死**。「内容更新」没有页数上限等于把整个内容运营外包给了你——那是一份不同的合同、不同的价；
- **P1/P2 的恢复目标要写「目标」不写「保证」**——恢复取决于攻击面（A7）与第三方（DNS/CDN/ESP），过度承诺等于把第三方故障背在自己账上。

## 四、定价的三个锚点

### 4.1 成本锚：工时账

§3.1 的目录工时 × 你的费率 = 成本下限。这条锚回答「低于多少不能接」。

### 4.2 价值锚：询盘数据的货币化

A8 的复盘给维护费提供价值叙事：一页纸上的「本月 X 条询盘、头部页面 Y」可以换算成客户的成交额。**维护费占单条询盘价值的比例**是客户感知的标尺——当每月维护费 < 半条询盘的毛利，这个价格在客户的财务表里是「保险费」而不是「成本」。这就是为什么 A8 的复盘会既是服务又是定价工具：**没有数据的价值锚，维护费永远在和「找个大学生兼职看看」竞价**。

### 4.3 结构锚：三档分法（模板见附录 B）

| 档 | 内容 | 对应章节 |
| --- | --- | --- |
| **托管级** | 监控五层 + 备份 + P1/P2 响应 + 季度巡检。**站活着** | A6、A7 |
| **标准级** | 托管级 + 月度复盘 + P3 内容更新（限次）。**站活着且有人看数据** | + A8 §6 |
| **增长级** | 标准级 + 内容迭代三张清单的执行 + B1 季度复评。**站越来越好** | + A8 §5、B2 |

三档的设计逻辑：**正好对应「站挂没挂 / 有没有人在看 / 有没有在变好」三个客户能感知的层次**。报价时从增长级讲起、按预算落档——先讲价值再谈价格的顺序，与 B6 §3.4 的销售纪律同源。

## 五、多站并管：第 N 单的边际成本

### 5.1 引擎架构的复利已经开始兑现

已交付三站的事实账（B5/CHANGELOG 可查）：

| 事实 | 出处 | 边际成本意义 |
| --- | --- | --- |
| leafworks 交付**引擎 0 改动** | 0.13.3 换皮记录 | 第 2 单起，引擎工时 ≈ 0 |
| kestrel/leafworks 换皮**零 Go 改动**（预置皮肤文件名发现） | 0.13.3/0.13.4 | 换观感不动代码 |
| 引擎缺陷 17 条全部以「边界白名单 / fail-fast」收口 | B6 10.6 | **一次修复全站受益**——多站并管让每个缺陷的修复价值 ×N |
| 三站同一套预置皮肤、同一套监控脚本、同一套复盘 SQL | A6–A8 | 运维资产全部可参数化复用 |

**这就是维护业务的结构性优势**：单站交付方卖工时，引擎交付方卖「已经修过 17 个坑的平台」。第 N 单的报价里，引擎与流程资产的摊销是真实成本优势，不是话术。

### 5.2 并管的工程形态

| 资产 | 并管形态 |
| --- | --- |
| 交付流水线 | B6 S2–S6 已是 SOP；每新站 = 按章执行，产出同一形态的 client 目录 |
| 基础设施配置 | `infra` repo：nginx/systemd 模板参数化（站点名、端口、域名三变量），新站部署 = 填三个变量 |
| 监控 | 同一监控服务注册多站点探针；告警通道带站名（A6 §7.3 的两人原则不变） |
| 备份 | 同一 cron 模式 × N；恢复演练按季度轮一站（第 N 季度练第 N 站，一年内每站至少练一遍） |
| 复盘 | A8 附录 B 的 SQL 已按 `inquiry` 表结构通用——换 DB 路径即用 |
| 引擎演进 | B6 10.6 纪律：所有站的共性缺陷回灌引擎，版本升级全站重建回归（0 错 0 警 + 测试全绿） |

### 5.3 并管的两条红线

1. **一份数据库一份备份，不共享**——多站共用备份目录是恢复事故的经典来源；
2. **告警必须带站名、复盘必须按站分页**——并管后最大的质量滑坡是「把 A 站的事当成 B 站的事」，一页纸模板（A8 附录 A）的站名栏不是装饰。

## 六、角色转换与你自己的单点风险

### 6.1 从「做站的」到「管站的」

四个月里的角色迁移（对应本系列各篇）：

| 阶段 | 角色 | 证明物 |
| --- | --- | --- |
| 交付前 | 供应商（按单计价） | B6 的 S0–S5 |
| 交付日 | 承包商（门禁验收） | B2 评分 + 60 分钟对账单 |
| 维护期 | 运营方（按月计价） | SLA 履约记录 + 复盘一页纸 |
| 长期 | 技术伙伴（参与客户的数字决策） | 增长级合同 + 季度复评报告 |

伙伴位置不是自称的，是**复盘会上连续 6 次带着数据和行动清单出现**之后客户给的。A8 §6.3 的逻辑在商业侧的镜像：复盘会同时是价值陈述会。

### 6.2 你的 bus factor：单人交付方的最大风险

客户问过「如果你病了/失联了怎么办」的时候，正确的答案不是「不会的」，是一份文档化的预案：

1. **一切皆文档**：B6 10.1 的交付 README 8 项 + A6/A7/A8 的全部脚本与模板，本来就在 repo 里——**单人风险的控制手段和多人团队是同一套**，这也是为什么前八篇坚持「文中每个数字可复现」；
2. **协作者预案**：至少一位知道 repo 在哪、监控在哪、密码 vault 在哪的同行（保密协议下）；不用每天参与，但要能在 48 小时内接手 P1；
3. **客户侧备份知情**：客户至少知道备份与数据资产的存在（A7 §7 第 5 件的交付物之一）——这不是泄露风险，是**最坏情况下客户自救的唯一线索**；
4. 引擎本身的开放性是冗余：Go 单二进制、模块结构在 B3 全文有设计文档——接手者的学习成本被 A/B 系列文档体系压到了「读完 B3 + B6 + A6–A8」。

## 七、退出与交接：合同的另一半

合同总要结束（客户换方向、你换赛道、或仅仅是到期不续）。**退出条款的质量决定这段关系的最后一印象**——而行业口碑在小圈子里传得比想象中快。

### 7.1 交接包（附录 C 有完整清单）

以 A7 §7 五件套 + B6 10.1 交付 README 为基础，退出时追加：

1. **全部账户的归属确认表**：域名/CDN/服务器/GA4/GSC/ESP 逐项确认转移至客户名下（域名尤其——A6 §2.2 铁律 1「域名永远在客户名下」在这里被验证）；
2. **密码 vault 转移**：共享 vault 整体移交 + 双方确认，交付方侧副本销毁的书面记录；
3. **数据终局交付**：`inquiries.db` + 全部历史备份 + CSV 导出的清单化移交（A6 §6.4 的格式无关出口在这里兑现价值）；
4. **运行状态快照**：交接日当天的监控基线、最近一次复盘、已知问题清单（含未修复项与原因）；
5. **30 天护航期**：交接后 30 天内的有限咨询（写进退出条款）——既保护客户，也保护你的口碑。

### 7.2 交接的验收动作

和交付一样，交接也要有门禁：**客户侧用交接包独立完成一次「恢复 + 探针 + 询盘双向验收」**（A6 附录 A 的 26–30 条）。客户做不出来 = 交接没完成——这条写进退出条款，避免「签了交接确认书但客户其实什么都不知道」的烂尾。

## 八、五个坑与三件别做的事

### 五个坑

1. **把维护当赠品**。「先免费维护三个月」是定价锚点自毁——客户对免费服务的估值是零，转正时会有强烈的价格反弹。要么写进首单总价，要么从第一天就是收费服务。
2. **SLA 承诺了第三方的故障**。DNS/CDN/ESP 的宕机不是你的恢复义务（§3.2 的「目标」措辞），但**发现它、告诉你、启动切换**是——边界要在签约时讲透。
3. **多站共享一个备份目录 / 一条告警通道**。恢复时拿错库、告警时分不清站——并管的红线（§5.3）。
4. **交接包里有密码明文**。交接用 vault 整体转移，不用 Excel 发密码——A7 §8 的纪律在退场时同样有效。
5. **续约靠临时想起来**。维护合同写自动续约 + 提前 60 天的续约对话（对话素材就是 A8 复盘）——沉默的合同会在沉默中到期。

### 三件别做的事

1. **别接没有对价的「帮忙看一下」**。每一次免费响应都在向客户证明维护服务没有价值；要用 P4 档把小事合法地计价。
2. **别让客户碰不属于自己的账户**。域名/服务器账户在客户名下但**凭据由你保管**是常态；但询盘数据（客户的资产）你必须能随时导出给他——数据所有权和凭据保管权是两回事，混起来两头都输。
3. **别在复盘会上承诺数据没支持的结论**。「这页该改因为我觉得」在复盘会上没有位置——A8 的纪律（每个建议锚定一个信号）是交付方专业度的日常体现。
