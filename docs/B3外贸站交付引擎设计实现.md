## 一、一句话定义与设计目标

> **输入一份客户资料，输出一个可上线、合规、多语言、能收询盘的外贸站。**

不是 CMS，是**交付流水线**。CMS 只是流水线上的一个零件。

真问题不是「缺一个 CMS」，而是每个项目都在重复同一批劳动：重写 12 个区块、重配 hreflang/sitemap/Schema、重接询盘与反垃圾、重做多语言目录。**真正的对手不是 Strapi，是「复制上一个项目的文件夹」。**

引擎的价值只有一个可衡量形式：**同类站点，交付工时下降 80%。**

> 由此推出一条贯穿全篇的硬约束：**凡是「每个站都要做一次」的事，必须被引擎做掉；凡是「每个站都不一样」的事，才留给人工。** 判断一个功能该不该做，先问它属于哪一类。

**与 B1 的关系**：B1 的七维（可达与渠道 / 内容 / 贸易信息 / 信任证据 / 技术 SEO / 性能移动 / 合规可运营，v2.0）就是「每个站都要做一次」的事的清单。**引擎欠账 = B1 维度里仍需人工补的部分**——本篇第十三、十四节专门处理这笔账。

## 二、产品边界与设计原则

| 是 | 不是 |
| --- | --- |
| 面向**询盘型 B2B 外贸站**的交付工具 | 通用 CMS（不与 Strapi / Payload 比功能广度） |
| **有明确主张**（内置最佳实践，不给你选） | 高度可配置的平台（配置项越多，交付越慢） |
| 静态优先、可长期不维护 | 需要持续运维的动态系统 |
| 开发者工具（CLI + 配置文件优先） | 可视化建站工具 |
| 开源（获客渠道） | 商业 SaaS |

### 2.1 用户与场景（三个阶段，顺序不可颠倒）

| 阶段 | 用户 | 验收标准 | 现状 |
| --- | --- | --- | --- |
| **P0（v0.1）** | **你自己，唯一用户** | 用它交付第 2 个真实客户站，工时不超 12 小时 | ✅ 已完成三次（Ridgeway / Kestrel / Leafworks） |
| **P1（v0.3）** | 1–2 位同行开发者 | 看文档半小时内能起一个站 | ✅ M4 实测 `new → build` 1 秒出 14 页站，操作见 B4 |
| **明确不做** | 非技术终端用户自助建站 | 那是 Wix / Shopify 的地盘，不碰 | — |

**这个顺序很重要**：先服务自己，产品自然会「窄而深」；先想服务大众，产品必然「宽而浅」，最后谁都不要。P0 阶段唯一要证明的事是「同一个引擎能交付第二个不同行业的站」——这也是 M2 的验收标准。

### 2.2 五条设计原则（后续所有取舍都从这里推）

1. **有明确主张**：该有的区块、hreflang、询盘字段引擎直接给定，不允许配置掉。**灵活性是这个产品的敌人**——每多一个开关，就多一种要维护的组合。
2. **静态优先**：除了 `/api/inquiry`，一切能静态化的绝不动态。静态站没有运行时补救机会，所以校验必须在构建期发生。
3. **文件即数据**：内容存 YAML，Git 就是版本历史；加客户 = 加目录。
4. **静默失败零容忍**：错误被吞处，最终都会以十倍成本在下游现形。B5 缺陷档案里的 1/2/3/4/5/15/16 全是这一类——**没有任何一条是靠「多加小心」避免的，都是靠白名单或 fail-fast 校验堵住的**。
5. **不重复造零件**：主题只改 token，不改结构；布局变体只换排版密度，不改信息架构。

## 三、架构总览

### 3.1 三层结构

```text
┌─────────────────────────────────────────────────┐
│ 内容层（文件，Git 管理）                          │
│   settings / pages / products / categories      │
│   scenarios / certificates / cases / media      │
│              ↓ 构建期读取                         │
├─────────────────────────────────────────────────┤
│ 模型层（Go struct，编译期确定）                   │
│   字段定义 + i18n 标记 + 校验规则 + 关系解析      │
│              ↓ 渲染                              │
├─────────────────────────────────────────────────┤
│ 输出层                                           │
│   静态站（HTML/CSS/JS/图片/sitemap/JSON-LD）      │
│   运行时 API（/api/inquiry → SQLite）            │
└─────────────────────────────────────────────────┘
```

### 3.2 ADR-001：内容存文件，不存数据库

**决策**：内容 100% 存文件，数据库只存询盘。

| 备选 | 取舍 |
| --- | --- |
| A. 内容存数据库（Strapi 式） | 未来加后台无需改存储，但 v0.1 无后台，收益为零 |
| **B. 内容存文件 + Git（选它）** | 零迁移、天然版本化、可 diff 可 review、改内容不需服务在跑 |
| C. 文件 + 数据库缓存 | 双写一致性复杂，收益不明 |

**接受的代价**：客户不能自助编辑（已用 `engine studio` 补上）；几千 SKU 时构建变慢（真到 5000 SKU 是 Headless 场景，不在定位内）；多站点共享内容需另做 include（P2）。

> **关键设计：存储换了，模型不换。** 第十一节的 Loader 适配器让「文件 → 数据库」只换读层，上层零改动。这是 ADR-001 不阻塞未来的原因。

### 3.3 技术栈

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 后端 / 构建 | **Go**（net/http，无框架），SQLite 纯 Go 驱动 | 单二进制、无 cgo、无 npm 供应链；客户三年不升级也能跑 |
| 后台 UI | 服务端渲染 HTML + 少量原生 JS | 不为后台引入前端构建链；后台是薄壳，不是产品 |
| 输出 | 纯静态 HTML/CSS/JS | SEO、速度、抗崩、便宜 |
| 动态 | 仅 `/api/inquiry` + `/healthz` | 能静态化的绝不动态 |
| 媒体 | 标准库解码 + 可选 `cwebp` | 不把构建绑在外部二进制上（AVIF 纯 Go 编码不可行） |

**二进制体积**：Windows amd64 约 22MB（含纯 Go SQLite），四平台发布包各约 6MB 压缩后（见 B5 M4）。

### 3.4 三种交付模式：要不要给客户后台

这是整个项目最重要的一个取舍，也是「给不给客户后台」这个问题的完整答案。

| | **模式 A：纯静态 + 内容文件** | **模式 B：静态 + 薄后台** | **模式 C：全动态 + 完整后台** |
| --- | --- | --- | --- |
| 内容怎么改 | 改 YAML / Markdown，重新构建 | 客户登录后台改产品 / 新闻 | 客户登录后台改**一切**（含内容模型） |
| 要写的代码 | 无后台 UI | 只有 products / news / media 三个模块 | 通用 CMS 全套（≈ 重写 Strapi） |
| 开发成本 | **1 份** | 1.5 份 | **4 份以上** |
| 交付速度 | 最快 | 快 | 慢 |
| 能否多卖钱 | ❌ 客户会问「我自己能改吗」 | ✅ 标准配置 | ⚠️ 卖得贵但养不起 |
| 适合谁 | 只要展示、内容一年不动的客户 | **80% 的外贸站客户** | 有专职运营的中大型客户 |
| 引擎现状 | ✅ M0–M2 | ✅ M3（`engine studio`） | ❌ 永不做 |

**推进路径（原计划）与实际执行**：

```text
v0.1 → 模式 A（不做后台 UI）
        ↓ 验证：能交付 1 个真实客户站，工时 ≤ 12h        ✅ 已完成
v0.2 → 加模式 B 的薄后台（只暴露三模块）                  ✅ 提前到 M2（admin）+ M3（studio）
        ↓ 验证：客户能自己改价格和产品，不需要找你          ✅ 本地可演示
v1.0 → 稳定在 A/B 双模式，永远不做模式 C 的通用后台         ✅ 当前定位
```

**为什么砍模式 C**：通用后台 UI 占一个 CMS 50% 的工作量，而这 50% 在交付阶段完全用不上。先砍掉它，把内核（数据模型 + 多语言 + SEO 输出 + 构建）做扎实，后台后面加一层薄壳就够。

> **术语澄清**：模式 C 常被说成「客户自己建站」，但准确含义是**客户在后台自定义内容模型与页面结构**（通用 CMS 能力），不是「客户拿引擎去起站」——后者是 M4 开源的目标（陌生人 10 分钟起站），属于获客渠道，不构成一种交付模式。两者成本差两个数量级，别混。

⚠️ **模式 A 的代价必须报价时讲清**：客户不能自己改内容，否则交付后会被反复要求「帮我改个价格」。对策是把「内容代维护」打包成月度服务，反而变成持续收入（对应 D2 / D5）。

## 四、数据模型

### 4.1 类型系统（仅 10 种）

| 类型 | 存储形态 | 说明 |
| --- | --- | --- |
| `string` | 单语或 i18n map | 短文本 ≤200 字符 |
| `text` | i18n map，含 Markdown | 长文本 |
| `enum` | 字符串 | 取值在 schema 声明 |
| `number` | 数值 + 可选 `unit` | 可筛选参数用这个 |
| `bool` | 布尔 | featured / published |
| `date` | `YYYY-MM-DD` | 证书有效期等 |
| `list<string>` | 数组 | 特性标签 |
| `ref` / `ref[]` | slug 引用 | 构建期解析，悬空即失败 |
| `media` / `media[]` | 相对路径 | 缺失即构建失败 |
| `group[]` | 内联结构 | 参数分组、区块内容 |

### 4.2 i18n 标记机制（多语言的技术保证）

```go
type Product struct {
    Slug    string            `yaml:"slug"        i18n:"-"`
    Title   map[string]string `yaml:"title"       i18n:"req"`   // 必译，缺则 build 失败
    Specs   []SpecGroup       `yaml:"specs"       i18n:"deep"`  // 深度遍历
    Moq     int               `yaml:"moq"         i18n:"-"`     // 数值不翻译
}
```

| 值 | 含义 | 缺失时 |
| --- | --- | --- |
| `-` | 不参与翻译 | 忽略 |
| `req` | 每语言必须有 | **build 失败** |
| `opt` | 可缺，触发 fallback | 警告 + 进报告 |
| `deep` | 递归检查内部字段 | 同成员规则 |

**多语言不靠自觉，靠构建期失败。** 忘译一个字段，构建就过不去。

### 4.3 公共字段

`slug`（类型内唯一）/ `status`（draft 不输出）/ `order` / `seo.title` / `seo.description` / `seo.og_image` / `seo.noindex` / `updated_at`（sitemap lastmod）。

### 4.4 实体

| 实体 | 角色 | 关键字段 |
| --- | --- | --- |
| `settings` | 单例全站配置 | brand / company(legal_name,address,founded) / contact(email,phone,whatsapp,wechat) / langs / default_lang / markets / social / analytics(ga4_id, gsc_verify) / **catalog(file,label，0.12.0 目录下载入口)** / **compliance(eu_responsible / legal_notice / epr，0.13.0 市场准入，见 8.4 上方说明)** / inquiry / theme / base_url / schema_version（另有 `nav` / `images` / `store` 三组次要配置，见 B4） |
| `page` | 固定区块页面 | `slug`（`home` 有特殊语义，其余自由）/ `title` / `blocks[]` / `cover` |
| `product` | 核心实体（33 个顶层字段） | 基础：slug/title/subtitle/category/scenarios/model_no/featured；内容：summary/description/highlights/applications；参数：`specs[]`（分组键值，`filterable` 必须有 `value_num`）；商务：**moq / moq_unit / lead_time / packaging / sample_policy / hs_code / price / carton**；认证：certificates/markets/test_reports；媒体：cover/gallery/video_url/**datasheet**；关系：related/cases |
| `category` | 两级品类 | slug/name/desc/parent/cover |
| `scenario` | 应用场景 | slug/name/summary/icon/cover |
| `certificate` | 证书 | **issuer / number / issued / expires / markets / file(PDF)** |
| `case` | 客户案例 | country(ISO-2) / industry / challenge-solution-result（result 须含数字）/ products / cover |
| `inquiry` | 运行时唯一写实体 | 见第九节 DDL |

> **`translation` 不作为独立实体**：文件方案下翻译内联在字段里；独立实体只在「需要待译/已译/已审状态流」时有价值（模式 C 的事）。

**产品字段的设计立场**：MOQ、交期、HS、包装、样品政策是 B 端买家最先看的五项，**必填**。缺了「专业度」不成立——这是 B1 C2 的引擎侧兑现。

## 五、校验体系

### 5.1 分级原则

> 会导致「上线后客户看到错误信息」的 → **失败**；只影响质量评分的 → **警告**。

这条原则保证校验不会被绕过——**一旦太严，人就会加 `--skip-check`，整套校验就废了。**

### 5.2 规则总表（56 个规则码：39 错 / 17 警，按主题归并为 14 行）

> 数字以 **v0.13.0 源码枚举为准：39 个 `addError` + 17 个 `addWarn`**（另有 `addI18n` 产出的 `I18N_MISSING` / `I18N_FALLBACK` 与构建层 `PAGE_BUDGET_EXCEEDED`，三者不计入这 56）。核对方法是脚本而非人眼：`grep -rhoE 'addError\("[A-Z0-9_]+"' internal/validate/*.go | sort -u | wc -l`——**必须带 `0-9`**，否则 `I18N_EMPTY` / `I18N_UNKNOWN_KEY` 这两个带数字的码会被漏掉，计数会凭空少 2（本次即踩过）。
>
> 演进脉络：0.11.0 新增 `PRIVACY_MISSING`（缺已发布 privacy-policy 页时提醒——引擎无法判定目标市场是否含 EU，所以是警告不是错误，交付门禁在 B6 拦）；0.12.0 新增 `MARKDOWN_BOLD_LITERAL`（落单 `**`）；**0.13.0 新增 6 条（2 错 4 警）**：`FACTORY_AUDIT_INCOMPLETE` / `TESTIMONIAL_INCOMPLETE`（证据缺可核验锚点 → **错误**），`GPSR_RESPONSIBLE_MISSING` / `EPR_MISSING` / `BUSINESS_TERMS_MISSING` / `LEGAL_NOTICE_MISSING`（缺位置 → 警告，交付门禁在 B6 拦）。**v1.2 曾按 0.11.0 核准为「35 错 / 12 警」，v1.8 复核实测 37 错**——说明那次人工清点漏了 2 个码。教训与 7.4 的 `og:image` 同一条：**数规则码、数区块、数皮肤这类事，只能枚举，不能凭记忆；枚举的正则本身也要先被数一遍。**

| 主题 | 规则要点 | 级别 |
| --- | --- | --- |
| 标识与唯一性 | slug 格式/唯一（按类型）；status 枚举 | ❌ |
| 引用完整性 | 所有 ref 指向存在且 published 的实体 | ❌ |
| 多语言 | 必译字段每语言有值；全空单列错误；可选缺失 → fallback + 报告；**i18n map 的键必须在 langs 白名单内（I18N_UNKNOWN_KEY）** | ❌/⚠ |
| 参数 | `filterable` 必须有 `value_num`；数值必须带 `unit`；参数必须有 `key` 且至少一个值 | ❌ |
| 商务 | `moq>0`；`moq_unit ∈ {kg,pcs,set,ton}`；`hs_code ^\d{6,10}$`（空值跳过）；`price.min ≤ max` 且币种 ISO 4217 | ❌ |
| 证书 | number 非空；已过期 → 警告且前台不展示；90 天内到期 → 警告；markets 必须在 settings.markets 内 | ❌/⚠ |
| 媒体 | 引用文件必须存在（缺失即失败，不是警告）；单图体积超限 → 警告 | ❌/⚠ |
| **主题** | **色板键 ∈ {primary, primary-fill, secondary, ink, paper, surface, muted, accent}；字体键 ∈ {heading, body, mono}；skin 须可解析（九套预置或站点 skins/ 目录自定义，SKIN_UNKNOWN）；旧键 layout 等同 skin；有 colors 无 primary → 警告** | ❌/⚠ |
| 页面与区块 | 区块 `type` 在白名单（20 种）；首页必须有 hero；每页能生成完整 hreflang 集 | ❌ |
| 链接 | 导航 href 落到真实页面；hreflang 互链闭环；**产物站内链接可达** | ❌ |
| SEO | title 30–60 / description 100–160；同语言产品标题不重复 | ⚠ |
| **证据（0.13.0）** | **`factory.audits[]` 有名称就必须有编号与日期（FACTORY_AUDIT_INCOMPLETE）；`testimonials.items[]` 有正文就必须有署名与公司（TESTIMONIAL_INCOMPLETE）** | ❌ |
| **市场准入（0.13.0）** | **`markets` 命中 EU/EEA/UK/GB 或任一成员国 → 必须有 `compliance.eu_responsible`；命中 DE → 必须有 `epr.de_packaging`；缺 `business-terms` / `legal-notice` 页 → 警告** | ⚠ |
| 结构 | company.legal_name/address 非空（Organization 必需）；base_url 为 https 绝对地址；schema_version 兼容 | ❌ |

**为什么「证据类」必须是错误级**：`factory` 和 `testimonials` 的共同点是**内容可以写得很像真的**——「已通过 BSCI 审核」「客户很满意」谁都会写。校验器拦不住真伪，能拦的只有「可核验的锚点有没有填」：报告编号与日期、署名与公司。没有锚点的证据不是证据，是形容词；而形容词出现在 B 端信任页上，比不写更伤（买家一查就知道是空的）。同理，`GPSR_RESPONSIBLE_MISSING` 只做警告：引擎无法断定客户是否真的在欧盟卖货，只能在他自己填了 EU 市场时提醒一句。

### 5.3 为什么「区块白名单」值一条规则

拼错一个 `type` 会让整块内容**静默消失**，页面看起来仍然正常。这类「合法但不正确」的输入只能靠白名单在构建期拦下。

### 5.4 校验的边界

校验器只管**结构与格式**，不管**商业判断**：它拦不住「MOQ 写错一个零」，也拦不住「英文像机翻」。后者属于 B1 B 维与 `B6` 第六节的写作规范。

## 六、构建流水线

```text
engine build
  ├─ ① Load      读 settings / content / theme → 内存模型
  ├─ ② Validate  56 个规则码；失败即中止
  ├─ ③ Resolve   解析 ref → 对象图；检测循环引用
  ├─ ④ i18n      按标记生成 fallback；产出缺失清单
  ├─ ⑤ Render    区块 → HTML（每语言一份）
  ├─ ⑥ Assets    图片变体发现 / 内容哈希 / 缓存头
  └─ ⑦ Emit      sitemap / robots / JSON-LD / hreflang / 404 / favicon
                 → .build/public + report.json
```

### 6.1 实现与设计的六处偏差（以本节为准）

| 项 | 原设计 | 实际实现 | 原因 |
| --- | --- | --- | --- |
| 区块契约 | 未细化 | 每个区块 = YAML 输入结构 + 视图结构 + `blk_<type>` 模板，输入走 YAML 二次解码 | 区块字段演进快，塞进公共模型会把它撑爆；代价是字段无编译期检查，用白名单兜住 |
| 固定页 slug | 枚举 7 个 | **任意 slug**，仅 `home` 特殊；`/en/{slug}/` | 实战场次需要 quality / private-label / technology 等页，枚举会逼着改引擎 |
| 图片 | 内置 AVIF/WebP 转码 | **不内置编码器**；发现同名变体则输出 `<picture>`，转码交给可选 `cwebp` | 纯 Go 无 cgo 编不出 AVIF；把构建绑在外部二进制上是交付风险 |
| 图片宽度 | srcset 4 档 | 变体发现 + 宽度探测；**宽度未知的候选不进 srcset** | `0w` 会让浏览器判全部候选无效，整张图不加载且零报错（B5 缺陷 5） |
| sitemap | 未定粒度 | 单文件，每条 URL 重复完整 hreflang 组 | 比 index 少一个出错点；5 万条上限远高于外贸站页数 |
| 主题 | 只改 token | token + **审美皮肤**（九套预置 + 站点自定义，免编译） | 只改颜色会让所有站长一样；皮肤换的是整套版式语法，且不碰内容与结构 |

### 6.2 report.json（交付凭证）

下面是 `clients/leafworks` 在 v0.8.2 下的真实产物，**照抄，不是示意**：

```json
{
  "site": "leafworks",
  "build_at": "2026-10-22T15:11:13+08:00",
  "pages": 70,
  "langs": ["en", "zh"],
  "errors": [],
  "warnings": [],
  "seo": {"hreflang_sets": 68, "hreflang_broken": 0, "sitemap_urls": 66, "link_broken": 0},
  "assets": {"images": 55, "media_files": 61, "media_bytes": 10183137, "oversized": 0, "transcoded": 0},

```

两点要注意：`errors` / `warnings` 是 **Issue 数组**（元素含 `code` / `entity` / `field` / `lang` / `message`），不是计数——交付时数一下 `len()` 才有「0 错 0 警」这个结论；证书过期统计不在本文件里，它是由 `CERT_EXPIRED` / `CERT_EXPIRING` 两条警告表达的（原稿把这两个字段写成独立对象，实现里没有）。

## 七、渲染与主题

### 7.1 区块（20 种，白名单）

`hero` / `richtext` / `image_text` / `stats` / `features` / `product_grid` / `category_grid` / `scenario_grid` / `certificate_grid` / `case_grid` / `process` / `team` / `faq` / `cta` / `logos` / `gallery` / **`factory`** / **`testimonials`** / **`legal_facts`** / `inquiry`

> 12 区块骨架是**页面级共识**（信任条 / 导航 / Hero / 产品 / 场景 / 工厂 / 认证 / 案例 / 服务 / 询盘 / 页脚 / 浮层联系），20 种区块是**组件级实现**。其中「页脚」与「浮层联系」不是区块，是 base 模板里的常驻组件（0.11.0 落地，由 `settings.company/contact/social` 驱动，无配置则不输出）。固定页 = 区块列表，首页也是普通固定页（`slug: home`），没有独立模板——两套语义迟早不一致。
>
> **0.13.0 新增三种都为「B1 v2.0 要求、但此前没有字段位」的证据类/合规类区块**：`factory`（D6 工厂证据链）、`testimonials`（D7 客户证言）、`legal_facts`（R2 法定披露，数据取自 `settings.compliance`，区块只提供标题）。三者都不是「多一种排版」，而是**把「没有证据」变成可渲染的缺口**：`factory`/`testimonials` 配了两条错误级校验（审核缺编号、证言缺署名即构建失败）。

### 7.2 主题 token

```yaml
colors: {primary, primary-fill, secondary, ink, paper, surface, muted, accent}
fonts:  {heading, body, mono}
radius: 2px
skin: classic | editorial | tech | industrial | organic | minimal | ecobike
```

- **键名是白名单，不是自由 map**：这 8 个色键与 3 个字体键是渲染层唯一会写进 CSS 变量的东西。多写一个键不会报错，只是「改了没效果」——v0.8.2 起由 `THEME_UNKNOWN_TOKEN` 在构建期拦下。
- **是 `primary-fill`（连字符），不是 `primary_fill`**。这个下划线写法曾同时出现在 B3/B4 两份文档里，照着抄的人会得到一个静默失效的主题。
- `accent` 与 `primary` **必须过对比度**（≥4.5:1）：强调色常被用于 kicker、步骤编号等小字，是 Lighthouse 高频翻车点（B5 缺陷 7）。
- `primary-fill` 是暗色主题的必要补充：深底文字色要亮、按钮填充色要深，同一个值无法同时满足。
- **主题不得改结构**，只能改 token 与皮肤名；否则每个客户都在改模板，复用率归零。皮肤体系见 7.3。

### 7.3 审美皮肤（0.10.0，CSS Zen Garden 模型）

**问题**：0.9.0 之前三站骨架已各自不同（区块序列相似度 56–62%），但「版式语法」只有一套——除 `image_text`/`cta`/`inquiry` 外，所有区块的容器都是同一个 `<section class="section">`，CSS 想按区块类型做差异化也没有抓手。此外 editorial/tech 两套布局变体的选择器硬编码在 `base.tmpl` 里，加一套审美就要改 Go 代码、重新编译。

**方案**：把「观感」整体抽成可替换的 CSS 文件（皮肤），HTML 完全不动。

```
theme.yaml                     皮肤名（skin:）+ 品牌 token（色板/字体/圆角）
engine/internal/skins/presets/*.css   九套内置审美，embed 进二进制
<site>/skins/<name>.css        站点自定义皮肤，免编译即生效（同名覆盖内置）
```

- **分工**：基础层 CSS（base.tmpl）只保「功能可用 + 响应式」——间距、栅格、表单、可读性；皮肤决定配色之外的**全部观感**：版式语法、边框/圆角/阴影、字阶、首屏构图、区块节奏。皮肤只需覆写它关心的部分，未覆写处落到中性基线，所以 30 行的皮肤也是合法的。
- **优先级靠顺序不靠 `!important`**：皮肤 CSS 由 `{{.SkinCSS}}` 追加在基础层之后，后写覆盖。
- **作用域**：皮肤每条规则都带 `html[data-skin=<name>]` 前缀，测试拦截无前缀规则。
- **自描述**：皮肤文件头部注释声明 `@skin / @label / @category / @tone`，`engine skins` 按行业分组展示；`@tone dark` 同时驱动渲染层的深色色板兜底（替代旧的 `layout == "tech"` 特判）。
- **九套预置**：`classic`（通用制造）/ `editorial`（出版文化）/ `tech`（消费电子，深色）/ `industrial`（机械工业）/ `organic`（食品农业）/ `minimal`（家居设计）/ `ecobike`（绿色出行：深林绿暗色门厅 + 白卡细线 + 薄荷绿，0.10.1 按设计稿 `design/ecobike-website.html` 逐段转译）/ `zentea`（茶韵东方：米白纸底 + 衬线标题 + 金色点缀 + 墨绿茶山渐变暗带，0.13.3 按设计稿 `design/zentea-website.html` 逐段转译）/ `aeronova`（航宇暗色：全页暗底 + 固定青色网格与辉光球 + bg2 暗带节奏 + 青靛渐变按钮/logo 底座 + mono 编号卡，0.13.4 按设计稿 `design/aeronova-website.html` 逐段转译）。
- **临时预览**：`engine build --skin industrial` 用同一份内容换皮构建，不写回 theme.yaml——比稿时连续出几版不污染配置。
- **校验**：皮肤名不存在 → `SKIN_UNKNOWN`（错），报错附可用清单与最接近的候选名；旧键 `layout` 等同 `skin`，存量站点不用改配置。
- **移动端契约**：基础层的 900px 断点重压所有网格；皮肤把列数写死在 `html[data-skin=x]` 上，特异性更高，因此每套皮肤末尾必须自带同断点重压——缺了会被测试拦下。

**实测**（同一份 ridgeway 内容 × 六套皮肤，0.10.0；0.10.1 加入 `ecobike` 后七套同样通过；0.13.3 加入 `zentea` 后八套同样通过（leafworks 实测）；0.13.4 加入 `aeronova` 后九套同样通过（kestrel 实测））：各版构建均 0 错 0 警、390px 零溢出，观感从「工程图纸」到「画廊标签」完全不同——这就是「内容与审美解耦」要买的东西。

| 现象 | 状态 |
| --- | --- |

## 八、SEO 与结构化数据

### 8.1 URL 与 hreflang

| 页面 | 路径 |
| --- | --- |
| 首页 | `/{lang}/` |
| 产品列表 / 品类 / 详情 | `/{lang}/products/`、`/{lang}/products/{category}/`、`/{lang}/products/{category}/{slug}/` |
| 场景列表 / 详情 | `/{lang}/scenarios/`、`/{lang}/scenarios/{slug}/` |
| 案例 | `/{lang}/cases/`、`/{lang}/cases/{slug}/` |
| 固定页 | `/{lang}/{slug}/` |
| 询盘成功 | `/{lang}/thank-you/`（noindex，构建自动生成） |
| 404 | `/{lang}/404.html` + 根 `/404.html` |

hreflang 对每个可索引实体输出**全集**（含 `x-default`），并做三条构建期硬校验：**互链完整**（70% 的 hreflang 错误来自缺返回链接）、**href 可达**、**语言码合法**（BCP 47）。

### 8.2 JSON-LD 现状（B1 E4 视角）

| 页面 | 已输出（0.12.0） | 仍缺 |
| --- | --- | --- |
| 首页 | ✅ `Organization`（legalName / address / telephone / email / description + **`logo` + `sameAs`**） | — |
| 产品详情 | ✅ `Product` + `Brand` + `sku` + `image` + `category` + **`BreadcrumbList`** | `offers`（D9 全询价下的已知代价，产品决策不是缺陷） |
| 列表 / 案例 / 场景 / 404 | ✅ **`BreadcrumbList`**（与视觉面包屑同源生成，永不分叉） | `ItemList`（列表页可加，非 B1 要求） |
| 其他固定页（about / contact / 法务） | ❌ 无 `Organization`——它只随首页输出 | 逐页 Organization，或把首页实体做成全站引用 |
| FAQ | ✅ **`FAQPage`**（faq 区块问答直出） | — |
| 案例 / 认证 | ❌ | `Article` / `ItemList` |

> **B1 v2.0 的 E4 四项（Organization 含 logo+sameAs / Product 含 sku+brand / BreadcrumbList / FAQPage）已全部输出**，引擎侧不再欠这一条。
>
> **产物取证**（ridgeway **0.13.0** 重建，**75 个 HTML 文件**，en+zh）：`BreadcrumbList` **47 页**、`FAQPage` **10 页**、首页 `Organization` 带 `logo` 与 `sameAs`、`og:image` 与 `twitter:card` **各 75 页**（100%）。本表在 v1.7 仍写着「面包屑仅视觉」「FAQ 无 schema」——那是 M5-5 落地**前**的状态，与第十四节 M5-5 的 ✅ 自相矛盾了两天。**文档的「缺失」清单必须带版本号，否则它会一直缺下去。**

### 8.3 robots / sitemap / favicon

robots 排除 `/api/`、`/*/thank-you/`；sitemap 单文件带 `xhtml:link`；favicon 由主题主色**构建期自动生成**（缺 favicon 的 404 会直接扣 best-practices）。

### 8.4 机器可读产物（0.13.0，E7 / C10）

搜索之外的第二个入口是**机器读取**：AI 搜索抓 `llms.txt`，采购把 CSV 丢进比价表。这两类产物都是**构建期生成、零内容成本**，所以必须做在引擎里——每站手写一遍等于每站都可能写错，且不可能随内容更新。

| 产物 | 路径 | 内容来源 | 为什么这样做 |
| --- | --- | --- | --- |
| `llms.txt` | `/llms.txt` | 品牌/tagline、`company`（法定名、成立年、地址）、`contact`、`markets`、`langs`、已发布产品（型号·MOQ·交期·HS）、已发布页面清单 | 只写「已被内容证明的事实」。AI 回答「这家能做 X 吗」时需要的是型号与 MOQ，不是形容词；实体段同时把 **NAP 表述固定下来**，减少各页说法不一 |
| 参数 CSV | `/{lang}/products/{cat}/{slug}/specs.csv` | 产品全字段：`Group,Label,Value` + `#` 注释元数据（产品名/SKU/型号/品类/MOQ/交期/包装/HS/箱规/样品政策） | `Group` 列让采购能按组透视，也能只取「商务」几行做比价表；Excel / Numbers / pandas 都直接可读 |
| SKU 清单 | `/data/sku-list.csv` | 所有**已发布**产品（slug / model_no / title / category / moq / moq_unit / lead_time / hs_code / url） | 买家发 RFQ 的底表。草稿产品不进清单——这是给买家的文件，不是内部台账 |
| 产品图包 | `/data/product-images.zip` | 产品封面图 + `README.txt`（用途与命名说明） | 「发我几张图」是外贸邮件里最高频的一句。图包**只在真有封面文件时才生成，页脚链接也跟着条件渲染**——宁可不给链接，也不给死链（E5） |

> **一条设计取舍**：这四类产物都不做配置开关。它们要么体现「站上有产品」这一事实，要么不体现；让客户选「要不要导出参数」只会制造「有人导、有人没导」的不一致。

## 九、询盘链路

### 9.1 对外暴露面（只有 2 个）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/inquiry` | 唯一写入口，支持 JSON 与表单 |
| `GET` | `/healthz` | `{ok, version}` |

> 原稿还列了 `GET /api/content/{entity}`「P2 预埋，默认关闭」——**代码里没有这个路由**。列一条不存在的接口，比不列更糟：读文档的人会去调用它、会以为已经为 Headless 留了口子。P2 若真要做，届时按 P2 立项，不做预埋。

### 9.2 处理顺序（严格，先便宜后贵）

```text
① 方法/Content-Type → ② 体积 ≤32KB → ③ 蜜罐 _hp 非空则静默 201
→ ④ 提交速度 <3s 静默 201 → ⑤ 限流（IP 哈希：10/h，30/24h）→ ⑥ Turnstile（若配置）
→ ⑦ 字段校验 → ⑧ 内容启发式（spam_score）→ ⑨ 落库 → ⑩ 异步通知（邮件/webhook）
→ ⑪ 服务端结构化日志（GA4 `generate_lead` 转化事件已由 0.12.0 在致谢页发出，前提是访客同意了 Cookie）
```

**第 ⑨ 步必须先于 ⑩**：先落库再发通知，邮件服务挂了也不会丢询盘。

第 ⑤ 步是两道闸，且两道都在同一把 IP 锁内复查：小时闸挡突发，日闸挡「每小时九个、连发一整天」。只有小时闸时，单 IP 一天最多能灌 240 条——原稿写的「24h 30 次硬封」在 v0.8.1 的代码里并不存在，v0.8.2 才补上（缺陷 14）。

### 9.3 反垃圾五层

蜜罐 → 时间戳 → 限流（IP 哈希 10/h + 30/24h 日闸）→ Turnstile → 内容启发式。

两个阈值可配（`settings.inquiry.rate_limit_per_hour` / `rate_limit_per_day`），默认值刻意留小：B 端外贸站的单个 IP 一天提交 30 条询盘，本身就不像真人。

**兜底原则**：误判不删，只标 `spam_score`——**宁可多一条垃圾，不可丢一条真询盘。**

### 9.4 实现中修正的三处

| 项 | 原设计 | 实际 | 原因 |
| --- | --- | --- | --- |
| 限流并发 | ⑤ 查 `count` 再继续 | **按 IP 分片互斥锁内复查再插入** | 压测同 IP 100 并发阈值 10 放行 18 条（超发 80%）；检查与写入不在同一临界区 = 没有上限 |
| 无 JS 提交失败 | 未定义 | **400 错误页，不跳成功页** | 跳「提交成功」会骗客户以为发出去了 |
| `lang` 提交值 | 未定义 | 收敛到 `settings.langs` 白名单 | 它会拼进 303 地址，直接用构成路径注入 |

另两条维护结论：SQLite 必须用纯 Go 驱动（cgo 破坏单二进制承诺）；Windows 控制台需切 UTF-8（否则询盘中文全乱码）。

### 9.5 容量与压测结论

> 本节原为独立的《12 询盘链路压测报告》，2026-10-22 并入。被测版本 `0.2.0-m1`，数据至今未被后续版本推翻。

**为什么不用 wrk / ab**：通用工具只能给状态码分布与延迟分位，而这条链路的核心承诺是**不丢单**——需要回答「返回 201 的那一条，真的在库里、且内容没在并发下被截断或串码吗」。所以压测工具（`engine/tools/loadtest`，329 行 Go）自己闭环：

```text
① 并发发压（记录每次响应的 ULID + 延迟 + 状态码）
② 只读打开 SQLite ③ 按 email 前缀定位本批次
④ 逐条比对：每个 ULID 在库？name/message/email/lang 逐字节相同？主键重复？
⑤ 任一不符退出码 1 —— 可以直接放进 CI
```

| 场景 | 配置 | 吞吐 | p99 | 回库核对 |
| --- | --- | --- | --- | --- |
| A | 100 并发 / 100 个不同 IP | 428 rps | 181 ms | 201×100，100/100，逐字节一致 |
| B | 100 并发 / 同一 IP（阈值 10） | 100 请求 / 83 ms | 76 ms | 201×10 + 429×90（**修复前 201×18**） |
| C | 50 并发 / 500 请求 | 609 rps | 618 ms | 500/500 |
| D | 200 并发 / 1000 请求 | 601 rps | 1122 ms | 1000/1000 |

各场景与复测累计 **1910 条：0 丢单 / 0 重复 / 内容逐字节一致**（含中文、`& < > " '`、emoji）。场景 C 与 D 吞吐几乎相同（609 vs 601）而 D 的并发是 4 倍、p50 延迟 4.9 倍——典型的饱和信号：**到产能上限后，多出来的并发只是在排队**。服务端同期 `SQLITE_BUSY` 0 次。

> **读数口径**：i5-10400F / 16 GB / Windows 10 / 本机 SSD，Go 1.27.3，SQLite WAL + `synchronous=FULL` + `busy_timeout=5000`，**压测端与被测服务同机回环**。所以延迟绝对值偏乐观（没有跨境 RTT，真实环境另加 100–300 ms），CPU 竞争偏悲观（压测端自己吃掉一部分核心）。这三类数字只用来判断三件事：有没有丢单、吞吐拐点在哪、并发提高时延迟怎么涨——**不要当客户体验的绝对值引用**。

**600 rps 天花板的成因**：不是 Go、不是 HTTP 栈、不是 SQL。只把 `synchronous` 从 `FULL` 改成 `NORMAL`，同负载 601 → **1479 rps**、p99 1122 → 289 ms（2.46×）。瓶颈就是「每次 INSERT 都要 fsync」。

**默认保持 `FULL`，且不做成配置开关**：进程崩溃两种设置都不丢，差别只在**操作系统崩溃 / 断电**——FULL 不丢，NORMAL 可能丢最近若干条。真实需求 0.2 次/秒，为 2.5 倍吞吐牺牲任何持久性都不划算。真有高吞吐客户（展会后集中爆发、把表单当 API 用），是**一行 DSN 参数**（`file:...?_pragma=synchronous(NORMAL)`，引擎支持 URI 原样透传），写进交付说明即可——**每多一个开关，就多一种要维护的组合**（与 M5 不加开关同一理由）。

**真实风险不是容量，是分布式刷单**：单 IP 被 10/h + 30/24h 挡住；1000 个 IP 各发一条就能打满 600 rps。正确应对是在 Cloudflare 层做速率限制与 Bot 管理，不是堆应用层吞吐——那是 CDN 的本职。

**以上全部以「单进程」为前提**：限流锁是进程内的，两个 `engine serve` 同时跑，同一 IP 会各放行一份。多实例部署必须把「复查 + 插入」下沉成数据库层的原子操作（`INSERT ... SELECT WHERE (SELECT COUNT(*) ...) < N`），**不是加分布式锁**。

**这个缺陷是怎么被锁死的**：复测 `201 × 10 + 429 × 90`，**精确等于阈值**；新增 `TestRateLimitNotBypassedByConcurrency`（40 并发 / 阈值 5），并**临时去掉锁反向验证它会变红**——一个永远为绿的测试毫无价值，能证明它会变红，才算真的锁住了缺陷。

### 9.6 存储（唯一 DDL）

`inquiry`：`id`(ULID) / `created_at` / `site` / `lang` / `country` / `name` / `company` / `email` / `phone` / `product_slug` + **`product_title`（快照）** / `volume`（0.11.0 起，年采购量档位，老库 ALTER 自动补列） / `message` / `source_page` / `referrer` / `utm_*` / `ip_hash`(**加盐哈希**) / `user_agent` / `spam_score` / `status` / `notified_at` / `note`。

两个设计要点：`product_title` 存快照——产品下架后历史询盘仍可读；`ip_hash` 加盐，既满足限流又不构成个人数据留存（GDPR 友好）。

## 十、两个后台

| | `engine admin` | `engine studio` |
| --- | --- | --- |
| 数据源 | YAML **文件** | **内容库**（`.data/content.db`） |
| 认证 | 无，强制回环 `127.0.0.1:9090` | 账号 + 角色（admin/editor）+ CSRF |
| 服务对象 | 交付期的**你自己** | 交付后的**客户** |
| 状态机制 | `status` 字段即状态 | 审核流 `draft → in_review → published` |
| 改动生效 | 保存即重建 | 走库，`/preview/` 预览，`export` 回文件 |

**两条链路互不相通，且刻意如此**：admin 改文件不写库，studio 改库不写文件。做成双向实时同步就要处理「文件手改 / 库手改」的冲突合并——那是另一个产品级难题。代价是交付时必须讲清楚：**别在两边同时改同一个产品。**

**studio 的保留语义**：字段 schema 只声明客户该动的字段；保存时 payload 解码进模型 → 应用表单值 → 整体重序列化，schema 外字段（specs/blocks/seo）自动保留。代价是 schema 与 setter 必须同步，由测试夹住。

**安全**：PBKDF2-SHA256 210k（标准库，零新依赖）；会话存表（撤销 = 删一行）；CSRF 每会话一令牌；admin 只绑回环 + 路径白名单 + 穿越检查；询盘列表对浏览器裁剪 IPHash/UA/UTM。

## 十一、内容库与双向迁移

```go
type Loader interface { Load() (*model.Site, error) }   // 单方法，上层零改动
type FileLoader struct{ root string }
type DBLoader   struct{ db *sql.DB }
```

- **payload 存 YAML 文本**而非 JSON：`Block.Extra` 是 `map[string]any`，JSON 往返把 int 变 float64，会污染区块二次解码。
- **列提升**：slug / order / status / category / country / expires / parent / featured 独立成列，列表与表单查询走列、不解析 payload。
- **单向闸**：`import` 对已有库拒绝（后台可能有未导出编辑），`export` 对非空目录拒绝且不触碰文件。
- **能拿回自己的内容**本身就是对 Wix/Shopify 的实质优势。

**A 维仍 70% 的原因没有变**：A6（企业邮箱、WhatsApp Business 认证）是客户账号资产；A7 路径深度由模板决定且实测已达标，属「已兑现但分数被同维其它条目平均掉」。

按 B2 v1.0 口径复算自测：**77 分（优秀，未达一等）**；按 B1 v1.0 逐条严格口径（E4/E7 各缺一项）为 **72.5**，细节见 `B6` 9.2。**这两个数只在 v1.0 口径下有效**：B1 v2.0 增了 11 条（C9/C10/D6/D7/E7/R2/R4/R6 等）且改了算法，v2.0 复算需按 50 条重跑，登记在 `B6` 9.2 的口径说明里。

## 十六、工程约束（血泪版，完整 30 条见 `engine/README.md`）

1. **测试不得拿示例站当夹具**——示例站是会演进的内容，不是契约。
2. **前端读 JSON 一律用小写键**——Go 的 tag 是小写，JS 写 `f.Group` 静默得到 `undefined`，列表全空但不报错。
3. **i18n 值禁止写成 YAML 流式映射**——`{ en: A, 20 MP, zh: B }` 合法但会静默截断。
4. **宽度未知的图源禁止进 srcset**——`0w` 会让整张图不加载。
5. **文件存在但解析失败必须报错**，只有「文件缺失」才允许回退默认值。
6. **限流的检查与写入必须在同一临界区**，否则等于没有上限。
7. **主题只改 token 与布局变体**，不改结构。
8. **交付中的引擎缺陷修复必须是通用修复**——行业特性 100% 落在 `content/` + `theme/`。
